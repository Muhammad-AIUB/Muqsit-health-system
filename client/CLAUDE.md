# client/CLAUDE.md — Doctor app (Next.js 14)

The doctor-facing SPA. App Router pages are thin shells; almost everything renders through `src/components/Muqsit.tsx` → `TabRouter.tsx` (tab = URL segment) with state in **one large context store**: `src/context/MuqsitContext.tsx` (`MuqsitStore = ReturnType<typeof useMuqsitStore>` — add to the return object and the type follows). Auth lives in `src/context/AuthContext.tsx`; server state in React Query hooks (`src/hooks/`); all HTTP through `src/lib/api.ts` (`apiFetch`: credentials, X-Workstation header, silent 401 refresh).

**Env trap:** `NEXT_PUBLIC_API_URL` must be set in both `.env.local` (dev, gitignored) and **`.env.production` (committed — the deployed build uses it)**. A missing prod value silently points the live site at `localhost:4000`.

## ⚕️ Clinical-accuracy rules specific to the client

- **Calculators (`src/lib/calculators/`, ~77 of them, wired via `calculator-registry.ts`):** each implements a published clinical score/formula. Never alter a formula, cutoff, unit, or interpretation without the published source; keep severity labels (`success/warning/danger`) consistent with the source. New calculators register in the registry and appear in Investigation "Special Scores".
- **Investigation catalog (`src/data/investigations.ts`):** the master test list (`INV_CATS`: `{cat, tests:[{name, fields}]}`, some via the `txt([...])` name-only helper). Test names must stay **unique across categories** (duplicates were purged deliberately); field units are clinical facts — verify before editing.
- **Never round, reformat, or "normalize" an entered clinical value.** Display exactly what the doctor typed.
- **Medicine search hits the server** (`/medicines/search`, raw `medicines` table). `src/data/drugs.ts` is only an 18-item static fallback for the legacy drug picker / monthly-cost demo — do not treat it as the drug database.
- **Prescribing alerts (`src/data/rxAlerts.ts` rules, `src/lib/rxAlerts.ts` matcher, `RxAlerts.tsx` → `RxAlertBanner.tsx` UI):** shown on **both** prescribing surfaces — the OPD editor (top of `ReportsSection`, desktop and mobile alike) and the IPD order sheet (above the ℞ pad in `IpdDetailView`). Keep them in step: a doctor who learns to trust the alert on one screen must not silently lose it on the other. Three structural rules that are not style preferences:
  - **Render `<RxAlerts input={…}/>`, never `RxAlertBanner` directly.** `RxAlerts` wraps the banner in an error boundary. The banner lives *inside* the editor and the order sheet, and React unmounts the whole tree on an uncaught render error — one bad value would take out the entire screen a doctor prescribes through, not just the advisory.
  - **Callers assemble the input only; the matching runs inside the banner.** Doing it in the caller's `useMemo` puts the computation outside the boundary, where no wrapper can catch it.
  - **The check fails loud, never silent.** `checkRxAlerts` is total — it normalises unknown input, skips what it cannot read, and returns an `unreadable` count that the banner turns into a visible "Prescribing check was incomplete" notice; the boundary's fallback says "not checked", not "nothing found". A doctor reads a blank advisory as *no contraindication*, so an empty render must only ever mean the rules actually ran and found nothing.

  The data file is a transcription of the physician's rule sheets and nothing else — adding a rule, correcting a spelling ("atleast" is theirs), or filling a truncated row from memory is a PRIME-DIRECTIVE violation, not a tidy-up. `src/lib/rxAlerts.test.ts` pins each message string, so a failure there is a clinical regression: check the source sheet before touching the expectation. Matching rules worth knowing:
  - Terms match on **word boundaries**, case-insensitively, so `pregnant` does not fire on `prepregnant`.
  - **Entecavir now carries all FOUR rows of its sheet** (`entecavir.xlsx`, received 2026-08-28): Pregnant and Lactating mother (one shared sentence), CKD, and Decompensated liver cirrhosis. The three message strings were written into `data/rxAlerts.ts` **straight from the spreadsheet cells**, not retyped — trailing space and all — and re-read from the file afterwards to prove they matched. Do the same for the next sheet; a renal dosing band is not something to copy by eye.
  - **A message can be a TABLE, so both surfaces render it `white-space: pre-line`.** The entecavir/CKD advice is four CrCl dose bands on four lines plus two closing sentences; collapsed into a paragraph they run together and read as one dose. Pinned in `RxAlertBanner.test.ts` (the style and every band) and `rxAlerts.test.ts` (band by band). Checked in a real browser at 1280×800 and 375×812: nine lines, no sideways scroll on either.
  - **The condition is read from ANY field in `CONDITION_FIELDS`, not just Final diagnosis.** The physician describes these rules in terms of the final diagnosis because that is where they write them, but `Associated illness` (whose quick-picks include CKD and CLD), `History` and the IPD sheet's own labels all still fire. Narrowing that list would take away warnings that work today — a clinical decision, not a cleanup.
  - Match terms added beyond the sheet's own words are only ever the same condition said differently (`chronic kidney disease` for CKD, `decompensated cirrhosis` for decompensated liver cirrhosis). Bare `decompensated` is NOT matched — it belongs to heart failure too — and neither is the `DCLD` shorthand; ask the physician before adding one.
  - A condition immediately preceded by a negator (`no`, `not`, `non`, `denies`, `without`, …) is skipped. That guard is deliberately literal — anything more ambiguous still fires, and the doctor judges from the record.
  - **The same warning is drawn against the medicine that raised it, in the ℞ pad (2026-08-17).** `rxAlertsByLine()` returns `Map<rxDrugs index → messages>`, and it is the ONE source the pad bubbles read on both prescribing screens — two independently-derived versions of a contraindication could disagree. The index comes from `AlertEvidence.rxIndex`, carried by the matcher, **not** matched back by drug text: two lines of the same brand at different strengths are indistinguishable by text. `rxDrugIndexByRow()` in `lib/rxRows.ts` maps a pad row onto that index using the same predicate as `rxItemsFromRows` — an off-by-one there would show a pregnancy contraindication against the drug on the next line.
    - **In the editor: ONE blinking sign, then the advice under its own medicine** (`RxPadAlerts.tsx`, physician's decisions 2026-08-28, twice). A single round red sign sits in the ℞ pad's toolbar beside ✎ Edit and blinks while any warned medicine is on the pad — **one sign however many warnings there are** — and the red bubble sits under each medicine that raised one, tail pointing up at that line. **Since 2026-09-24 (physician's flow) a warning appears ON ITS OWN when its medicine is written; the sign stays lit while any warned medicine is on the pad, whether or not its message was dismissed; pressing it brings every dismissed warning back (and, pressed with all showing, tucks them all away); it goes out only when the medicine leaves the pad, and a medicine written anew is shown again.** The dismissal state is `ignoredAlerts` in `MuqsitContext`; `SignBody` clears the dismissal of a warning whose medicine left. Pinned in `RxPadAlerts.test.tsx`. It is a **15px filled disc** with a white `!` inside a 24px button — at this size an outlined ring with a hairline `!` reads as a stray character, while a 24px hit area keeps it tappable on a phone — and it pulses a soft halo rather than fading out: the dot never drops below 0.4 opacity, because a warning that blinks all the way out is one a doctor can look straight past. The blink stops under `prefers-reduced-motion`; the dot does not. **The bubble sits IN THE FLOW, never over it.** Between those two decisions the advice lived in a floating panel hung off the sign; it was dropped the same day because it moved around the screen on every scroll, and advice that drifts away from its drug is advice that can be read against the wrong one. In the flow it travels with its own line — verified in a real browser: 3px under the medicine before a scroll and 3px under it after the pad was scrolled to the bottom and the page moved 300px. `MedicinePad` owns the open/closed state (one switch for the whole pad) and keeps the **text guard** on the row→alert index: `rows` is the pad's own state while `alertInput` comes from context one render later, so for a frame after a line is deleted the indices disagree — long enough to be seen and photographed against the wrong medicine. Sign and bubble each carry an error boundary and run the matching in a child, exactly like `RxAlerts.tsx`, and the fallback SAYS the check did not run. **Nothing is hidden by any of this:** the banner still lists every alert in full at all times, and every alert is still logged to the activity feed on save.
    - **⚠️ NOT on the printed sheet, and not in the saved copy (physician's decision, 2026-08-17).** The advice exists only while the doctor writes: the printed prescription and the gallery snapshot show what the doctor entered, not what the system inferred. A red callout row *was* printed earlier the same day (`RxLine.alerts`, `.rx-alert-*`) and was removed the same day — `prescriptionDoc` now takes no alert input at all, `PrescriptionView` passes `m.rxItems` straight through, and `prescriptionDoc.test.ts` pins the absence of the callout markup, its stylesheet and its `#c0392b`. Do not reintroduce it as a safety improvement; it is a product decision that was made and reversed.
    - **One assembly, `hooks/useRxAlertInput.ts`**, shared by the banner and the pad. Two surfaces assembling it separately could scan different sidebar fields and then disagree about whether a drug is contraindicated.
    - **Both prescribing screens number their ℞ lines the same way.** `IpdDetailView` used to build `rxDrugs` with its own filter (`isMedicine && !continuation`, keeping empty rows); it now goes through `rxItemsFromRows` like the OPD editor. The matched *pool* is identical either way — blank rows and continuations carry no drug text and the matcher drops them — but the **indices** are what attach a warning to a line, and a second numbering would put the bubble on the wrong medicine. Pinned in `rxRows.test.ts`, including a test that the old basis genuinely disagrees. The IPD pad gets the bubbles too and `showHabits` stays off there (ward doses are not outpatient habits, design D5).
  - **The banner shows the advice only.** The `Because: <drug line> + <sidebar entry>` line under it was removed on 2026-08-16 at the physician's request — the advice already names the drug and the condition, so the echo was noise on a screen read every visit. `RxAlert.evidence` is still computed by the matcher and simply has no reader; `RxAlertBanner.test.ts` pins the absence, so restoring it is a product decision, not a bug fix. A side effect worth knowing: nothing a doctor types is rendered in the banner any more, so typed markup cannot reach it at all.
  - Only the fields in `CONDITION_FIELDS` are scanned for conditions, compared **case-insensitively** because the two screens name them differently (OPD `Chief complaints`; IPD `Sign` + `Symptoms`, and `Chief Complaints` on admissions written before that rename). Drug history, investigation findings, procedure and follow-up vitals are excluded on purpose (a drug named *Pregnacare* is not a pregnancy). It is an allowlist so a newly added field cannot silently start firing clinical alerts — adding one is a deliberate edit.
  - **drug-drug rules see the ℞ pad plus CURRENT drug history**, where "current" is the same derivation `DrugHistoryField` uses for its Current medications tab (entry dated on `ptDate`). Distant-past entries are excluded on purpose — a timing rule fired for a drug stopped two years ago is alert fatigue, and a doctor who stops reading alerts is the failure this feature exists to prevent. **At least one of the two drugs must be on today's ℞:** if both are already current, nothing changed this visit and the alert would repeat on every open. Do not "simplify" either half of that condition away.
  - `Sofosbuvir+Velpatasvir` matches on **velpatasvir**, not bare sofosbuvir — sofosbuvir also ships with ledipasvir and daclatasvir, and the advice text names the velpatasvir combination.
  - **Known gap:** a brand free-typed by hand (not picked from the medicines table) carries no generic, so a rule written against the generic cannot see it. Picked medicines are covered — see `RxItem.generic` below.
- **Prescribing habits — "Your usual" (`hooks/useRxHabits.ts`, `lib/rxHabitRows.ts`, `lib/rxHabitKey.ts`, rendered inside `MedicinePad.tsx`):** the doctor's own past instructions for the medicine being typed, offered as full lines above the medicine results. The domain rules are in the root `CLAUDE.md`; these are the client-side ones:
  - **`showHabits` is opt-in and defaults to FALSE.** Four screens render `MedicinePad` — the OPD ℞ pad (`RightColumn`, the only one that opts in), the IPD order sheet, the Drug-history pad and the template editor. Ward doses and a patient's existing medication are not outpatient prescribing habits, so the default has to be "off": a new caller must never pick up clinical suggestions by accident.
  - **The render is total, and the conversion is a pure module for that reason.** `contLines` reaches the browser from a `Json` column, so `safeContLines` skips anything it cannot read rather than mapping over it, and every string goes through `safeHabitText`. This code runs *inside* the prescription editor, where React unmounts the whole tree on an uncaught render error — the same failure that took out `rxAlerts` on 2026-08-01. `rxHabitRows.test.ts` throws garbage at every entry point.
  - **Insertion never overwrites.** `insertHabitRows` replaces the clicked row and SPLICES the tapering lines below it, pushing what followed downward; focus then goes to the **next medicine row**, not `dose` — the clicked row is already complete, which is the entire point.
  - **The count reads "7 patients", never "7×".** It means distinct patients, and a bare `×` invites the reader to supply their own meaning for the one number that separates a routine dose from a one-off.
  - **Empty renders nothing — never an empty-state message.** A failed lookup resolves to `[]` silently. On a clinical screen "no suggestions" and "the lookup failed" must not look alike, and the safe rendering of both is silence plus a working dropdown; the operator hears about it in the server log instead.
  - **`✕` needs the permanent way back, not just Undo.** Hiding raises the Undo bar — which lives OUTSIDE the dropdown, because the dropdown closes on the very click that raises it — and the group also shows `N hidden — show` whenever that medicine has hidden rows. Without that second route `✕` is a one-way door: dismiss the Undo bar, change your mind tomorrow, and the suggestion is unreachable. Hiding is never destructive (the prescription record is untouched), so a failed hide is reported by simply putting the row back.
  - **The `generic` comes from the SERVER, with the suggestion.** Prescribing-alert rules are written against generics (`entecavir`) while the ℞ line carries the brand (`Tablet. Barcavir 0.5 mg`), and a habit learned from history cannot carry a generic of its own — so `RxItem.generic` is the only bridge, and losing it means a contraindication silently stops firing on the *fastest* path through the editor. The first design resolved it on the client from the medicine results already loaded; that made a safety field depend on a race between two independent requests, so `RxHabitGroup.generic` now travels on the same response and cannot separate from the suggestion. `resolveGeneric` in `rxHabitRows.ts` remains as a fallback. Pinned end-to-end (suggestion → generic → alert) in `rxHabitAlerts.test.ts`, using the real Barcavir/Entecavir pair.
  - **`lib/rxHabitKey.ts` is a deliberate mirror of `server/src/rx-habits/normalise.ts`, and the two test files share one literal table** (`rxHabitKey.test.ts` ⇄ `normalise.spec.ts`) so editing one copy alone turns a suite red. It backs that fallback resolution — matched on the NORMALISED key, because a raw comparison misses on a space (`500 mg`), a case, a dropped `n/a` or a form qualifier. A mismatch yields no generic, never another medicine's.
- **`RxItem.generic`** is set only when the line was chosen from the medicines dropdown; `drug` holds the brand label (`"Tablet. Entaliv 0.5mg"`). It is **cleared as soon as the doctor edits the drug text by hand** (`MedicinePad.tsx`) — a stale generic pointing at a different medicine would let a safety rule fire on the wrong drug. Additive: prescriptions and drafts saved before it simply lack the field.
- **OCR (`src/lib/ocr.ts`, tesseract.js)** verifies the typed NID number against the uploaded NID photo during signup. It is assistive only — never let OCR overwrite what the user typed.

## Storage string protocols (the data model hiding in strings)

These formats are persisted in drafts, prescriptions and patient JSON columns — **changing them silently orphans existing data**. Extend parsers, don't break them:

- **Investigation finding:** `dd/mm/yyyy:TestName:value` (parse via `lib/investigationSummary.ts`). Report-pool images: `dd/mm/yyyy:Report N:[image attached]`; test-tagged images use key `dd/mm/yyyy:TestName` in `invImages` + a `…:[image attached]` entry. `[image attached]` / `Report N` rows are filtered out of print and summaries.
  - **A test's report image is only ever attached by an explicit act of the doctor** — dragging the open report onto that test's "Add report image", or picking a file there (`tagTestImage`/`untagImageKey` in `InvestigationPopup.tsx`). Until 2026-08-16 a `resolveTestImage()` fallback stamped *whatever report was open in the left viewer* onto every result the doctor typed (`addInvResult`, `addInvNormal`, and the auto-save on date-change/close), so a finding's 📎 opened a report it was never taken from — one report silently became the evidence for every line on the visit. Do not reintroduce a "helpful" default: on a clinical record an attachment has to mean the doctor attached it, and a wrong one is worse than none. Each attached image is a thumbnail + ✕ on the test card so the doctor can see what landed and take any one back off. **Findings saved before that date keep their auto-stamped images** — nothing was rewritten; the ✕ is the doctor-driven cleanup.
  - **A test holds MANY images (2026-08-16), keyed `dd/mm/yyyy:TestName`, `…#2`, `…#3`** — helpers in `lib/investigationImages.ts` (`testImageKeys`, `nextImageKey`, `hasImageUrl`, `hasValueLine`), unit-tested in `investigationImages.test.ts`. The first image keeps the historic unsuffixed key, so every draft/prescription/admission written before this reads back unchanged and no migration exists. No name in `data/investigations.ts` contains `#`. Three rules the code depends on: **keys are never renumbered** (removing the middle of base/#2/#3 leaves a gap that `nextImageKey` reuses — renumbering would rewrite keys inside saved prescriptions for a cosmetic tidy-up); **the same URL twice on one test+date is a no-op** (but the same report dropped on a *different* test tags it there too — one CT legitimately backs several findings, and removing it from one test must not remove it from the other); and **deleting a result drops that test's images only when it was the last value line for that test+date** (`deleteResult`), because with two lines for one test, deleting one to fix a typo must not discard the other line's evidence.
  - **Findings are ordered NEWEST DATE FIRST, on screen and on paper** (physician's report, 2026-09-21). They had never been ordered at all: a reported sheet printed 29 findings in the order they had been TYPED across a year of visits (`08/09/2026 → 19/06/2026 → 24/01/2025 → 08/09/2026 …`), which nobody can scan. `lib/investigationOrder.ts` owns it and BOTH surfaces use it — `sortFindingsByDate` for the printed list in `PrescriptionView`, `sortDateGroups` for the sidebar's date groups — so what the doctor checks on screen is the order that prints. Two rules: **inside one date the doctor's own order is kept** (Hb, then WBC, then PLT is how a blood count is read, so the sort is made stable explicitly rather than trusting the engine's), and an **undated finding sorts LAST**, because the top would give it a recency nobody claimed for it. `findingDateKey` compares `yyyymmdd` as an INTEGER, never a `Date` — the root CLAUDE.md's slashed-date trap, plus no local time or DST in something that is only ever compared. Pinned in `investigationOrder.test.ts`. Note the side effect: a mistyped future date now sorts to the TOP of the list instead of hiding in the middle.
  - **A test tagged with images but given no value renders in the app, never in print.** `InvestigationFindingsField` builds that row at render from the `[image attached]` markers — it is *not* stored in `investigation`, so `prescriptionDoc`/`PrescriptionView`/`investigationSummary` keep excluding it through their existing `[image attached]` filters with nothing new to maintain. A value-less test name on a printed prescription would read to a pharmacy as a missing result. Images hang off a test's **first** value line (one test+date is one row, one 📎, showing the count when >1); the lightbox walks them with ‹ › / ←→ and closes on Escape.
  - **⊘ Hide — findings the printed prescription must not carry (physician's decision, 2026-09-21).** Beside `✎ Edit`, an amber toggle whose tooltip is the physician's own wording, "Hide in Printed Prescription". It is a decision about the DOCUMENT, never about the record, and four rules carry it:
    - **Nothing leaves the screen.** A hidden finding stays in `Prescription.investigation` and stays in the sidebar **in full** — its bullet turns amber and a `⊘` is appended, nothing is removed, faded or truncated. The physician asked for this explicitly: a line the doctor cannot read is a line they cannot check before printing. Pinned in `InvestigationFindingsField.test.tsx`.
    - **A tick MEANS hidden.** No second "apply" press and no inverted tick-to-keep reading for a doctor to get wrong under time pressure. The header button is the master switch and the "select all" the physician asked for: nothing hidden → hide the field; anything hidden → bring it all back. It reads `⊘ Hidden (N)` and carries `aria-pressed` when anything is off.
    - **Only a line that could print is markable.** `[image attached]` markers, `dd/mm/yyyy:Report N` pool rows and the synthesised "report attached, no value yet" row get no tick, because a tick that changed nothing on paper would be a lie on screen. `lib/investigationHidden.ts` owns that test (`isPrintableFinding`) and now owns the print filter `PrescriptionView` used to carry inline; pinned in `investigationHidden.test.ts`.
    - **The mark is the exact stored string**, so it can never suppress a look-alike on another date, and it is **pruned when its finding is deleted** (`pruneHidden`, an effect in `MuqsitContext`) — a line re-typed at a later visit is a new clinical moment and must start visible.
    - **Where it lives:** `hiddenInvestigation` in the editor state, carried in the draft snapshot (`incompleteRx` JSON — additive, no migration) **and in the device mirror**, so the marks survive a reload, a patient switch and "Save to complete later", and a doctor hiding on the laptop does not print everything from the phone. `resetEditor` clears it, so a new visit starts with nothing hidden. The printed sheet and the snapshot image kept in the patient's record are built from the same HTML and can never disagree about what was handed over.
    - **Opt-in, OPD only.** `InvestigationFindingsField` renders the control only when given `onHidden`; `IpdDetailView` and the On-examination field pass nothing and are untouched.
    - **One button, two fields.** The toggle itself is `components/common/HideToggle.tsx`, shared with Drug history's whole-section hide, so the tooltip wording, the amber and the pressed state can never drift apart — a doctor who learns what the amber ⊘ means on one field reads it the same way on the other. It takes an optional `count` (Investigation shows `Hidden (N)`; a whole-section toggle has nothing to count and shows plain `Hidden`).
- **Drug history (per-patient `Patient.drugHistory`):** `dd/mm/yyyy: Drug — dose — food — duration`, notes `dd/mm/yyyy(note): …`, tapering `dd/mm/yyyy(cont): dose — food — duration`. Legacy `Current:`/`Past:` prefixes must keep parsing. Current-vs-Distant-past is **derived from the entry date vs `ptDate`** — never store the bucket.
  - **The ℞ pad mirrors into it live (`lib/rxDrugHistory.ts`, physician's decision 2026-09-07).** Every medicine written on today's ℞ is stamped with `ptDate` and merged into `drugHistory` by an effect in `MuqsitContext`, so it appears in **Current medications** as it is typed and reads as Distant past on the next visit. Before this the two lists never spoke and a patient prescribed Napa today showed "0 current" — the earlier `ptDate` fix corrected the split *boundary*, which could never put a medicine into a list nothing was feeding. Five rules hold it, each pinned in `rxDrugHistory.test.ts`:
    - **It withdraws only what it added.** `syncRxDrugHistory(stored, prevDerived, nextDerived)` removes an entry only if the mirror contributed it AND it has left the pad; `rxDerivedRef` (keyed by patient id, so another patient's pad is never consulted) is that memory. A medication the doctor typed into the modal by hand can never be deleted by editing the ℞. An empty `prevDerived` — a reload, a patient switch — is always safe: it withdraws nothing.
    - **It echoes and completes nothing.** A medicine with no dose yet is recorded with no dose. `MedicinePad`'s `1+0+1`/`After meal`/`Continue` defaults belong to "↻ Rx" (an explicit click), never here.
    - **`rowsFromRxItems` owns the head/taper/note classification**, including the pre-2026-08-17 blank-drug fallback for `isCont`. Re-deriving that test here is how a taper turns into a second unrelated medicine. ℞ **notes are skipped** — a note is not a medication, and the printed block renders every entry as a drug name.
    - **It never persists by itself.** `Patient.drugHistory` keeps the writers it already had (`savePrescription`, `saveDrugHistory`); the debounced editor auto-save carries it in `incompleteRx` so a parked or reloaded visit keeps it. It also waits for `drugHistoryHydratedRef` to match the loaded patient, so it never mirrors onto a not-yet-fetched (blank) list.
    - **The mirror is stripped back out of the printout** (`PrescriptionView#buildHtml`). Today's medicines are the ℞ table; printing them again under "Drug history" would state that the patient was already on them before this visit. Matched on the exact entry, so a prior medication hand-typed on the same date still prints.
  - **The modal is NOT EDITABLE — both tabs (physician's decision, same day, still in force).** Current medications is a list of what is on today's ℞ and is corrected on the ℞; Distant past is a record. `DrugHistoryField` renders no `MedicinePad`, no text input over a stored entry and no Done, and it writes nothing to `Patient.drugHistory` (no `saveDrugHistory`, no `onAdd` activity line, no `setItems` prop). This replaced the editable pad because the two surfaces disagreed: a correction typed over an ℞-mirrored row lost to the mirror on the next keystroke, which reads as "I can't write in here". **Do not re-add an editor without asking.**
  - **Selection replaced the per-row `↻ Rx` button (physician's decision, 2026-09-21).** Every medicine row on **both** tabs carries a checkbox; the footer holds **Select all** (which becomes **Clear**) and **Move to Rx (N)**, which appends the ticked blocks to today's ℞ pad and reports `N added · M already on ℞`. This is not a second writable surface over the history — nothing here edits an entry; the only write is into `rxItems`, exactly what `↻ Rx` did one row at a time. `lib/drugHistorySelect.ts` owns the rules and `drugHistorySelect.test.ts` pins them:
    - **It invents nothing.** `↻ Rx` filled a missing dose with `1+0+1`, food with `After meal` and duration with `Continue`; one press of Select all would have written those onto a dozen medicines. A blank cell now reaches the pad blank.
    - **A block is a head medicine plus the `(cont)` rows under it**, bounded by the next medicine, a note, or the end of its **date group** — so a taper can never attach to a drug from another visit. A `(cont)` row has no tick of its own and a skipped block takes its tapers with it: a taper must never reach the ℞ without the medicine it qualifies.
    - **No dedupe between ticked rows.** The same medicine ticked on two dates goes twice, in tick order — which dose is right is the doctor's judgement. Only a line **already on the pad** is skipped, matched on all four of drug/dose/instruction/duration (not the three `↻ Rx` compared: two lines differing only in the food instruction are two instructions).
    - **Notes and nameless rows are not selectable**, and selection is **per tab**, so the number on the button is always what is ticked in front of the doctor.
    - **The controls need `rx.medicines`**, the ℞ pad's own key — without it the modal renders exactly as it did before. This closes a hole `↻ Rx` had: the pad is locked in `RightColumn` for an assistant who holds only `rx.drugHistory`, and Drug history was writing medicines around that lock.
  - **Consequence the physician accepted:** there is still no way in the app to hand-record a medication the patient takes that is not on today's ℞, and no way to correct or remove an entry from an earlier visit. Prescribe it (with `Continue`) so the mirror records it — Move to Rx makes re-prescribing a past visit's list one press, but it cannot author an entry that was never prescribed. If that gap needs closing, it needs a deliberate add/remove affordance, not a re-editable pad.
  - **⊘ Hide keeps the WHOLE section off the printed sheet (physician's decision, 2026-09-21).** The toggle sits beside the `💊 N current · N past · view` badge and takes the entire Drug history block off the printed prescription (`PrescriptionView` passes `[]` for that block when `hideDrugHistory` is set). **No per-line ticks here, deliberately** — the medicines live behind the modal, so a tick on this row would mark something the doctor cannot see from it; the physician asked for all-or-nothing. The entries are untouched: the badge still counts them, the modal still lists them, and `Patient.drugHistory` is not written. State is the boolean `hideDrugHistory` in `MuqsitContext`, carried in the draft snapshot and the device mirror and cleared by `resetEditor`, exactly like `hiddenInvestigation`. Pinned in `DrugHistoryField.test.tsx`.
  - **The `Lock` in `LeftColumn` stays** even though nothing is editable: an assistant without `rx.drugHistory` could not reach this list before, and turning an editor into a view must not quietly hand them a patient's medications.
- **On-examination summary:** `{date, text}` objects (`lib/onExaminationSummary.ts`); investigation summary: `{date, category, test, value}` (`lib/investigationSummary.ts`). Both merge-on-save (deduped), grouped by date newest-first on the records page.
- **HM duration overrides:** `Patient.hmDrugDates` / `Patient.hmSymptomDates` are both `{ [name]: { sf, upto } }` (`DrugDateMap` in `lib/hmDates.ts`), values parsed by `cellToDate`. ## ⚠️ Patient sex: one word, one vocabulary, never a guess

The field is **"Sex"** on every screen (the header said "Gender" until 2026-07-27 — a different concept, and the second name is how the two screens drifted). It is `Patient.sex`, and every `<select>` offers the same four: `—` / Male / Female / Other.

**The OPD queue's `gender` column holds two spellings and always will:** `MuqsitContext` writes the full word from the editor (`gender: ptGender`), `PatientsView` used to write `"M"`/`"F"`. Read it through **`normaliseSex()` in `lib/sex.ts`**, never `=== "F"` — that test showed a woman stored as `"Female"` as **Male**, and opening her OPD row loaded that into the prescription editor.

**Patient Records has no Delete (physician's decision, 2026-08-30).** The patients list (`PatientsView`) used to carry a red Delete beside Open and Edit, guarded only by a `window.confirm` — one mis-click from erasing a person's entire record, in the row a doctor presses all day, with no Undo behind it. The button, its handler and its `useDeletePatient()` call are gone; **the hook and the owner-only `DELETE /patients/:id` route are deliberately left in place with no caller**, so bringing the affordance back (behind a real confirm affordance, not a browser dialog) stays a product decision rather than a re-implementation. Do not wire a delete into any other patient screen without asking.

**Never default a missing sex.** Five places used to: `patientForm.ts` pre-filled the form with `"Male"`, `PatientsView` listed and stored `M`, `OpdView` seeded the queue with `M` and pushed `"Male"` into the editor. Sex selects reference ranges (Hb, creatinine, eGFR) and sex-dependent dosing, so an unrecorded sex must stay unrecorded — `normaliseSex()` returns `""` for anything it does not recognise, and `sexLabel()` renders `—`.

**Sex and age are asked for where a patient is CREATED, and fillable where they are missing.** Both modals in `PatientMobileLookup.tsx` (new patient, and person-related-to) take them in the product owner's order — name, **Sex**, then **date of birth or age** (`IdentityFields`, 2026-08-15) — so a record no longer starts blank on the fields that decide dosing and reference ranges. All three stay **optional** there, because a guessed sex is worse than a missing one and an unknown age must not block opening the prescription. **Date of birth wins and the manual age is dropped from the payload:** `displayAge` prefers the DOB, so an age stored beside one is written and then never shown again — the box goes read-only and displays what the DOB computes to instead. The DOB box is a `DateField` on `YEAR_POLICY.past`, so `030398` is 1998, not 2098. In `PatientHeader`, Age and Sex are the one exception to the identity lock, and only to **fill a blank**: `fillable` is captured when the patient loads (not derived per render, or the box would re-lock mid-typing and a typo could never be corrected), and changing an already-recorded value still goes through Patient Settings — the same patient is seen by several practices. Age stays locked when a **DOB exists even if the box renders blank** (an unparseable or future DOB): `displayAge` prefers the DOB, so a manual age typed there would save and never appear. The header **persists these itself** (`useUpdatePatient`, 600 ms debounce) — nothing else writes them back, since `savePrescription` sends age/sex only when it is *creating* the patient — and a failed write is shown in red under the header rather than dropped.

Header and Patient Settings mirror each other live (`onGender` → `setPtInfo.sex`; the form's select → `setPtGender`; `loadPatient` sets both). If they ever disagree again, suspect a fabricated default, not the sync.

## ⚠️ Date parsing: `new Date("25/07/2026")` is Invalid Date

JavaScript reads a slash date as **month**/day/year, so the app's own `dd/mm/yyyy` blows up for any day past the 12th, and silently swaps day and month for days 1-12 (`03/06/2026` → 6 March). Anything that turns a stored date string into a `Date` must parse `dd/mm/yyyy` explicitly and reject rolled-over calendar dates (`31/02/2026` must not become 3 March) — `lib/hmDates.ts#cellToDate` and `HealthTrendsChart`'s `ddmmyyyyMs` both do, with calendar validation. Never reach for a bare `new Date(str)` on a stored date, and never let a failed parse fall back to an instant: `|| 0` yields 1 Jan 1970 and `yy || 0` yields 1900, and one such point stretches a shared axis across decades. Return `NaN`, drop what cannot be placed, and say how many were dropped.

### Ordering by a stored date: `ddmmyyyyMs` in `lib/dateInput.ts`, and nowhere else

**One copy, shared by every caller that orders clinical data by a `dd/mm/yyyy` string** (consolidated 2026-09-21 from EIGHT hand-written ones, each written slightly differently). Two screens disagreeing about which of two findings is newer is a real hazard here — the Health-trend chart, the investigation summary and download, the on-examination summary, the drug-history ranges, the Drug-history modal and the printed sheet's finding order all hang off this.

- **Milliseconds, not a `yyyymmdd` sort key**, because three callers do real time ARITHMETIC and not just comparison: `rxAlerts` divides a difference by `86_400_000` for days, `DrugHistoryField` compares against `Date.now()`, and `investigationSummary.filterByDate` is handed epoch bounds from a date picker. A sort key would silently break the "last 6 months" filter.
- **Lenient about the calendar**, matching the seven parsers it replaced: `31/06/2026` rolls over to 1 July. A malformed value returns **0**, which sorts older than every real clinical date, so junk lands at the end of a newest-first list rather than the top.
- **There is a second, STRICT contract beside it: `ddmmyyyyMsStrict`, which returns `NaN` and refuses a rolled-over date** (`31/02/2026`). Two callers need it because they must DROP a date they cannot read rather than place it: `HealthTrendsChart` plots on a shared time axis (when its parser returned 0 for junk, ONE malformed record stretched the axis across 126 years and squeezed every real value into a couple of pixels) and `rxAlerts` divides a difference by `86_400_000` to decide whether a drug is one the patient is CURRENTLY on (an epoch-zero stamp computes a ~56-year gap and silences an alert that should fire). **Pick by what a bad date must do: sort last → lenient; be dropped → strict.**
- Proven non-behaviour-changing when it landed: every well-formed `dd/mm/yyyy` gives a byte-identical result under all the old forms and the new ones; the malformed inputs that differ in VALUE all still sort oldest (lenient) or were already rejected (strict), so no screen moved. Nine hand-written copies became these two.

### Two-digit years: one helper, one policy per field

A 2-digit year is ambiguous, and both parsers used to resolve it by hard-coding `2000 + yy` — so `030398` meant 2098 and a birth year was silently a century out. That is now **`resolveTwoDigitYear(yy, futureAllowanceYears, now?)` in `lib/dateInput.ts`**, a sliding window anchored on the current year (so it survives 2099, unlike a baked-in `2000`): the forward reading wins unless it lands beyond the allowance, in which case the previous century does.

The allowance is the whole design — **there is no single correct rule for every field**, and a global "never future" would be the same bug pointing backwards (a 2027 follow-up typed as `030127` would become 1927). Pick from `YEAR_POLICY`:

| Policy | Allowance | Fields |
|---|---|---|
| `YEAR_POLICY.past` | 0 years | Date of birth, calculator dates (LMP, ultrasound). Also turns on a **day-level** check: a date later than today is refused outright, not shifted, because 1926-vs-2026 there is a genuine ambiguity and guessing would be a second silent century move. A real 1926 date is typed in full. |
| `YEAR_POLICY.clinical` | 5 years | Prescription header Date, findings, medicine pad, health-monitoring durations — a follow-up may legitimately be years out. `HealthTrendsChart`'s `FUTURE_LIMIT_YEARS` **is** this constant; don't redeclare it. |

`parseDateInput` returns `{ok:true,iso}` or `{ok:false,reason:"malformed"|"future"}` — the reason exists because the field has to say *which* rule was broken. `parseFlexibleDate` is the old `string | null` wrapper and still works for callers that don't need the reason.

Separate from the policy, `parseDateInput` also enforces a sanity range: **year 1900 to today + 100**. The policy only decides which century an *ambiguous* 2-digit year belongs to; the range catches a year that is not a date at all however it was typed. `03/03/998` used to parse as year 998 — an age of 1028 — and `prescriptionDoc` prints the date string verbatim onto the prescription.

**Age comes from `lib/age.ts#ageFromDob`, everywhere.** Do not recompute it as `elapsedMs / (365.25 * day)`: leap days accumulate, so that form read 29 for someone born 27 Jul 1996 on their 30th birthday while the header said 30. Age drives dosing — one function.

**All date entry goes through `components/common/DateField.tsx`.** Do not add a native `<input type="date">`: it cannot take the DDMMYY shorthand, which is how doctors actually type, and it bypasses the century policy. `DateField` reverts to the last valid value on a bad parse **and** says why underneath — reverting alone swallowed the reason. Enter commits, Escape abandons (the Escape flag is a **ref**, set before `blur()`, because `blur()` runs the commit synchronously — the same trap documented for the chart below).

**Pass `allowEmpty` on every optional date.** The native pickers this replaced all had a clear button; without the prop a doctor can never take a wrong date of birth back out, because `parseDateInput("")` is "malformed" and the box reverts to the value they were trying to drop. It is off by default so the prescription visit date keeps refusing to be emptied, as it always did.

Dates stored **before** this fix keep their wrong century; nothing is rewritten. `isImplausibleDate()` flags them where they render (DOB field, `PatientRecordsView` date headings, the chart's amber note) and the doctor decides. A bulk repair would be its own reviewed migration.

Server side, `dob` is validated in `patients/dto/patient.dto.ts` (`@IsISO8601({strict:true})` + `NotFutureDateConstraint`, 24h grace for UTC+6-vs-UTC clock skew). Its messages are doctor-facing — `apiFetch` joins `body.message` straight into the save banner, so write them for a clinician.

## Health monitoring tab (idsp)

`HealthMonitoringView.tsx` is now a thin shell: it derives the ranges and owns the override state/mutations, and `HealthTrendsChart.tsx` does the rendering plus editing. The old "Drug timeline" SVG and its per-drug SF/Upto panel were removed (2026-07) — one chart, one place to edit. The decorative "Export Patient's Data" card went with them: a button that looks actionable and does nothing is worse than no button on a clinical screen.

- **Window ≠ filter.** The time dropdown (3m / 6m / 1y / all, default **all**, not persisted) clamps only the LOWER bound. A track whose effective end is inside the window stays visible even if it started years earlier: the bar clips at the plot edge and gets a chevron. Never make a running medication disappear from a narrow window. The window start is pulled back off month-end overflow (31 Jul − 3 months is 30 Apr, not 1 May) so it can't be a day short.
- **Order matters:** apply the override first, then the window. Filtering on recorded dates first would hide a bar the doctor just moved into view.
- **Nothing vanishes quietly.** A ticked lab parameter with no in-window reading keeps a (short) lane saying so — a missing lane would read as "never measured". Entries whose stored date can't be read are dropped from the plot but counted, with an amber note saying so and that the record still holds them.
- Editing is owner-only (`canEdit` = not assistant mode **and** `patient.doctorId === activeWorkstationId ?? user.id`); the server enforces the same in `patients.controller.ts`. Every edit is written to the activity feed under `Health monitoring` — from the mutation's `onSuccess`, so a failed save is rolled back and announced rather than logged as if it landed. The patient id travels inside the mutation payload, not a closure: a blur fires as the lookup steals focus, which is exactly when `currentPatientId` is changing.
- **Bar durations are derived and understate.** A tapering `(cont)` drug-history line carries no drug name, so it does not extend that drug's range even though the drug was still being taken; a legacy `Current:` entry resolves to *today*. Both are why the override exists — don't "fix" them by guessing in `drugHistorySummary.ts`.
- **A typo is not an instruction.** Every rejection is stated in place and nothing is stored: an unreadable date, a date more than 5 years out (the DDMMYY century trap), and an end that falls before the start. `buildTrack` still clamps an inverted range so nothing draws backwards, but the clamp is the drawing-time backstop, never the whole answer — clamping silently would hand the doctor a one-day bar with no reason for it.
- Keyboard: Enter commits, Escape abandons. Escape must set a ref **before** blurring — `blur()` runs the commit synchronously, ahead of React flushing the reverted draft, so without it Escape saves the value it was meant to discard.
- Each reading carries its parsed `ms` from the memo that builds the series; the render path compares numbers. Typing in a duration box re-renders the whole chart, so don't move date parsing back into render.
- `hmSelectedDrugs` no longer has a UI writer (the chart's checkboxes are view state). It is still seeded on patient load and carried over by the family-link flow, so the column and its data stay.

## BAN / EN — phonetic Bangla typing (2026-09-23)

A `BAN | EN` switch at the end of the desktop tab row, beside Settings (`components/layout/BanglaTyping.tsx`). In BAN a doctor types the SOUND of a word on an ordinary keyboard — `khabar por` — and it becomes `খাবার পর` as they type, by **Avro Phonetic's own rule table** (vendored unmodified but for one `export` line at `src/vendor/avro-phonetic/`, **MPL-1.1** — keep the header and the licence file beside it). The engine is pure (`lib/banglaInput.ts`) and pinned in `banglaInput.test.ts`; the wiring in `BanglaTyping.test.tsx`.

- **Only the fields the physician named convert:** Chief complaints, Previous complaints (the note box), Note, Plan, Advice (`BANGLA_FIELDS`), and the OPD ℞ pad's dose / food / duration (`MedicinePad`'s `bangla` prop, passed by `RightColumn` only). A field opts in with `data-bangla="on"` (`BANGLA_ATTR`); `ExpandableField`'s `bangla` prop puts it on the popup box, the in-place edit boxes and the per-item note box. **Everything else types English in BAN mode and shows a notice** (once per visit to the field) — a medicine search, a date or a mobile number typed in Bangla would silently find nothing. The medicine NAME box is deliberately excluded: it is a search. Widening the list is a product decision.
- **⚕️ Numbers are never converted.** Only letters (plus Avro's `` ` `` and `^`) feed the phonetic buffer; digits, `+`, `/`, `-` pass through as typed. Avro itself turns digits Bangla and `.` into the dari — which would turn a half-tablet `0.5` into `০।৫`. So `1+0+1` and `0.5` stay exactly as keyed, and the dose shorthand (`101` → `1+0+1`) still works in BAN mode. `.` becomes `।` only straight after a Bangla letter.
- **Food/duration shorthand is English letters**, so in BAN mode `am` becomes `আম`, not "After meal" — the doctor sees it immediately. Units (`ml`) convert too. Switch to EN for either.
- The handler is ONE document-level **capture-phase** `keydown` listener: the conversion must land before a field's own Enter handler reads the value. It writes through the native value setter plus an `input` event, so each field's own `onChange` stays the source of truth — no field holds Bangla state of its own.
- The choice is remembered per signed-in user on this device (`mhs_kbd_lang:<userId>`), like the IPD view; logout returns to EN. Not mirrored across devices, and not offered in `MobileShell` (a phone's own keyboard already types Bangla).
- **Print:** `PRINT_FONT` in `prescriptionDoc.ts` is shared by the stylesheet and `measureRxText`. The Bangla faces (Nirmala UI, Noto Sans Bengali, Kohinoor Bangla, Vrinda) sit **after Arial**, so an English line resolves exactly as before — Nirmala UI has Latin glyphs too, and ahead of Arial it would have moved every English width on the sheet.

## Editor lifecycle (easy to break — know it)

- `resetEditor()` blanks everything and sets `ptDate` = today. `loadPatient(p)` = reset + header fields + restore `p.incompleteRx` **only when the patient belongs to the effective doctor** (`activeWsRef.current ?? authIdRef.current`). **Supervised patients (other doctor's) always open with a blank editor** — also enforced during draft hydration (the draft's patient is fetched and checked). Do not weaken either check.
- **Stale-draft `ptDate` advance (2026-09-07): `applyEditorSnapshot` automatically advances `ptDate` to today if the draft carries a date from a prior calendar day.** This is intentional, not a bug. A doctor who opened a patient yesterday, saved a draft, and resumes today is starting a NEW visit — the drug-history Current/Past split boundary must be today, not yesterday. The advance lives inside `applyEditorSnapshot` (not in its callers) so it covers both `loadPatient` and the page-reload path. `applyMirrorSnapshot` applies the same guard so secondary devices are not left with a stale visit date if they connect before the primary's first auto-save. Drug-drug alert checks use a 90-day recency window (`RECENT_DRUG_HISTORY_DAYS` in `lib/rxAlerts.ts`) so medications from the resumed draft (dated yesterday) still trigger contraindication warnings even after the advance. **Do not "fix" this away** — the original bug it solved was Current tab showing yesterday's medicines, and drug-drug alerts silently not firing for them.
- **The IPD clinical sheet is written WHOLESALE — build the payload with `mergeIpdClinical`.** `IpdDetailView` sends the entire `clinical` object and the server writes it verbatim, so a key this build does not list is not "left alone", it is DELETED from the patient's record with no error and nothing in the feed to notice. `lib/ipdClinical.ts` starts the payload from the admission's stored `clinical` and lays the known fields on top, which makes an unknown key mean "leave it alone". The server carries `analogueSheets` across the same seam (`ipd.service.ts#preserveAnalogueSheets`) because the client guard only protects clients that have it — an old tab still open on a ward PC, or a rollback of the build that introduced the key, would otherwise erase every photographed page on the next Save. Both halves are pinned (`ipdClinical.test.ts`, `ipd.service.spec.ts`).
- Auto-draft: the editor persists per-doctor via `prescription-draft`; fresh login (sessionStorage `mhs_fresh_login`) starts blank+gated, plain reload restores. "Save & print" completes the visit: merges findings/OE/drug-history into the patient's permanent JSON, clears `incompleteRx`, marks the OPD visit complete, and snapshots the printed sheet to the "All prescriptions(Image)" gallery (html2canvas in an off-screen iframe).
- **Save & print takes ONE save at a time (2026-08-23).** It had no in-flight guard, so a double-press ran the whole flow twice and recorded one consultation as **two `Prescription` rows** — measured in the running app: two clicks 120ms apart produced two rows 321ms apart. `handleSave` now holds a synchronous `savingRef` and returns immediately on a second click (no second window, no second row), with `runSave` carrying the old body; the `saving` state beside it only disables the two Save buttons and shows "Saving…", because doctors press twice when nothing appears to have happened. "Save to complete later" is disabled for the same window so a draft cannot interleave with the visit being completed. (Historic note: `runSave` was split out so everything up to its first `await` ran inside the click, which was what kept the old `window.open` out of the pop-up blocker. The sheet is in-app since 2026-08-26 and no longer needs the gesture; the split stays because the guard reads better with it.) `savePrescription` itself is still not re-entrant and does not serialise — the guard is the caller's, and any new caller owes the same.
- **A retried save files the record ONCE (2026-09-24).** `savePrescription` holds a pair of `Idempotency-Key`s in `rxSaveKeysRef` (one for `POST /patients`, one for `POST /prescriptions`), minted on the first attempt and **reused on every retry** until the save succeeds or `resetEditor` runs. A save that timed out on a clinic connection may have been stored; the retry sends the same key and the API replays its stored answer instead of filing the consultation twice. An edit between the two attempts is a different body under the same key — the API answers `422`, the keys are dropped, and the message tells the doctor an earlier attempt was already filed and to check the record. This is the network-failure half; the double-press half is `savingRef` above. Neither replaces the other. Never mint a fresh key per attempt, and never reuse one across two visits.
- **The client never auto-repeats a write, and reads wait out a short `Retry-After` once.** `apiFetch` sleeps and retries a GET once on 429/503 when `Retry-After ≤ 5 s`; `ApiError.retryAfterSec` carries it to React Query, whose `retry` (`Providers.tsx`) refuses every 4xx except 429. A 429's `message` is written for the doctor on the server side and shown verbatim.
- **`X-App-Build` → `NewBuildBanner`.** The first build id a tab sees is remembered; when a later response carries a different one, a calm bottom bar offers Reload and never reloads on its own — the doctor may be mid-consultation. This is the answer to "an old tab open across a deploy" (server/CLAUDE.md, Rule 2d).
- **"Ignore Warning" — entecavir only, pad only (2026-08-23).** The ℞ pad's warning panel carries an **Ignore Warning** button on the entecavir rule and no other. It is keyed on `RxAlert.drug` — the RULE's own drug label, not the brand in the ℞ line — so every entecavir brand behaves alike: Barcavir and Entaliv are the same medicine and must not offer the doctor two different affordances. The allowlist is `IGNORABLE_RULE_DRUGS` in `RxPadAlerts.tsx`; **widening it is a clinical decision, not a tidy-up.** Pressing it dismisses that warning's MESSAGE and nothing else — **the sign stays lit for as long as the medicine is on the pad** (physician's correction, 2026-09-24: it used to go out with the last ignored warning, leaving no way back to it), pressing the sign brings the dismissed warning back, and the advisory in "Notifications, Chats & Reports" stays up; the printed sheet was never carrying warnings anyway. `ignoredAlerts` therefore means "message dismissed"; `hideAlerts`/`showAlerts` beside `ignoreAlert` are what the sign uses. `ignoredAlerts` lives in `MuqsitContext` keyed by `RxAlert.id` (`${rule.drug}|${message}`, stable across renders), is **never persisted**, and is cleared both by `resetEditor` and on a successful save: the physician's rule is **this prescription only**, so the next visit puts the same decision in front of the doctor again.
- **Every warning a visit raised is written to the activity feed on save (2026-08-23).** `savePrescription` logs one `"Prescribing alert"` row per active alert, verbatim, **whether or not it was ignored** — dismissing hides the bubble, never the fact that the doctor was warned. That is the permanent half of the physician's ask; the advisory itself stays derived and vanishes with the editor. The message is logged **verbatim** because it is the physician's own rule text (`data/rxAlerts.ts`) — rewording it would put an unapproved sentence into a patient's permanent record. Fire-and-forget and wrapped, like the "Prescribing habits" line beside it: a save that already succeeded must never be undone by an audit line that failed. **Note `ActivityLog` rows do NOT cascade when a patient is deleted** (the FK is on `doctorId`), so they outlive the patient record.
- **One assembly of the alert input, now shared beyond React.** `buildRxAlertInput` (`lib/rxAlerts.ts`) is the single builder; `useRxAlertInput` is its hook wrapper and `savePrescription` calls it directly. The old rule stands and is the reason it was extracted rather than copied: two assemblies could drift and show a contraindication on one surface and not another, with no way to tell which was right.
- **The gallery snapshot is filed ONCE PER SHEET (2026-08-23).** "Save & print" still pictures the printed document into "All prescriptions(Image)", but only when that gallery does not already hold it: the physician's rule is that the first save files a copy, and after that only a save whose sheet actually differs does — clicking Save any number of times on a visit nothing was changed on must not file the same paper again. The comparison is the **HTML**, never the image bytes: two captures of one prescription are not equal as files (html2canvas rasterises a live DOM, and `compressImage` re-encodes lossily and only when that comes out smaller), while the HTML is the very string that feeds both the print window and the capture. It is deliberately **not** normalised — the header date, page size and margins are in it, and a sheet printed on another date or another page is another document (the physician asked for any change to count, not only a change of wording). `lib/rxSnapshot.ts` holds all of it: `rxSnapshotKey` (SHA-256 hex, or **null** when `crypto.subtle` is missing outside a secure context) and `createRxSnapshotGate`. Three rules there are safety, not tidiness: a **null key always files** (cannot tell ⇒ keep the copy), **no recorded key always files** (a first save, and every patient from before the column existed), and a failed capture **releases** the claim (`releaseRxSnapshot`) — a gate that believed a sheet was filed when nothing arrived would suppress every identical save after it, leaving a document the doctor handed over with no copy on file. The claim is taken *before* the capture precisely so a second click landing mid-capture is refused; Save & print has no in-flight guard of its own. The fingerprint lives in `Patient.lastRxImageKey` and is written in the SAME PATCH as `prescriptionImages`, so image and key can never disagree. Hand-added images ("Add more prescription image") never touch it.
- **The first snapshot for a NEW patient used to be dropped (fixed 2026-08-23).** `handleSave` captures the context at click time, and `savePrescription` creates the patient mid-flight — so the old `saveRxImages` closed over `currentPatientId === null`, skipped its PATCH, and the patient-load effect then replaced the local list with the server's. `MuqsitContext` now keeps `patientIdRef` (set synchronously right where the patient is created, not a render later) and `saveRxSnapshot` reads it and inserts functionally. Any new post-save write to the patient should use the ref for the same reason.
- **The prescription gallery is NEWEST FIRST (physician's decision, 2026-08-30).** A new sheet goes to the FRONT of "All prescriptions(Image)" — both the "Save & print" snapshot (`saveRxSnapshot`, `[url, ...prev]`) and a hand-added batch (`addRx`, `[...urls, ...rxImages]`, which keeps the order the files were picked in and lands as one block at the top). Two things this deliberately does NOT do: it never re-sorts what is already stored, and it never sorts on render. Uploads are named by UUID and carry no date, so **the array order is the only record of order** — a display-time sort would have nothing to sort by, and forcing one would silently overwrite a gallery the doctor dragged into a deliberate order (`ImageGallery` reorder is on for this gallery). **"All reports(image)" was left appending** at the doctor's request; if that ever changes, change `addReports` the same way.
- **"Save & print" also PRINTS (2026-08-15), IN THE APP (2026-08-26).** It shows the same `buildPrescriptionHtml` document "Preview PDF" shows; the two routes differ only in that this one persists the visit first. Until 2026-08-26 the sheet was a second browser window (`window.open`), which the physician called out as user-hostile: it needed a pop-up allowance to appear at all, it buried the editor behind it, and on a tablet it is a second app to dismiss. It is now `components/prescription/PrintSheetModal.tsx` — a full-screen in-app overlay owning the Print / Close buttons, opened from `sheet` state in `PrescriptionView`.
  - **The sheet still renders in an `<iframe>`, and that is not incidental.** The document carries its own `@page` size, print stylesheet, `<base href>` and font rules; loose in the app's document they would restyle the editor and print the wrong thing. `iframe.contentWindow.focus()` then `.print()` prints the framed document — the printed page is byte-identical to what the pop-up printed, only the frame around it changed. `buildPrescriptionHtml` no longer emits a `.toolbar` of its own (a `window.close()` button is meaningless in a frame), so the document is now the medical page and nothing else.
  - **Ctrl/Cmd+P is intercepted while the modal is open** and sent to the frame. Left alone it prints the APP page with the sheet squeezed in as one framed element — and a doctor's reflex is to press it.
  - Three things in `handleSave` are still load-bearing, not style: (1) the modal opens **immediately on the click** in a "Saving the prescription…" state, so the doctor never wonders whether the click registered; (2) **the save runs before anything that can throw** — building the sheet sits after it, in a `try`, so a render failure costs the printout and never the record; (3) a failed save **closes** the modal — a printable prescription must never be on screen for a visit the record does not have. The fill-in is `setSheet((prev) => prev.open ? … : prev)`, so a doctor who pressed Close mid-save does not get the sheet thrown back at them. The same HTML string feeds the on-screen sheet and the gallery snapshot, so the stored image is provably the document that was printed.
  - **Still a pop-up:** `InvestigationDownload.tsx` opens its report in a `window.open`. Same treatment when it comes up.
- **`saveDraftNow()` ("Save to complete later") is the doctor-initiated twin of that auto-save, and differs on purpose in two ways.** (1) It is **awaited**, and the editor is cleared *only after the server confirms*; on failure it says `Draft NOT saved: …` and touches nothing, so every value survives. Never reorder that — clearing on a fire-and-forget write is worse than the silent auto-save, because the doctor walks away believing the visit is safe. (2) It sets the OPD `rxStatus: "incomplete"` flag **unconditionally**, not gated on `rxFlaggedRef`: `flushEditorDraft` never sets it, so a patient typed-into and left inside the 1200 ms debounce used to end up with stored work and no Incomplete badge to find it by. Supervised patients take the same branch as the auto-save — own draft only, never the owner's `incompleteRx` or OPD queue. The button is gated on a loaded patient + `hasRxContent` only; `hasRxContent` ignores follow-up, `invImages` and `oeData`, so an image-only visit leaves it disabled — the tooltip has to say why rather than sitting there dead.
- The 3.docx mobile gate: nothing is writable until a patient is picked via the mobile lookup (`PatientMobileLookup`, exact 11-digit match, family-tree info rows, "SUPERVISED" badge for other-practice matches).

## UI conventions

- **The ℞ pad sets the brand NAME in bold, and nothing else** (`MedicinePad`, medicine column, 2026-08-23) — the same emphasis the printed sheet carries, via the same `splitDrugLabel`. An `<input>` can only hold ONE font weight, so the line the doctor is **not** typing in is covered by a read-only `aria-hidden` copy that can, with the input's own text turned transparent underneath. On focus the overlay goes and the real input shows through unchanged: bold glyphs are wider than regular, and an input places its caret using its own single weight, so leaving the overlay up while typing would drift the caret away from the letters. Two traps if you touch it: the overlay's content must stay ONE flex item (a bare text node beside the `<b>` becomes its own flex item and its outer spaces collapse — `Tablet.Napa500 mg`), and `white-space: pre` is what keeps the spacing identical to the input's. The input itself is untouched — still mounted, still holding `drugRefs[idx]`, so focus, Enter-navigation, the autocomplete dropdown and device mirroring all behave as before. Verified in the browser: programmatic `focus()` drops the overlay, editing re-splits the label on blur. Free-typed note lines are not medicines and are never split or bolded. **Known cosmetic limit:** a click lands the caret by the input's regular-weight metrics while the eye aims at the wider bold name, so clicking into a name can be under half a character off.
- **℞ lines can be moved (physician's request, 2026-09-23), OPD pad only** (`MedicinePad`'s opt-in `reorderable`, passed by `RightColumn`). Two ways: **drag the line by its serial number** (it turns into a ⠿ grip on hover), or **▲ / ▼ beside the ✕ while ✎ Edit is on**. `lib/rxRowMove.ts` owns the rules and `rxRowMove.test.ts` + `MedicinePad.reorder.test.tsx` pin them: **what moves is a BLOCK** — a medicine with its `>>>` tapering lines — because a taper row has no drug name and moved alone it would hand its dose to whichever medicine it landed under; a note is a block of one;
  - **The drag is LIVE, pointer events, one step per neighbour middle crossed — never native drag-and-drop.** The first version (same day) used HTML5 DnD and chose the landing spot at release from React state set during `dragover`; a quick release read the previous render's value and fell back to "before", so dragging UP went one step too far and DOWN one step short (measured in the browser: 2 steps and 0 steps for a one-row move). Now nothing is decided at release: `dragStep` swaps the block with one neighbour each time the pointer passes that neighbour's middle, the same rule both ways. **Row heights are measured once at pickup and carried through the swaps**, and positions are computed from them — reading positions off the DOM meant waiting for a render between steps, and a fast three-row sweep (which a browser reports as ~2 pointer events) moved two places. The move/up/cancel handlers are attached on every row of an opted-in pad, not just grips: rows are keyed by position, so after a swap the element holding pointer capture can be a taper row. `touch-action: none` on the grip makes it work on a tablet too.
  - Rules, continued: the trailing "start typing" row never moves and nothing lands below it; and no field of any row is edited, only the order. The printed serial numbers and the alert-to-line indices simply follow the new order (both are derived from `rows` every render). The IPD sheet, the Drug-history pad and the template editor do not opt in.

- **⚕️ Image formats: ONE table, `lib/imageFormats.ts`, and it reads the BYTES (2026-09-20).** Accepted: **JPEG, PNG, GIF, BMP, WEBP, AVIF, HEIC/HEIF, TIFF**. Before this there were **five disagreeing allowlists** — `compressImage`, the IPD panel's `ACCEPTED_TYPES`, the server's multer MIME filter, the server's magic-byte check, and `PatientChat.isImageUrl` — so a format could pass one gate and fail another and *which screen broke depended on which list it hit*: the ward's order-sheet panel refused GIF and BMP that the server stored, and the chat rendered SVG (never storable) but not AVIF (stored every day). Rules:
  - **Detection is by content, not by name or MIME.** `detectImageKind` sniffs the first 32 bytes; the filename and `file.type` are only a fallback for when the read fails. A file's declared MIME is the least reliable signal here — iPhone photos routinely arrive as `application/octet-stream`, and HEIC bytes under a `.jpg` name are ordinary.
  - **HEIC and TIFF are CONVERTED to JPEG before upload** (`lib/decodeImage.ts`, `heic2any` + `utif`, both behind a dynamic `import()` so an ordinary JPEG upload downloads neither — verified in a production build: heic2any's 1.3 MB is its own chunk and First Load JS is unchanged). No mainstream desktop browser can draw either, so storing them as they arrived filed a document nobody could open.
  - **A failed conversion THROWS; it never falls back to the original.** That asymmetry is the safety rule: for a format the browser can read, handing the original back is fine (it still renders); for one it cannot, the fallback is an unviewable file in a patient's record. `compressImage`'s old blanket `catch { return file }` is exactly how that happened. The error names the file and tells the doctor what to do.
  - **`IMAGE_ACCEPT` is the `accept` attribute everywhere — `image/*` alone is NOT enough.** Windows has no MIME registration for `.heic` or `.tif` on a stock install, so a picker filtered on `image/*` greys the doctor's own scan out and they cannot select it at all.
  - **SVG is refused and must stay refused** — it carries script and stored images render inline. That is a security boundary, not a gap. `imageUrlIsRenderable` deliberately excludes it.

Napa 500 mg` the eye should land on `Napa`, not on the dosage form or the strength. `.rx-drug` is weight 400 and `splitDrugLabel` (`lib/rxShorthand.ts`, the inverse of `fmtMedicine`) wraps the name in a `<b>`. The form rule is the structural one from `server/src/rx-habits/normalise.ts#splitForm` (up to the first `.`, no digit in the head, ≤4 words, qualifier included); the strength is the trailing run starting at the first digit-leading token or a trailing `N/A`, and never the first token after the form, so `Tablet. 5-FU 500 mg` keeps its name. A label whose name cannot be read stays wholly bold — no emphasis at all would be worse. **`layoutRxColumns` still measures the label as if all of it were bold**: an over-estimate of a couple of percent that can only hand the column more room than it needs, deliberately kept over a slightly larger print.
  - **Whether the sheet can print `nowrap` is read off the width each column GOT, not the share it asked for.** Widths are whole px and their total can never exceed the row; a `nowrap` cell sitting a fraction wider than its own column is sub-pixel, invisible in a browser, and exactly the kind of thing that prints as a collision — pinned by "never lets a cell overflow its own column, at any sheet width" in `prescriptionDoc.test.ts`. There is no legibility floor any more (`FLOOR_PX` is gone): nothing is ever truncated or pushed past the printable width, and nothing is ever printed under 14px.
  - `rxTableInnerPx` derives the row from the doctor's own page-size settings (in/cm), so a custom page or wider margins stays safe. Verified in a real browser, not just in theory; `prescriptionDoc.test.ts` pins those numbers (`A4_INNER` is the **data** columns — **458px** since 2026-08-26, was 428px — with `RX_NO_PX` making up the rest). **`RX_NO_PX` (32) is sized for a TWO-digit serial**, because a 10-medicine prescription is ordinary and `10.` measures 19.5px at 14px DM Sans; at the old 22px the number dropped onto a second line beside the medicine it numbers. **Known trade-off — SUPERSEDED 2026-09-12, kept for the reasoning:** at a fixed 14px a crowded sheet used to buy its size with wrapped drug names — a label past ~34 characters alongside food values took a second line, and the note here said no sane page split fixed that (fitting a 38-character label on one line needs the clinical column down to ~150px). A page split did fix it: moving the dose **under the medicine name** freed its whole column for the names, and the reported 8-medicine sheet now prints every label on one line at 14px (see the dose bullet above). Two levers bought the width back on 2026-08-26, both product decisions the physician made rather than tweaks: the `.body` grid went `0.8fr / 0.5px / 1.6fr` → **`0.7fr / 0.5px / 1.7fr`** (clinical column 239px → 209px) and `CELL_PAD_PX` went 12 → **8** (`td { padding: 7px 4px }`). Measured then: **dropping the type size is NOT a third lever** — at 13px and even 12px the same two labels still wrap, because the non-drug columns are capped at a share of the row that does not shrink with the font. Keep 14px. The document carries a `<base href>` because it is written into an `about:blank` window (and an off-screen iframe for the gallery snapshot), where a relative image `src` has no reliable base — that is why the footer logo loads at all. Each `.sheet` is a single-cell `<table class="pagegrid">` whose `<tfoot>` holds the MHS / By EXHORT brand bar: a `tfoot` repeats on every printed page **and** has its height reserved in the flow, so it can never overprint a medicine row. Do not "simplify" it to `position: fixed` — that sits lower but is free to overlay content on a full page. The scoped `.pagegrid > tbody|tfoot > tr > td` resets exist so the global `table`/`td` rules (which belong to the Rx table) do not leak into the wrapper; keep the child combinators. The OPD "privacy copy" masks identity and drops clinical content — keep new sections out of it unless the patient needs them. Drug history prints **names only**, deduped.
  - **The patient header's right half — Date / Mobile / Address — starts PAST the middle of the sheet** (physician's ask, 2026-09-12). `.pt` was two equal halves (`1fr 1fr`); it is now `minmax(0, 0.56fr) minmax(0, 0.44fr)`, so the date column begins at ~57.5% of the printable width instead of ~51.7%. Three things hold it, all pinned in `prescriptionDoc.test.ts`:
    - **The offset is a SHARE, never a px indent.** That is the whole of "keep it aligned for every paper size": measured across A4, Letter, Legal, A5, a 5.8in page and the reported 7.5×15in, the date starts at **57.5–58.2%** on every one (it moved 42px on A4 and 27px on A5 — proportionally, which is the point). A fixed px nudge would be a hair on A4 and a third of the column on a narrow sheet. To move it further, raise `PT_LEFT_FR` and lower `PT_RIGHT_FR` by the same amount; they are one pair of constants beside `PT_GAP_PX`, which now also writes the CSS `gap` so the stylesheet and the width bound cannot drift apart.
    - **`minmax(0, …)` for the same reason `.body` carries it.** A bare `fr` track floors at its content's min width, so one long name or address would shove the date column to wherever it happened to fit — a different offset on every patient. With `minmax(0, …)` the halves hold their share whatever they carry and long values wrap inside their own column.
    - **The two halves are measured SEPARATELY in `wordHeadroom`.** They are no longer equal, and the narrower right half carries the **Address** — the longest value on that side. The old single `headAvail` (`content / 2 - PT_GAP_PX / 2`) would now over-state the room the address has and let the fill factor grow the type until an address word broke. **Known trade-off the physician should see in use:** a long address has ~12% less width than before and will wrap to a second line sooner. It wraps — it is never truncated — and the fill bound stops it being split mid-word.
- Mirror devices: editor state broadcasts over SSE (`DeviceMirror`); new editor state that should sync must be added to `mirrorSnapshot`/`applyMirrorSnapshot` in MuqsitContext.

## Responsive layout

The app adapts to the real device viewport, not just the manual preview toggle:

- `Muqsit.tsx` derives `effectiveView` from `matchMedia("(max-width: 767px)")` — phones always render `MobileShell`, regardless of the manual Desktop/Mobile toggle (hidden on real phones). It does **not** mutate the shared `view` state, since `view` is part of the mirrored snapshot (`mirrorSnapshot`/`applyMirrorSnapshot` in MuqsitContext) — device mirroring must stay unaffected.
- `MobileShell` takes a `preview` prop: `true` (desktop's manual "Mobile" toggle) renders the classic 375px bezel + fake status-bar mock; `false` (a real phone) fills the viewport (`100dvh`, no bezel). Both render the same children — the mock is presentation-only.
- `DesktopShell` now also serves **tablets** (≥768px, capped at 1440 via `.app-root`), not just desktop — "not mobile" no longer means "plenty of width." Check ~768px as well as ~375px when adding or changing a view.
- Styling is inline-only, so there's no ambient CSS breakpoint. Working patterns for a new row/grid/modal: `flexWrap:"wrap"` on any row that can overflow; `gridTemplateColumns:"repeat(auto-fit,minmax(Npx,1fr))"` instead of a fixed column count; `width:"min(Npx,92vw)"` + overlay `padding` for fixed-width modals. For a genuine breakpoint collapse (e.g. a 2-column layout that must become 1-column below some width — inline `style` can't express a media query), use a scoped `<style>` block with a class name, e.g. `.rxEditorGrid` in `PrescriptionView.tsx` (≤860px), `.invModal` in `InvestigationPopup.tsx` (≤820px), `.msgGrid` in `MessageView.tsx` (≤680px).
- A `mobile` prop being absent on a tab/view doesn't mean it's exempt from this — it usually means nobody's added responsive handling yet. Check how sibling views in the same tab group handle it before assuming a new fixed-width row is fine.

## Verification checklist for client changes

0. `npm test` (vitest) — the clinical pure functions are pinned there; a red test is a clinical regression, not a formatting nit.
1. `npx tsc --noEmit` clean (Next build also lints — unused vars fail the prod build).
2. Exercise the flow at :3000; for editor changes also check reload-restore and a supervised patient stays blank.
3. Touching print/downloads → open Preview PDF and check fit; touching summaries → check records page grouping + Undo.
4. "Jest worker encountered N child process exceptions" from `next dev` = corrupted cache → stop, `Remove-Item -Recurse -Force client\.next`, restart. Not your change.
5. **Never run `npm run build` while `next dev` is running.** They share `client/.next`; the build dies with `EPERM ... .next\trace` and leaves the dev server serving a half-written tree (`Server Error: Cannot find module './vendor-chunks/next.js'`). Stop dev → delete `.next` → build → restart. This *is* your change, and it looks exactly like the corrupted-cache symptom above.
6. Verify persistence through the API, not the rendered UI — from the page, `fetch('http://localhost:4000/api/...', { credentials: 'include' })`. A value can be stored and still unreadable by the app (see the date-parsing section); only comparing the two catches it.
