## At a glance

- A visit's work is never kept in a place that a reload, a patient switch or the next sign-in empties: each kind of visit is parked in a place of its practice's own, and "printed" rides the draft.
- "Printed" is not a latch: it means "what the visit says is what was sent", compared both ways by a short fingerprint (`visitSig.ts`), only for the visit's own patient; `resetEditor` clears it.
- A background fetch never believes its own answer is the whole record: the patient fetch MERGES `drugHistory` against live state (`MuqsitContext.tsx`) — nothing dropped, nothing duplicated.
- A late answer never decides it is still wanted by asking about ONE of the ways the editor can move on: every writer that replaces the editor moves `editorEpochRef`, not `resetEditor` alone.
- Storage string formats persisted in drafts, prescriptions and patient JSON columns: changing them silently orphans existing data; extend the parsers, don't break them.
- `loadPatient` restores the parked visit of the PRACTICE that read it; a supervised patient never opens with the owner's draft (only a `workstationId` of this practice); do not weaken either check.
- A reload restores the patient's record fields (`ptInfo`, watched) from the fetched record, not the draft; anything else `loadPatient` takes from the record belongs on the reload path too.
- ⚕️ Header photo is the on-screen patient's: `resetEditor` blanks `ptInfo` and `watchPatient`; `loadPatientById` opens only the LAST patient asked, if not reset since; `<img>` keyed by patient+URL.
- `applyEditorSnapshot` advances a stale draft's `ptDate` to today on purpose (mirror too, except a printed visit); do not "fix" this away; alerts use the 90-day `RECENT_DRUG_HISTORY_DAYS` window.
- How it works — Editor auto-draft persists per doctor (`prescription-draft`); fresh login starts blank+gated; Save & print merges into the record, clears `incompleteRx`, marks OPD complete, snapshots the sheet.
- ⚕️ Printed = Save & print done AND the visit still says what was SENT (`fingerprint`, never text); "+ Add medicine" lines are appended by the server via one queue; `DEFECT-RELOAD-MIDNIGHT` (+8 more)
- ⚕️ A reload's draft is dropped if the editor moved while it was on its way: every applied snapshot moves `editorEpochRef`; state arriving then is marked arrived (`mirrorAppliedRef`) (+1 more)
- Any post-save write to a patient created mid-save must read `patientIdRef` (set synchronously at creation), as `saveRxSnapshot` does, and insert functionally.
- "Save to complete later" (`saveDraftNow`) is awaited and clears the editor only after the server confirms — never reorder; sets OPD `rxStatus: "incomplete"` unconditionally (+2 more)
- Merely opening a patient is not prescription work: `hasRxContent` counts drug history only when it differs from the stored baseline (`drugHistoryBaselineRef`).
- Mirror devices: editor state that should sync must be added to `mirrorSnapshot` / `applyMirrorSnapshot` in MuqsitContext (broadcast over SSE, `DeviceMirror`)
- A practice never reads another's draft: a Patient read for a possibly-supervising caller goes through `PatientsService.get` / `findByMobile` or `forViewer` (+N more: drug-history, on-exam).
- `mirror` fans out editor snapshots in-memory; every SSE route must set `X-Accel-Buffering: no` or nginx buffers the stream in prod.

# The rules, in full

## Patterns We Do Not Use

_From the root `CLAUDE.md`._

- We do not keep a visit's work in a place that a reload, a patient switch or the next sign-in empties. The owner's practice parked its unprinted visit on the patient (`incompleteRx`), and three kinds of work were kept nowhere else but the one-slot editor draft: a supervising doctor's visit (a reload threw it away ON PURPOSE, to keep the owner's draft out), a change made after Save & print, and the fact that the visit WAS printed — after a reload a printed visit read as unprinted and was put back to "Incomplete", ready to be filed twice (physician, 19/10/2026: "If every saved data is gone after reloads that is not perfect for this app"). Each kind of visit is parked in a place of its practice's own, and "printed" is state that rides the draft like the rest. A guard that keeps one practice's draft from another is written so that the other practice keeps its OWN, not so that it keeps nothing (`client/CLAUDE.md`, Editor lifecycle; `server/CLAUDE.md`, Rule 2).

- We do not keep a state as a latch that only one kind of event sets, and we do not carry a visit's own words where a fingerprint will do. "Printed" first meant "Save & print happened and nothing changed since": an IPD admission's findings on loan, the records' "+ Add" box or a letter typed and deleted dropped it for good, and the printed patient went back to "Incomplete", to be printed and filed again (review, 19/10/2026). It means "what the visit says is what was sent" now, compared both ways. And "what was sent" was first kept as the visit's TEXT, riding the draft, the parked copy and the device mirror, while nothing but opening a patient cleared it — a fresh visit ("New Prescription") then parked the printed patient's diagnosis and medicines in the next patient's record (third review, before release). What rides with the visit is a short fingerprint (`fingerprint` in `client/src/lib/visitSig.ts`), only for the visit's own patient, and `resetEditor` clears it with the rest. A comparison needs a fingerprint; only what a person reads is text.

- We do not let a background fetch believe its own answer is the whole record. The patient fetch beside the ℞ → Drug history mirror (`MuqsitContext.tsx`) used to set `drugHistory` to `p.drugHistory` outright on arrival — safe for every writer that existed when it was written, because each was either that same fetch's own last answer or the ℞ mirror, which re-derives itself from `rxItems` the moment it is disturbed. "+ Add medicine" (2026-10-14) is neither, and so is a line an `incompleteRx` draft has just restored on reload: this fetch is slow enough, on a brand-new or just-edited patient, to land after either — a Distant-past addition on a just-created patient was gone on the very next reload (caught in the browser pass, before release). The handler now merges — the record's own order first, whatever is live beyond it appended, nothing dropped, nothing duplicated once the record catches up — rather than overwriting. A background fetch that refreshes part of the editor is written to merge against live state from the day it is added, not patched once a second writer finds the gap.
- We do not let a late answer decide it is still wanted by asking about ONE of the ways the state it would replace can move on. A reload's draft was dropped when the editor had been RESET while it was on its way (`editorEpochRef`, moved by `resetEditor` alone); another device's state arriving through the mirror replaces the editor too, and the draft was laid over it — the patient that device had just brought replaced by the draft's, under that patient's open Investigation box and half-typed result, and the stale draft written back into its patient's parked visit (independent review, 19/10/2026; closed 20/10/2026). Every writer that replaces the editor moves the ref now, and what arrives in that moment is "arrived" for the auto-save as it is afterwards (`client/CLAUDE.md`, Editor lifecycle).

## Editor lifecycle (easy to break — know it)

_From `client/CLAUDE.md`._

- `resetEditor()` blanks everything and sets `ptDate` = today. `loadPatient(p)` = reset + header fields + restore `p.incompleteRx` — **the parked visit of the PRACTICE that read the patient** (19/10/2026): the owner's practice gets the patient's own column; a supervising practice gets its own (`SupervisedDraft` on the server, written by `patientsApi.setSupervisedDraft`), never the owner's. **A supervised patient never opens with the owner's draft:** the server gives a supervising practice no other, and the client opens one for a supervised patient only when the snapshot's `workstationId` is this practice — an owner's draft carries the owner's. Until 19/10/2026 a supervised patient always opened blank, and a supervisor's unprinted work lived only in their one-slot editor draft: a reload threw it away on purpose, another patient opened overwrote it, the next sign-in cleared it. A reload now restores a supervising doctor's own draft when it says it was written in this practice; one that does not say (from before that field) reloads the patient fresh, as before. Do not weaken either check. Pinned in `MuqsitContext.test.tsx` ("a supervising doctor's unprinted visit is kept") and `server/test/supervised-draft.int-spec.ts`.
- **A reload restores the patient's RECORD fields from the record, not the draft (fixed 2026-09-25).** The per-doctor `prescription-draft` holds the editor, never `ptInfo` — so the reload path used to set `currentPatientId` and leave `ptInfo` at its blank initial value: the header PHOTO showed 👤 and Patient Settings a blank form for a patient whose photo was on file (the physician's report). The reload path already fetched the patient to check supervision; it now reuses that record to `setPtInfo(patientToPtInfo(record))` and `setWatchPatient(record.watched)`, exactly as `loadPatient` does. Anything else `loadPatient` takes from the record belongs there too. Verified in the browser by reload; there is no provider-level test harness to pin it.
- **⚕️ The header photo always belongs to the patient on screen (physician, 02/11/2026: "Prscrptn chng krle image dekhay jay previous image er").** The photo is `ptInfo.picture`, and `resetEditor` blanked every field but `ptInfo` ("set by the caller right after" — and "New Prescription", a practice switch, a fresh login and Save to complete later never did): the last patient's face stood over an empty header, and a new patient saved from that screen was CREATED with that photo (`savePrescription`'s `pictureUrl: ptInfo.picture`) and the last patient's watch flag (`carryOver.watched`). Now: `resetEditor` sets `ptInfo` back to blank and `watchPatient` to false (a caller that opens a patient sets both after it, as `loadPatient` does); `loadPatientById` opens its answer only if it is still the LAST patient asked for (`loadSeqRef`) and the editor has not been reset or replaced meanwhile (`editorEpochRef`) — a slow fetch for A landing after B, or after New Prescription, put A back on the screen; a mirrored state of ANOTHER patient that carries no `ptInfo` (an older build) blanks it; and the header's `<img>` is keyed by patient and URL, because a browser keeps drawing an image's OLD picture until its new `src` has downloaded. Pinned in `context/MuqsitContext.photo.test.tsx` (red before the fix). The `<img>` key is not unit-tested (jsdom loads no images) — it was not checked on a slow network.
- **Stale-draft `ptDate` advance (2026-09-07): `applyEditorSnapshot` automatically advances `ptDate` to today if the draft carries a date from a prior calendar day.** This is intentional, not a bug. A doctor who opened a patient yesterday, saved a draft, and resumes today is starting a NEW visit — the drug-history Current/Past split boundary must be today, not yesterday. The advance lives inside `applyEditorSnapshot` (not in its callers) so it covers both `loadPatient` and the page-reload path. `applyMirrorSnapshot` applies the same guard so secondary devices are not left with a stale visit date if they connect before the primary's first auto-save — except for a visit already printed (Save & print), whose date is kept (the ℞ mirror bullet under Drug history says why). Drug-drug alert checks use a 90-day recency window (`RECENT_DRUG_HISTORY_DAYS` in `lib/rxAlerts.ts`) so medications from the resumed draft (dated yesterday) still trigger contraindication warnings even after the advance. **Do not "fix" this away** — the original bug it solved was Current tab showing yesterday's medicines, and drug-drug alerts silently not firing for them.

- Auto-draft: the editor persists per-doctor via `prescription-draft`; fresh login (sessionStorage `mhs_fresh_login`) starts blank+gated, plain reload restores. "Save & print" completes the visit: merges findings/OE/drug-history into the patient's permanent JSON, clears `incompleteRx` (a supervising practice: its own parked visit), marks the OPD visit complete, and snapshots the printed sheet to the "All prescriptions(Image)" gallery (html2canvas in an off-screen iframe).
  - **⚕️ Nothing typed is lost on a reload or a patient switch (physician, 19/10/2026: "If every saved data is gone after reloads that is not perfect for this app").** Two holes besides the supervised one above. (1) **The printed mark rides the draft** (`rxCompletedPid` in the snapshot, read back by the reload's `restore`): it lived in memory only, so a visit printed and then reloaded read as unprinted — parked again and put back to "Incomplete" in OPD, ready to be filed a second time. (2) **A change made after Save & print is unprinted work again.** It was kept only in the one-slot editor draft, so another patient opened and the correction the doctor believed made was gone, the record holding the version printed before it. **Printed means: Save & print happened for this patient AND what the visit says is still what was SENT** (`printedNow`; `rxPrintedSig` is `visitSig` at the press — a short fingerprint of what the visit says (`fingerprint`, `lib/visitSig.ts`), never its text: kept as text, a fresh visit parked the printed patient's diagnosis and medicines in the next patient's record (third review) — and it rides the draft and the device mirror for the visit's own patient only; `resetEditor` clears it). While it differs, the visit is parked like any unprinted visit (`incompleteRx`, or a supervising practice's own) and OPD shows "Incomplete"; put back as it was sent, it is printed again — the parked copy taken back and OPD told "complete". A parked copy is taken back when one is known to exist (`changedSincePrintRef`): this device parked the change, the patient's parked copy was opened, or the changed visit arrived from another device or was restored by a reload. A change typed and taken back inside the auto-save's wait parked nothing, and takes nothing back. The day of the print rides with the mark (`rxPrintedOn`, not the visit's own date, which a back-dated visit does not share — review of 409be0b; a device on an older build sends none, and its mark is taken as today's). A parked copy carries the mark only on that day: opened on a later day it is that day's visit, unprinted. A reload keeps the mark across midnight, so the editor's own last visit, printed, is not parked again the next morning — and once it is changed it is that day's visit, unprinted (`parkVisit`). **Known gap, `DEFECT-RELOAD-MIDNIGHT` (20/10/2026; `it.fails` in `MuqsitContext.test.tsx`, "a printed visit reloaded after midnight"):** the reload's `applyEditorSnapshot` still moves the printed visit's date to today, as `applyMirrorSnapshot` did before 6e4cbbf. The printed ℞ line stays in Drug history (`withoutBlocksIn`), and the mirror writes a second copy under today's date. Current medications then shows the visit on the pad as its own "previous visit", and a reprint (Save & print again) sends that copy. It is not what was printed, so even inside the server's 30-minute repeat window it files a second prescription, and the record keeps the medicine under both dates. A same-day reload is not affected. Which fix to take (keep a printed visit's date on reload, as the mirror does, or open the patient as a new visit on a later day) is the physician's decision. Related, from the same tests: a printed visit kept across midnight by the MIRROR, then changed, keeps yesterday's date while it counts as today's unprinted visit; the correction replaces yesterday's printed line in Drug history, and the new sheet is dated yesterday. Another patient arriving through the device mirror is a new visit as after `resetEditor` — the records' "+ Add" box ends and closes with it (reviews of dfdd1c4 and 409be0b: it put the last patient's findings into the next one's visit, and left open, what was typed next went into the new patient's). An OPD status write sends an age only as a whole number of years (`wholeAge`): a typed `1.5` was refused, and the write with it. "+ New patient" and a walk-in's Prescribe park the last patient's latest edits first, as opening a patient does. What the visit says (`visitSig`, with keys sorted, `lib/visitSig.ts` — a draft read back from the database gives an object's keys in another order): the clinical lists, ℞ lines, advice and follow-up the prescription stores, the pad's held lines, and what is hidden from the sheet, read off the visit's OWN findings (`visitInvestigation`: not an IPD admission's on loan, not what the records' "+ Add" box writes for the patient's history — the parked copy reads them so too). NOT the drug history (the record's own list lands in it after a print; it prints unless hidden, and is printed from the record) and not the header (name, age, weight, date print but are not part of the stored prescription). **A line added to Drug history after the print ("+ Add medicine") is written to the patient's record at once instead** (`addDrugHistoryEntries`): parking does not carry it, and it lived in the editor's draft until the next patient was opened (third review). **The server appends them** (`POST /patients/:id/drug-history`, `patientsApi.appendDrugHistory`) to whatever the record holds; the request carries the new lines alone. Every drug-history write of the editor goes through one queue (`dhWritesRef`), so a line added right after Save & print is appended after the print's own list lands, not before it. One press's lines (a medicine and its tapers) are one request. The answer — the record as it now stands — is taken as the record's list only by that patient's own editor, and into its list when the patient was opened again while the line was on its way (the next Save & print wrote the list without it: review of b8e4a3e). No answer is not taken for "not added" — the answer may be what was lost, and a line added again was stored twice: the record is read, and a line found on it is kept. A line NOT on it is said in a box, taken back off the screen as a run (never line by line: a failed medicine's taper took another medicine's identical taper), and out of any Save & print list taken before that was known — queued already, or with its prescription still on its way (`dhWithdrawnRef`, against the count at the press: the box said "not added", and the re-print wrote it; reviews of b8e4a3e and 340d901). Not covered — the older last-writer-wins of a whole-list write: a later Save & print from an editor whose list was read before the line landed writes its list without it — another user of the practice, a device without the mirror or whose mirror connection dropped, or another device printing in the same moment. Any new post-save write to the patient should use the ref for the same reason.

- **`saveDraftNow()` ("Save to complete later") is the doctor-initiated twin of that auto-save, and differs on purpose in two ways.** (1) It is **awaited**, and the editor is cleared *only after the server confirms*; on failure it says so in a box the doctor has to read — "The visit was not saved for later." with the reason in their words (`whyNotSaved`, below) and "Everything you wrote is still here." — and touches nothing, so every value survives. Never reorder that — clearing on a fire-and-forget write is worse than the silent auto-save, because the doctor walks away believing the visit is safe. (2) It sets the OPD `rxStatus: "incomplete"` flag **unconditionally**, not gated on `rxFlaggedRef`: `flushEditorDraft` never sets it, so a patient typed-into and left inside the 1200 ms debounce used to end up with stored work and no Incomplete badge to find it by. A supervised patient's visit is parked in the supervising practice's own place (`patientsApi.setSupervisedDraft`, awaited the same way: a failure keeps the editor) — never the owner's `incompleteRx` or OPD queue. The button is gated on a loaded patient + `hasRxContent` only; `hasRxContent` ignores follow-up, `invImages` and `oeData`, so an image-only visit leaves it disabled — the tooltip has to say why rather than sitting there dead.

## ⚠️ Rule 2 — the patient access model (do not widen casually)

_From `server/CLAUDE.md`._

**A supervisor reads the patient row without the owner's draft (2026-09-29) — and with their OWN (19/10/2026).** `incompleteRx` is the in-progress prescription of the practice that READS it. The owner's practice gets the patient's column; a read by another practice goes through `patients.service.ts#withOwnDraft` (`get`, `findByMobile`), which gives that practice its own `SupervisedDraft` row's data, or `null` — never the owner's (`forViewer` blanks it first) — and the `patient` included on `GET /prescriptions/:id` gives it `null` (`forViewer`). A supervising practice writes its row only through `PUT /patients/:id/supervised-draft` (the owner's practice gets 400; an assistant needs any `rx.*` key, as for `incompleteRx`); `PATCH /patients/:id` still refuses a supervisor wholesale. Keyed by the practice (the workstation doctor), so its assistants share it as the owner's practice shares `incompleteRx`. Before, a supervising doctor's unprinted visit was kept nowhere but their one-slot editor draft — a reload, another patient opened or the next sign-in lost it. `manual-supervised-draft.sql` must be applied BEFORE the release that reads it is deployed. A new read path that returns a Patient row to a possibly-supervising caller must go through `PatientsService.get` / `findByMobile` (`withOwnDraft` is private to it) or use `forViewer`. `SupervisedDraft` missing (the SQL not applied) costs only the parked visit: the read logs an error and answers it as none, never a 500 for the patient (review). Removing a supervising doctor (`patient-chat` `removeSupervisor`) removes their parked visit for that patient after the link, on its own: when the parked visit cannot be removed — the table missing, or any other failure — the link still goes and a warning is logged, and the parked visit stays behind (third review: in one transaction, a missing table failed the removal and the supervisor kept their access). Not covered: the owner's patient DELETE removes a supervising practice's parked visit with the patient (it refuses only over another doctor's PRESCRIPTIONS); and `apiFetch` re-reads the `X-Workstation` header when it retries after a 401, so a parked visit written exactly as the user switches practice can land under the new one — rare, for a user assisting two practices that both supervise the patient. Pinned in `test/supervised-draft.int-spec.ts`. **Lines added to a patient's drug history after Save & print go through `POST /patients/:id/drug-history`** (19/10/2026), which appends them under the row's lock to whatever the record holds: the first version sent the client's whole list, and one device's copy, behind the record, erased what another device had just printed (independent review, before release). Owner's practice only, like `PATCH`; a stored value that is not a list is refused (409), never replaced. Pinned in `test/drug-history-append.int-spec.ts`. **One stored medicine's start date and duration are put right through `PATCH /patients/:id/drug-history`** (07/11/2026, physician's sheet: "Edit option add hobe … date duration edit kora jabe"; `patients.service.ts#replaceDrugHistoryBlock`, `patients/drug-history-edit.ts`): the only route that rewrites a stored drug-history line, so it is as narrow as the request. The body is the BLOCK as stored (`replace`: a medicine line and the `(cont)` lines under it) and its replacement (`replacement`). The block is found in the record **by its exact text, under the row's lock** (`ROW_LOCK_TX`) — never at a position a client read, since the list a client holds is one device's copy — and when it is no longer there (another device changed it) the answer is 409 and nothing is written; of two identical blocks the first is changed. `blockEditProblem` accepts only the SAME number of lines, each the same kind (the medicine first, tapers under it; a note, a legacy `Current:`/`Past:` line and a taper with no medicine are refused — 400), every cell but the last (the duration) character for character the same — name, dose and food cannot change through it — one real `dd/mm/yyyy` date (1900–2200) on every line, and no cell separator or line break in a duration. Same reach as the append: the owner's practice only (403 for a supervising doctor, 404 for a patient the practice cannot reach), an assistant needs any `rx.*` key; a stored value that is not a list is 409, never replaced. It writes no activity line itself — the client does, once the answer is in. `client/src/lib/drugCourse.ts#rewriteCourse` is the client's copy of the same rules (`drug-history-edit.spec.ts` ⇄ `drugCourse.test.ts`: edit one, edit both). Pinned in `drug-history-edit.spec.ts` and `test/drug-history-edit.int-spec.ts` (an edit and an append sent together are both kept; run against a real Postgres). **A saved visit's On-examination findings go through `POST /patients/:id/on-examination`** (31/10/2026; `patients.service.ts#appendOnExamination`, `patients/on-examination.ts`): appended under the row's lock to `Patient.onExaminationSummary`, an entry with the same date and text not written twice, nothing stored changed. **Wider than the drug-history append on purpose: a SUPERVISING practice may append** (the physician's rule: the history is the patient's, seen by all their doctors) — append only, and `by` is the name of `@WorkstationDoctorId()`'s user read here, never a client value.
