## At a glance

- On examination is APPENDED by the server; `by` is stamped by the server, never sent or made up; Records page history sections are read-only, each line as written (+3 more)
- Patient Records has no Delete; hook and owner-only `DELETE /patients/:id` are left with no caller on purpose; do not wire a delete into any other patient screen without asking.
- "All prescriptions(Image)" is newest first (new sheets to the FRONT); never re-sort stored order or sort on render — array order is the only record; "All reports(image)" still appends.
- Records page: sections start collapsed; Total summary shows lines AS STORED, premium only (locked, not hidden); Imaging DICOM premium-only; DICOM viewer in-app (`dwv`), never a third party (+2 more)
- Gallery ⤓ Download PDF: one A4 page per FULL image in on-screen order, never cropped, footer `n / N`; all or nothing — if any image fails no file is downloaded (+1 more)
- `Patient.imageThumbs` is a display-only side map riding `...rest`, not in `RX_LIFECYCLE`; it must never widen the `pt.info` key and only travels in the same PATCH as its gallery.
- `Patient.lastRxImageKey` (SHA-256 of the newest auto snapshot) rides `...rest`, not `RX_LIFECYCLE`; only travels with `prescriptionImages` and must not widen `pt.info`; NULL = nothing filed yet.
- `PatientFile`: add/remove owner practice only (assistant needs `pt.info`); DICOM is premium-only, checked on the server; removal SOFT; DICOM bytes checked for `DICM` at byte 128 (+N more).

# The rules, in full

## Storage string protocols (the data model hiding in strings)

_From `client/CLAUDE.md`._

- **On-examination summary:** `{date, text, by?}` objects (`lib/onExaminationSummary.ts`); investigation summary: `{date, category, test, value}` (`lib/investigationSummary.ts`). Investigation merges on save (deduped, whole-list PATCH); **On examination is APPENDED by the server since 31/10/2026** (`patientsApi.appendOnExamination` in `savePrescription`, physician's sheets 28/10 item 7 and 31/10 item 3): it is the PATIENT'S shared history — every doctor who can reach the patient sees it, and a supervising doctor's findings are added too — and `by` (the practice doctor's name) is stamped by the server, never sent from here. An entry from before that has no `by`, and none is ever made up (`oeAuthorLabel` → null). The answer is taken as the list only while that patient is still loaded (`patientIdRef`); it needs no stored list in hand, so it is sent even before the record has loaded. The records page shows one card per date AND author (`groupOeForRecords`, `28/10/2026 by Dr. X`), read-only — no Edit, no delete (physician: "Edit option thakbe na"; the context's `saveOnExaminationSummary` went with it) — and a Download (`lib/recordsDoc.ts`, a printed page on the `rawColours` SKIP list). **⊘ Hide for On examination** (`hideOnExamination`, whole section, `HideToggle` through `InvestigationFindingsField`'s `sectionHidden` / `onSectionHidden`): starts OFF — the section prints, as it always did — rides the draft, `incompleteRx` and the device mirror, `resetEditor` sets it back to false, and `PrescriptionView` prints `printableOnExamination(lines, hidden)`. It joins `visitSig` ONLY when set, so a visit printed before it existed keeps its fingerprint and does not go back to "Incomplete" after the update. **After the Investigation summary** the page lists Drug history, Patient's input (an honest empty section — no such record exists), Disease and surgical history, Chief complaints history and Diagnosis history (`RecordsHistorySections.tsx`, `lib/patientRecords.ts`): read-only, each line as written; drug history in BLOCKS (a taper never leaves its medicine) by date; disease/surgical from the shared OE history's `Disease Hx:` / `Surgical Hx:` lines (written by the sidebar's History block since 02/11/2026, by the OE popup before), each once at the visit it was first recorded, an entry removed there (`removedAt`) left out here and on its OE card; complaints and diagnoses per saved prescription of this practice (the `["prescriptions", pid]` query, its error drawn before any data). Pinned in `onExaminationSummary.test.ts`, `patientRecords.test.ts`, `RecordsHistorySections.test.tsx`, `InvestigationFindingsField.test.tsx`, `MuqsitContext.test.tsx`.

## ⚠️ Patient sex: one word, one vocabulary, never a guess

_From `client/CLAUDE.md`._

**Patient Records has no Delete (physician's decision, 2026-08-30).** The patients list (`PatientsView`) used to carry a red Delete beside Open and Edit, guarded only by a `window.confirm` — one mis-click from erasing a person's entire record, in the row a doctor presses all day, with no Undo behind it. The button, its handler and its `useDeletePatient()` call are gone; **the hook and the owner-only `DELETE /patients/:id` route are deliberately left in place with no caller**, so bringing the affordance back (behind a real confirm affordance, not a browser dialog) stays a product decision rather than a re-implementation. Do not wire a delete into any other patient screen without asking.

## Editor lifecycle (easy to break — know it)

_From `client/CLAUDE.md`._

- **The prescription gallery is NEWEST FIRST (physician's decision, 2026-08-30).** A new sheet goes to the FRONT of "All prescriptions(Image)" — both the "Save & print" snapshot (`saveRxSnapshot`, `[url, ...prev]`) and a hand-added batch (`addRx`, `[...urls, ...rxImages]`, which keeps the order the files were picked in and lands as one block at the top). Two things this deliberately does NOT do: it never re-sorts what is already stored, and it never sorts on render. Uploads are named by UUID and carry no date, so **the array order is the only record of order** — a display-time sort would have nothing to sort by, and forcing one would silently overwrite a gallery the doctor dragged into a deliberate order (`ImageGallery` reorder is on for this gallery). **"All reports(image)" was left appending** at the doctor's request; if that ever changes, change `addReports` the same way.

## UI conventions

_From `client/CLAUDE.md`._

**Records page: collapsible sections + Total summary (physician's sheet 07/11/2026).** Every section of `PatientRecordsView` starts COLLAPSED; the arrow (`components/common/CollapseToggle.tsx`, `useOpenSections`) opens/closes only the BODY — the section's buttons stay. `ImageGallery` takes opt-in `collapsed` / `onToggleCollapsed`, `DrugHistoryTable` `collapsed`, `SectionHeader` `open` / `onToggle`; `RecordsHistorySections` with no `sec` prop draws everything open (how its tests see it). **Total summary of this patient** (`TotalSummary.tsx`, pure `lib/totalSummary.ts`): every dated record in one list, by date, and inside a date in the sheet's order (Chief complaints, Surgical and disease history, On examination, Patient's input, Investigations, Final diagnosis, Drug history); lines are shown AS STORED (the drug line keeps its brand — the sheet's own example writes `Tab. Napa 500mg`, unlike the Drug history table's generic display). Filter chips + Newest/Oldest first (default newest first, like the other sections; the sheet's example was oldest first — open question). **Premium only** (`accountTier === "premium"`): others see it blurred with every button disabled — a locked view, not a hidden one; client-side only. Download = the sheet's modal (date window + what to include) → `buildRecordsDoc`, same printable page as the other Downloads. **Imaging DICOM is premium-only (09/11/2026): other accounts see it blurred, nothing pressable and nothing fetched; the server refuses them too.** **Permissions and Imaging DICOM** (same sheet), after Diagnosis history: `PermissionsSection.tsx` is an `ImageGallery` of the `PatientFile` rows of kind `permission` (Download PDF, "Add new permissions"; the sheet's *Templates form to download* waits for the physician's templates — no button until they exist) and `DicomSection.tsx` lists `dicom` rows as an icon + name + date, with an upload box (file, name, date), Edit to remove (asks first; soft on the server) and a press to open `DicomViewer.tsx`. Both go through `patientFilesApi` (`lib/api.ts`; `apiFetch` leaves the Content-Type to the browser for a `FormData` body) and are offered only where `usePatientFileAccess()` says the practice owns the patient (and `pt.info` for an assistant). **The viewer is in-app, with `dwv`** (open source): a scan is fetched from OUR server and never sent to a third party (RadiAnt, the sheet's example, is a Windows desktop program). It is loaded with `next/dynamic` `ssr:false` and `import("dwv")` only when a scan is opened; `next.config.mjs` aliases `dwv$` to its browser build because its package `exports` sends the server compile to a Node file that cannot be bundled. Tools: window/level, zoom/pan, scroll through slices, reset, full screen; an unreadable file says so and offers the download. Checked in a real browser with a hand-made uncompressed 16-bit 3-frame file; **compressed transfer syntaxes (JPEG, JPEG 2000, RLE) use `dwv`'s workers and were NOT tried.** Pinned in `PatientFiles.test.tsx`. Pinned in `totalSummary.test.ts`, `PatientRecordsView.collapse.test.tsx`.

**⤓ Download PDF on both patient galleries (physician's request, 2026-09-24).** `ImageGallery`'s opt-in `pdf` prop, passed by `PatientRecordsView` for "All prescriptions(Image)" and "All reports(image)" only. One A4 page per image, **in the order on screen** (the URL list is frozen at the click), the WHOLE image fitted and never cropped, page turned for a landscape image, and a footer `All reports  -  n / N` on every page so a missing or shuffled page is visible. Built in the browser with no new dependency: `lib/galleryPdf.ts` fetches each FULL image (never the thumbnail) one at a time, draws it through a canvas (so EXIF rotation matches what the gallery shows) and re-encodes JPEG; `lib/imagesPdf.ts` is a pure ~100-line PDF writer embedding those JPEGs with `/DCTDecode`. **All or nothing:** if any image fails, no file is downloaded and the red line names the image's position — a PDF silently missing page 7 would be a record with an invisible hole. The fetch uses `cache: "no-store"` because a copy cached by an `<img>` tag was fetched without CORS. Needs the server's CORS-before-static order (`server/src/main.ts`). Reading, so not gated by `canEdit`. Pinned in `imagesPdf.test.ts` and `ImageGallery.pdf.test.tsx`; a PDF built from real uploads was checked with pypdf (strict).

## ⚠️ Rule 2 — the patient access model (do not widen casually)

_From `server/CLAUDE.md`._

`Patient.imageThumbs` (2026-09-07, `manual-patient-image-thumbs.sql`) is a nullable `Json` side map, `{ [fullImageUrl]: thumbUrl }`, holding 400px copies for the two document galleries. Display-only and additive: it carries no clinical content, nothing was migrated, and a gallery URL absent from it falls back to the full image — which is how every image stored before it reads. It rides the generic `...rest` passthrough in `patients.service.ts#update` and is deliberately **not** in the controller's `RX_LIFECYCLE` set, so an assistant needs exactly the `pt.info` key `prescriptionImages` already requires; it must never widen that, and it only ever travels in the same PATCH as the gallery it describes. The arrays themselves were left alone on purpose — see `client/CLAUDE.md` for why the thumbnails are a side map rather than a richer array.

`Patient.lastRxImageKey` (2026-08-23, `manual-patient-last-rx-image-key.sql`) is a plain `TEXT?` that carries no clinical content: the SHA-256 of the printed sheet behind the newest AUTO snapshot in `prescriptionImages`, so the client can tell a re-save of an unchanged visit from a real edit and stop filing the same paper into the gallery on every click (see `client/CLAUDE.md`). It rides the generic `...rest` passthrough in `patients.service.ts#update` — no service branch of its own — and it is deliberately **not** in `RX_LIFECYCLE`: it only ever travels in the same PATCH as `prescriptionImages`, which already requires `pt.info` for an assistant, so it must not widen that. NULL means "nothing filed yet" and the client always takes a snapshot, which is why the column needed no backfill.

## `patient-files` — Permissions and Imaging DICOM (07/11/2026)

_From `server/CLAUDE.md`._

`PatientFile` (`manual-patient-files.sql` — **apply it before the release that reads it**; until then the routes answer 500 and a boot check logs one ERROR). One row per file of kind `permission` (a scanned image) or `dicom`, under `/patients/:id/files`. Rule 2 column: **read** anyone who reaches the patient (`PatientsService.get`); **add / remove** the patient's OWNER practice only (`patient.doctorId === workstation doctor`; a supervising doctor gets 403, as `PATCH /patients/:id` refuses them for the galleries), and an assistant needs `pt.info`. **Imaging DICOM is PREMIUM-only (physician, 09/11/2026): the signed-in user's `accountTier === "premium"` is checked on the server for the dicom list, upload and removal (403 otherwise); Permissions are not gated.** Removal is SOFT (`removedAt`/`removedById`) and the bytes stay in `/uploads` — no hard delete. The row says who added it (`addedByName`) and each add/remove writes one activity line (section `Permissions` / `Imaging DICOM`). **DICOM bytes:** multer streams to `uploads/tmp-<uuid>` (limit 300 MB, `DICOM_MAX_BYTES`), `UploadService.storeDicomFromDisk` checks `DICM` at byte 128 (extension and Content-Type prove nothing), refuses a local `PUBLIC_URL` like every upload, renames to `<uuid>.dcm`, and the temp file is meant to be always gone afterwards — it sits where `/uploads` is served (**known DEFECT, 2026-11-18: not when the DTO refuses the request first** — a `fileDate` not in dd/mm/yyyy shape, or a name over 120 characters: multer has already written the file and the handler's `finally` never runs, so any signed-in user can leave up to 300 MB per try; a prototype fix, an interceptor listed after `FileInterceptor` that unlinks `req.file.path` on any error, was checked in a copy and not applied; see `audit/records-page.md`). A file with no preamble is refused with a message, not guessed at. The name and the owner check run BEFORE the file is kept. Pinned in `patient-files.service.spec.ts` and `upload.service.spec.ts`, and — over HTTP, real multipart, the test database and the disk — in `server/test/patient-files.int-spec.ts` (2026-11-18: who reads and who writes, the premium gate on the list, upload and removal, soft removal with the bytes kept, `DICM` by bytes, one activity line per add or removal, and that a request refused by the premium, owner, key, DICOM-name or format checks leaves no file on disk). It was run green on Node 22 in a copy (the whole integration suite, 472 tests; the spec alone, 27 tests, after its last edit), and each of its "must not" tests was checked by breaking a copy of the code (22 breaks, each caught — one of them by the unit spec instead); it has NOT run in CI yet, its first CI run is the release that carries it. **It pins one known DEFECT with `it.failing`** (the temp file above). Not covered: the 300 MB `DICOM_MAX_BYTES` limit; whose tier the premium gate reads when an assistant works under a doctor; and a request refused after its file was kept (an unreal date, a permission with no usable name) — all in `audit/records-page.md`.
