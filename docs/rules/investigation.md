# The rules, in full

## Patterns We Do Not Use

_From the root `CLAUDE.md`._

- We do not put a space, or anything else, inside a number in order to show it — and we do not guess from a string which comma is which. The Investigation popup spaced every comma of a stored result, so `ANC 1,500` was shown `ANC 1, 500`; the first fix kept together whatever LOOKED like a grouped number, and showed ETT's `METs:10` and a report beginning `150 bpm` as `METs:10,150 bpm`. The catalog says which values can hold several parts — only a test that has, or ever had, several boxes — and everything else is shown as stored (`client/src/lib/findingParts.ts`). A display rule that is right for one test's values and wrong for another's is not a fix, and neither is one that is tested beside the line that applies it: the panel's own line was wrong twice with the rule's tests green.

- We do not convert, or record, a number we have not read whole. `parseFloat` reads the start of a text and stops: in a two-unit result box a viral load typed `1,20,000` copies/mL was converted from its first group and recorded — and printed — as `0.18IU/mL` (in production until the release that carried this). Only a whole, plain number is converted; anything else is recorded exactly as typed, in the unit of the box it was typed in (`client/src/lib/twoUnitValue.ts`). Never `parseFloat` / `parseInt` on something a doctor typed without first checking that ALL of it is the number.

- We do not let a key that MOVES also CHOOSE. In the Investigation calendar the arrows move along the days and only Enter, Space or a click chooses one, because choosing a day files whatever is half typed under the old date.

## ⚕️ Clinical-accuracy rules specific to the client

_From `client/CLAUDE.md`._

- **Investigation catalog (`src/data/investigations.ts`):** the master test list (`INV_CATS`: `{cat, tests:[{name, fields}]}`, some via the `txt([...])` name-only helper). Test names must stay **unique across categories** (duplicates were purged deliberately); field units are clinical facts — verify before editing.

- **A label that names a measurement or carries a unit is never forced to capitals** (`textTransform: "uppercase"`). Until 2026-10-05 the Investigation popup, the calculators and On-examination did exactly that: `g/dL` read `G/DL`, `fL` read `FL`, `pg` read `PG`, and a calculator's `WBC (×10³/µL)` read `ΜL` — `µ` uppercases to a Greek capital Mu that looks like `M`. The catalog and the calculator definitions are written in the right case; show them as written (`testLbl` in `InvestigationPopup`, `lbl` in `CalcRenderer`, `oeLbl` in `OePopup`). Capitals are fine for labels with no unit (Patient name, Mobile). **A test's NAME is not forced to capitals either (settled 2026-10-12):** in the catalog the case is part of the name — `eGFR` in capitals is `EGFR`, a different test; `HbA1c` becomes `HBA1C`, `HBsAg` becomes `HBSAG`. A name that should be in capitals is written that way in `data/investigations.ts`, one name on purpose. The unit beside a test name is `n[500]` at 10.5px, not the old `n[300]` at 9px (1.5:1 contrast).

## Storage string protocols (the data model hiding in strings)

_From `client/CLAUDE.md`._

- **Investigation finding:** `dd/mm/yyyy:TestName:value` (parse via `lib/investigationSummary.ts`).
  - **⚕️ A two-unit result box records a conversion only of a number it has read WHOLE (`lib/twoUnitValue.ts`, 2026-10-12).** Forty boxes take their value in either of two units (creatinine, bilirubin, glucose, the lipid profile, HBV DNA…): type in one and the other is filled in with the catalog's own factor, and the doctor's preferred unit is the one recorded. The conversion used `parseFloat`, which reads the START of a text and stops — so a viral load typed with its groups, `1,20,000` copies/mL, was converted from `1` and recorded, shown and printed as `HBV DNA: 0.18IU/mL`; `120,000` became `21.48IU/mL`, `1.2 x 10^5` became `0.21`, and with umol/L preferred a creatinine typed `1,2` in the mg/dL box became `88.42umol/L` (found in the fifth review; **in production until the release that carried this**). Two rules now, and neither reads a comma — what a typed comma means is still the physician's to say: only a whole, plain number is converted (`12`, `12.5`, `.5`, and `12.` on its way to 12.5); and what is not converted is recorded **exactly as it was typed, in the unit of the box it was typed in** (`HBV DNA:1,20,000C/mL`) — never a conversion of part of it, and never nothing (typed in the box of the unit that is NOT preferred, a value like `>2000` was not recorded at all: Enter filed nothing, and Done closed the popup without it). The box of the unit that is NOT preferred counts only when something is typed in it: for one review round a stray space there was recorded as a result with a unit and no value (`S. Creatinine: umol/L`), where before the rule nothing was (sixth review, before release; the preferred box, like a box with one unit, still records a space as it always did — `FUNCTIONAL-AUDIT.md`). A plain number behaves exactly as before. **Values recorded before the fix cannot be told from real ones:** a wrong one is a perfectly formed number in the other unit. Never call `parseFloat` / `parseInt` on what a doctor typed without checking that all of it is the number. Pinned in `twoUnitValue.test.ts` and, through the real popup from the keys to the stored finding, `InvestigationPopup.units.test.tsx`.
  - **⚕️ The parts of a value are joined by a comma with no space, and only the popup's "Added results" panel adds one to read them by** (`lib/findingParts.ts`). Until 2026-10-12 it spaced EVERY comma, so a calculator's `ANC 1,500 cells/µL` was shown as `ANC 1, 500 cells/µL` and a platelet count typed `1,50,000` as `1, 50, 000` — one number entered, three shown. **The string cannot say which comma is which, so the CATALOG does** (`readFinding` / `isOneValue`): only a test that HAS several boxes can hold several parts. Everything else is one value and is shown exactly as stored — a calculator's sentence, a test with ONE box, and the doctor's own free text, with a colon in it or not (`Platelet: 1,50,000` is read as a test called "Platelet"; no test is called that, and a name the catalog does not have has never been a several-box test). A test with several boxes keeps the space after every comma, as it always has. **Do not replace that with a pattern for "what looks like a grouped number".** The first fix did, and fused two parts into one number: ETT's `METs:10` beside a report beginning `150 bpm` read `METs:10,150 bpm` (caught in the second review, before release). Three things keep it honest, all in `findingParts.test.ts`: over every multi-box test in the catalog no two parts are ever shown without a space between them; **every test that has EVER had several boxes is listed there by name** and may never be read as one value — GCS and Child-Pugh had boxes until 2026-06-17 and are calculators now, so their older values (`Eye:4/4,Verbal:5/5`) stay set apart through `ONCE_SEVERAL_BOXES`, and a several-box test that is ever renamed, removed or collapsed has to be added to it (the test fails until it is); and `InvestigationPopup.results.test.tsx` renders the real popup and reads the panel, because twice the defect was on the panel's own line and the rule's tests passed with that line broken (third review). What is left is pinned as `DEFECT-INV-GROUPED` (`it.fails`, twice): in a test with several boxes a number typed with its groups (`WBC:12,000`) is still set apart at them in that panel, and so is free text that begins with such a test's exact name and a colon (`CBC: TC 12,000`) — closing it needs the parts stored apart, not a cleverer reading of the string. Display only; the stored string, the sidebar and the printed sheet never had the rule. **The Health-trend chart reads the same stored string and has the same blind spot — see `numericInvSeries.ts` under "Health monitoring tab".** Report-pool images: `dd/mm/yyyy:Report N:[image attached]`; test-tagged images use key `dd/mm/yyyy:TestName` in `invImages` + a `…:[image attached]` entry. `[image attached]` / `Report N` rows are filtered out of print and summaries.
  - **A test's report image is only ever attached by an explicit act of the doctor** — dragging the open report onto that test's "Add report image", or picking a file there (`tagTestImage`/`untagImageKey` in `InvestigationPopup.tsx`). Until 2026-08-16 a `resolveTestImage()` fallback stamped *whatever report was open in the left viewer* onto every result the doctor typed (`addInvResult`, `addInvNormal`, and the auto-save on date-change/close), so a finding's 📎 opened a report it was never taken from — one report silently became the evidence for every line on the visit. Do not reintroduce a "helpful" default: on a clinical record an attachment has to mean the doctor attached it, and a wrong one is worse than none. Each attached image is a thumbnail + ✕ on the test card so the doctor can see what landed and take any one back off. **Findings saved before that date keep their auto-stamped images** — nothing was rewritten; the ✕ is the doctor-driven cleanup.
  - **A test holds MANY images (2026-08-16), keyed `dd/mm/yyyy:TestName`, `…#2`, `…#3`** — helpers in `lib/investigationImages.ts` (`testImageKeys`, `nextImageKey`, `hasImageUrl`, `hasValueLine`), unit-tested in `investigationImages.test.ts`. The first image keeps the historic unsuffixed key, so every draft/prescription/admission written before this reads back unchanged and no migration exists. No name in `data/investigations.ts` contains `#`. Three rules the code depends on: **keys are never renumbered** (removing the middle of base/#2/#3 leaves a gap that `nextImageKey` reuses — renumbering would rewrite keys inside saved prescriptions for a cosmetic tidy-up); **the same URL twice on one test+date is a no-op** (but the same report dropped on a *different* test tags it there too — one CT legitimately backs several findings, and removing it from one test must not remove it from the other); and **deleting a result drops that test's images only when it was the last value line for that test+date** (`deleteResult`), because with two lines for one test, deleting one to fix a typo must not discard the other line's evidence.
  - **Findings are ordered NEWEST DATE FIRST, on screen and on paper** (physician's report, 2026-09-21). They had never been ordered at all: a reported sheet printed 29 findings in the order they had been TYPED across a year of visits (`08/09/2026 → 19/06/2026 → 24/01/2025 → 08/09/2026 …`), which nobody can scan. `lib/investigationOrder.ts` owns it and BOTH surfaces use it — `sortFindingsByDate` for the printed list in `PrescriptionView`, `sortDateGroups` for the sidebar's date groups — so what the doctor checks on screen is the order that prints. Two rules: **inside one date the doctor's own order is kept** (Hb, then WBC, then PLT is how a blood count is read, so the sort is made stable explicitly rather than trusting the engine's), and an **undated finding sorts LAST**, because the top would give it a recency nobody claimed for it. `findingDateKey` compares `yyyymmdd` as an INTEGER, never a `Date` — the root CLAUDE.md's slashed-date trap, plus no local time or DST in something that is only ever compared. Pinned in `investigationOrder.test.ts`. Note the side effect: a mistyped future date now sorts to the TOP of the list instead of hiding in the middle.
  - **A test tagged with images but given no value renders in the app, never in print.** `InvestigationFindingsField` builds that row at render from the `[image attached]` markers — it is *not* stored in `investigation`, so `prescriptionDoc`/`PrescriptionView`/`investigationSummary` keep excluding it through their existing `[image attached]` filters with nothing new to maintain. A value-less test name on a printed prescription would read to a pharmacy as a missing result. Images hang off a test's **first** value line (one test+date is one row, one 📎, showing the count when >1); the lightbox walks them with ‹ › / ←→ and closes on Escape.
  - **⊘ Hide — findings the printed prescription must not carry (physician's decision, 2026-09-21).** Beside `✎ Edit`, an amber toggle whose tooltip is the physician's own wording, "Hide in Printed Prescription". It is a decision about the DOCUMENT, never about the record, and four rules carry it:
    - **Nothing leaves the screen.** A hidden finding stays in `Prescription.investigation` and stays in the sidebar **in full** — its bullet turns amber and a `⊘` is appended, nothing is removed, faded or truncated. The physician asked for this explicitly: a line the doctor cannot read is a line they cannot check before printing. Pinned in `InvestigationFindingsField.test.tsx`.
    - **A tick MEANS hidden.** No second "apply" press and no inverted tick-to-keep reading for a doctor to get wrong under time pressure. The header button is the master switch and the "select all" the physician asked for: nothing hidden → hide the field; anything hidden → bring it all back. It reads `⊘ Hidden (N)` and carries `aria-pressed` when anything is off.
    - **Only a line that could print is markable.** `[image attached]` markers, `dd/mm/yyyy:Report N` pool rows and the synthesised "report attached, no value yet" row get no tick, because a tick that changed nothing on paper would be a lie on screen. `lib/investigationHidden.ts` owns that test (`isPrintableFinding`) and now owns the print filter `PrescriptionView` used to carry inline; pinned in `investigationHidden.test.ts`.
    - **The mark is the exact stored string**, so it can never suppress a look-alike on another date, and it is **pruned when its finding is deleted** (`pruneHidden`, an effect in `MuqsitContext`) — a line re-typed at a later visit is a new clinical moment and must start visible.
    - **Where it lives:** `hiddenInvestigation` in the editor state, carried in the draft snapshot (`incompleteRx` JSON — additive, no migration) **and in the device mirror**, so the marks survive a reload, a patient switch and "Save to complete later", and a doctor hiding on the laptop does not print everything from the phone. `resetEditor` clears it, so a new visit starts with nothing hidden. The printed sheet and the snapshot image kept in the patient's record are built from the same HTML and can never disagree about what was handed over.
    - **Opt-in, OPD only.** `InvestigationFindingsField` renders the control only when given `onHidden`; `IpdDetailView` and the On-examination field pass nothing and are untouched.
    - **One button, two fields.** The toggle itself is `components/common/HideToggle.tsx`, shared with Drug history's whole-section hide, so the tooltip wording, the amber and the pressed state can never drift apart — a doctor who learns what the amber ⊘ means on one field reads it the same way on the other. It takes an optional `count` (Investigation shows `Hidden (N)`; a whole-section toggle has nothing to count and shows plain `Hidden`).

## UI conventions

_From `client/CLAUDE.md`._

- **Advised tests / investigation has two tabs (physician's request, 2026-09-24):** `Investigations` (the usual box and suggestion chips, unchanged) and `Investigations group`. `ExpandableField`'s opt-in `investigationTabs`, passed by `RightColumn` only. The second tab holds the doctor's OWN groups (below) and shows "No investigation groups yet." until they make one. Never pre-fill it with a system panel of tests: which tests make up a group is clinical content. The Added list shows on the Investigations tab only (hidden on the group tab at the physician's request, same day), but it is one list and one Done applies it, so switching tabs never loses a pick. Pinned in `ExpandableField.test.tsx`.
  - **"Select from Directories" (same day), under the suggestions on the Investigations tab:** `components/investigation/InvestigationDirectory.tsx`, passed in through `ExpandableField`'s generic `renderDirectory` slot. Every category of `INV_CATS` in the catalog's own order, Favourite first; `+` opens one to its test **names** with a tick box each — no result fields, because here the doctor is ordering a test, not recording one. A tick stages the name through the popup's own `toggleOption`, so Cancel still writes nothing. Favourite is the doctor's own list (`useInvestigationPrefs`), looked up against the catalog the same way the Investigation popup does, so a favourite no longer in the catalog is not offered. Nothing here is new clinical content: every name is the catalog's. Pinned in `InvestigationDirectory.test.tsx`.
  - **The doctor's own investigation groups (same day) — the "Investigations group" tab is no longer empty.** `+ Add new group` opens a window: *Name of the group*, the same Select-from-Directories list below to tick the tests, and ONE **Save** in a footer at the very bottom that stores the name and the tests together (physician's request, same day — it was an Add button beside the name). The footer sits outside the scrolling list, and a problem ("Give the group a name.") is shown there beside Save, so it is seen however far the list was scrolled (`InvestigationGroups.tsx`). Before the directories there is also a box to TYPE a test with **Add** beside it (Enter works too; a repeat is not added twice), and the group's tests so far are listed as tags with × — a typed test has no tick box to take it back out with. Saved groups list with a tick box each: ticking puts every test of the group into Added, unticking takes them back out — **except a test another still-ticked group also carries** (`toggleGroup`), so unticking one group never silently drops a test the doctor still asks for through another. Stored per signed-in user in `User.investigationGroups` (`manual-investigation-groups.sql`, applied 2026-09-24), saved through `PATCH /users/me` like favourites. **The save is NOT optimistic**: the window waits for the server and stays open with the name and ticks if it fails, so a group that was never stored can't look saved. Read through `safeGroups` (a Json column: anything malformed is skipped, never thrown on). A group is only ever what the doctor put in it. Not yet built: editing or deleting a group. Pinned in `investigationGroups.test.ts` and `InvestigationGroups.test.tsx`; the server DTO in `update-profile.dto.spec.ts`.
  - **No built-in suggestion chips on the OPD field (same day):** `RightColumn` passes no `suggestions`, so the chips are only tests THIS doctor has added before — the per-user recents every Done saves, whether the test was typed, ticked in a directory or picked. Typing a test + Add still puts it straight into Added. The IPD sheet's "Advice tests" still uses `advisedTestSuggestions`; it was not part of the request.

## Responsive layout

_From `client/CLAUDE.md`._

**A test's report image opens BESIDE the Investigation form (physician's request, 2026-10-15).** Clicking a test's thumbnail used to open a new browser tab. It now opens `ReportViewerPane`, a column to the right of the form:
- the image large, with zoom (− / + / Fit, also `+` / `-`), rotate ↺ ↻ and drag to move about;
- ‹ › and ← → through **every test image of the chosen day** (`dayImages` in `lib/investigationImages.ts`; pool reports not yet tagged to a test are not in it), with thumbnails to jump;
- its own × (Escape closes the viewer first and leaves the popup open);
- on a phone it covers the form instead of standing beside it.
A zoomed image is centred with `margin: auto`, never `justify-content: center`: centred by its box, it spilled out on the LEFT, where no scroll reaches, and the start of every line was cut off. The older reports pane on the left had the same fault and was fixed with it. Pinned in `ReportViewerPane.test.tsx` and `InvestigationPopup.viewer.test.tsx`. In the sandbox an upload's URL carries `:4100` while the API serves on `:4200`, so its images show broken there: that is the sandbox, not the viewer.
