# The rules, in full

## Patterns We Do Not Use

_From the root `CLAUDE.md`._

- We do not change a colour, size or spacing in `prescriptionDoc.ts` as part of an app restyle. It imports no theme on purpose; its five accent rules were moved to blue once, by the physician's decision, with the whole-document snapshot updated in the same commit.

## ⚕️ H/O drug hypersensitivity and High-Alert Medication (physician's sheet, 31/10/2026)

_From `client/CLAUDE.md`._

Its styles are INLINE, so a sheet without it is byte-for-byte the sheet as before (whole-document snapshots unchanged); its words bound the fill factor like the rest of the column, and lines wrap, never cut (`prescriptionDoc.drugSafety.test.ts`).

## Editor lifecycle (easy to break — know it)

_From `client/CLAUDE.md`._

- **The gallery snapshot is filed ONCE PER SHEET (2026-08-23).** "Save & print" still pictures the printed document into "All prescriptions(Image)", but only when that gallery does not already hold it: the physician's rule is that the first save files a copy, and after that only a save whose sheet actually differs does — clicking Save any number of times on a visit nothing was changed on must not file the same paper again. The comparison is the **HTML**, never the image bytes: two captures of one prescription are not equal as files (html2canvas rasterises a live DOM, and `compressImage` re-encodes lossily and only when that comes out smaller), while the HTML is the very string that feeds both the print window and the capture. It is deliberately **not** normalised — the header date, page size and margins are in it, and a sheet printed on another date or another page is another document (the physician asked for any change to count, not only a change of wording). `lib/rxSnapshot.ts` holds all of it: `rxSnapshotKey` (SHA-256 hex, or **null** when `crypto.subtle` is missing outside a secure context) and `createRxSnapshotGate`. Three rules there are safety, not tidiness: a **null key always files** (cannot tell ⇒ keep the copy), **no recorded key always files** (a first save, and every patient from before the column existed), and a failed capture **releases** the claim (`releaseRxSnapshot`) — a gate that believed a sheet was filed when nothing arrived would suppress every identical save after it, leaving a document the doctor handed over with no copy on file. The claim is taken *before* the capture precisely so a second click landing mid-capture is refused; Save & print has no in-flight guard of its own. The fingerprint lives in `Patient.lastRxImageKey` and is written in the SAME PATCH as `prescriptionImages`, so image and key can never disagree. Hand-added images ("Add more prescription image") never touch it.

- **"Save & print" also PRINTS (2026-08-15), IN THE APP (2026-08-26).** It shows the same `buildPrescriptionHtml` document "Preview PDF" shows; the two routes differ only in that this one persists the visit first. Until 2026-08-26 the sheet was a second browser window (`window.open`), which the physician called out as user-hostile: it needed a pop-up allowance to appear at all, it buried the editor behind it, and on a tablet it is a second app to dismiss. It is now `components/prescription/PrintSheetModal.tsx` — a full-screen in-app overlay owning the Print / Close buttons, opened from `sheet` state in `PrescriptionView`.
  - **The sheet still renders in an `<iframe>`, and that is not incidental.** The document carries its own `@page` size, print stylesheet, `<base href>` and font rules; loose in the app's document they would restyle the editor and print the wrong thing. `iframe.contentWindow.focus()` then `.print()` prints the framed document — the printed page is byte-identical to what the pop-up printed, only the frame around it changed. `buildPrescriptionHtml` no longer emits a `.toolbar` of its own (a `window.close()` button is meaningless in a frame), so the document is now the medical page and nothing else.
  - **Ctrl/Cmd+P is intercepted while the modal is open** and sent to the frame. Left alone it prints the APP page with the sheet squeezed in as one framed element — and a doctor's reflex is to press it. Since 2026-10-12 the same key is caught INSIDE the frame as well, where the focus sits after every Print; Escape and Tab there are handled too (the popup bullet under UI conventions).
  - Three things in `handleSave` are still load-bearing, not style: (1) the modal opens **immediately on the click** in a "Saving the prescription…" state, so the doctor never wonders whether the click registered; (2) **the save runs before anything that can throw** — building the sheet sits after it, in a `try`, so a render failure costs the printout and never the record; (3) a failed save **closes** the modal — a printable prescription must never be on screen for a visit the record does not have — and `savePrescription` has already said why in a box ("The prescription was not saved.", or "…may not have been saved." where its answer was lost and three quiet re-sends brought none; "What the Save buttons say" under UI conventions). The sheet stays at "Saving the prescription…" through those re-sends, up to seven seconds. The fill-in is `setSheet((prev) => prev.open ? … : prev)`, so a doctor who pressed Close mid-save does not get the sheet thrown back at them. The same HTML string feeds the on-screen sheet and the gallery snapshot, so the stored image is provably the document that was printed.
  - **Still a pop-up:** `InvestigationDownload.tsx` opens its report in a `window.open`. Same treatment when it comes up.

## UI conventions

_From `client/CLAUDE.md`._

- Print/PDF: `lib/prescriptionDoc.ts` builds a standalone HTML document, `document.write`-n into the print modal's iframe (and, for the gallery snapshot, into an off-screen one). Tables are `table-layout: fixed` with wrapping cells — long values must wrap **inside** the printable area, never overflow. **The Rx table is the exception: it prints at ONE fixed type size — 14px — for the whole sheet, and on ONE line per cell wherever the row has the width** (`layoutRxColumns`, 2026-08-16; size fixed 2026-08-26). Its columns were fixed percentages (drug 25%), so `Tablet. Barcavir 0.5 mg` broke across three lines — which a dispenser reads as three things — while an empty "food" column sat holding a quarter of the row. Now:
  - **⚕️ The dose prints UNDER the medicine name, and has no column of its own** (physician's decision, 2026-09-12). `1+1+1` is the instruction for the medicine directly above it; as a column it sat an inch away across white space. The name and the dose are now two block `<span>`s in ONE `<td>` (`.rx-name` / `.rx-dose`), so the table is **drug + [food] + duration** — 2 or 3 data columns, not 3 or 4, and `noteSpan` follows. Four consequences, all pinned in `prescriptionDoc.test.ts`:
    - **The drug column is sized for the WIDER of name and dose, never their sum** (`drugLineNeed`) — they are separate lines. `rowPx` measures the same way, so a row is only shrunk for whichever of the two is tighter.
    - **A tapering (`>>>`) row has no name for its dose to sit under, so its dose prints BESIDE the ↳** (`.rx-dose-inline`), and that row is measured as `CONT_INDENT_PX + dose`. Keep the constant in step with the ↳'s 14px indent if that ever changes.
    - **⚕️ The ↳ marker is a SCREEN aid and is hidden on paper** (physician's decision, 2026-09-12): `@media print { .rx-cont { visibility: hidden; } }`. It still renders in the print preview and in the gallery snapshot — only the printed sheet drops it. **`visibility`, never `display: none`**, and both halves are load-bearing: the dose keeps the arrow's space so it stays indented under the medicine it continues (flush left, `0+0+2 · Continue` reads as a medicine of its own with no name — a misread on a dispensed sheet, not a tidier line), and the width maths stays honest, since `drugLineNeed` measures that row as `CONT_INDENT_PX + dose` and a collapsed box would print the row narrower than the column it was measured for. Pinned in `prescriptionDoc.test.ts`, including that `display: none` has not crept in — a print-only rule is invisible to every other check in the suite.
    - **An empty dose emits nothing** — not a blank second line, which would space the next medicine away from its own row.
    - **This is what finally fixed the wrapping medicine names.** The width the dose column held went straight to the drug names: the reported 8-medicine sheet now prints **all eight labels on one line at 14px**, including `Capsule (Enteric Coated). Sergel 40 mg` and `Oral Solution. Avolac 3.35 gm/5 ml`, which the note below listed as the honest exceptions no page split could fix. `lay.wrap` is `false` on that sheet where it used to be `true`. **The trade-off is height, not width:** a medicine with a dose is now two lines tall, so a long prescription reaches the foot of the page sooner and the page-fill factor grows the type less.
  - **Columns are measured, not assigned.** Each is sized against the widest value it actually carries, and the food column is **dropped entirely** when no line has one (the note row's `colspan` follows). Widths ship as a `<colgroup>` of px — do not put percentage widths back in the CSS.
  - **Widths come from real text metrics.** `measureRxText` asks a canvas, because character counts lie: `Illlll` and `Wmmmmm` are the same length and nowhere near the same width, and guessing wide shrinks a name that would have fitted. There is a character-count fallback for when no canvas exists (SSR, tests) — it is deliberately generous, since underestimating means text off the edge of the page.
  - **14px is the FLOOR, and the sheet is scaled up to FILL the page** (`--k`, physician's decision 2026-08-28, superseding the fixed-14px rule of 2026-08-26). A six-medicine prescription printed at 14px on A4 left the bottom half of the page blank and came back “so small it is not readable”. Every **type size** and the `td` *vertical* padding is written as `calc(var(--k, 1) * Npx)` through `SCALE_PX`, so one number grows the whole document evenly. **Widths are NOT scaled, and must never be again** — see the bullet below. `--k` is chosen by a small script INSIDE the generated document (`FIT_SCRIPT`), not by the builder: only the browser knows how many lines a diagnosis wrapped to or which font actually resolved. It binary-searches the largest `--k` that keeps three promises, in order: never shrink (`--k` starts at 1, the sheet exactly as it printed before), never spill onto a page the prescription did not need (`data-avail-h` = `sheetContentPx`), and never let text run past the column it is printed in (`data-kmax`, re-checked by measuring the table's `scrollWidth`, so it holds even if the printer resolves a different font from the one the widths were measured against). If the script throws, `--k` stays unset and the sheet prints at its floor. Measured in a real browser on the reported prescription at A4: 14px → 15.8px, **99% of the page height used**, every ℞ row still on one line.
    - **⚠️ `MAX_SCALE` is 1.25, down from 1.6 (physician's report, 2026-09-12: "when I print the prescription all characters shows very big").** At 1.6 the ceiling was 22.4px, and a SPARSE sheet hit it every time — the script grows until the page is full *or* the cap bites, and on a short prescription it is always the cap, so the emptier the sheet the bigger the type. The old comment here said 22.4px "is already large print; past that it reads as a poster"; the physician's answer is that it already did. 1.25 puts the ceiling at 17.5px, still well clear of the 14px floor this fill was introduced to lift. **This is the one number that sets how large a printed sheet can get** — lower it again if the print still reads big; it can never go under the base sizes, because the script starts at 1 and only grows.
    - **The clinical blocks: the green heading is now LARGER than the lines under it** — `BLOCK_TITLE_PX` 11 → **13**, and a new `PROSE_PX` **12** for `li` (same decision). The heading used to be the smaller of the two (11 under 14px items) and only its weight, colour and tracking made it read as a heading at all. Both sit below the ℞ table's 14px on purpose: the medicines stay the most prominent thing on the sheet. **The 14px floor documented here is the ℞ TABLE's and has never applied to the clinical prose.** `PROSE_PX` is written into both the CSS and `wordHeadroom`'s measurement, so the size that prints and the size the width bound is computed from cannot drift — measuring 14px words against a column printing 12px would silently cap the sheet too low.
    - **The ℞ table is no longer ONE size either: the medicine NAME is bigger than everything beside and under it** — `DRUG_PX` 14 → **13**, `MID_PX` 14 → **11** (physician's decision, 2026-09-12, third pass: "medicine er name ektu boro thakbe, er nicher dose r ja likha thake segulo tar theke choto thakbe… existing ja ase tar theke size komaw"). `MID_PX` covers **every** non-name cell — the dose line under the name, the food column, the duration column and a free-typed `.rx-note` row (at 14 a note printed *larger* than the medicines above it). `FOOT_PX` (13) keeps the follow-up line and the signature level with the medicine name so nothing on the ℞ side outranks it. `MAX_SCALE` came down again with it, 1.25 → **1.15**.
    - **A shrunk row shrinks BOTH sizes by the same ratio** (`midSize = floor(MID_PX × rowPx/DRUG_PX × 10)/10`), so the name/dose relationship is constant down the sheet and the width guarantee survives: `rowPx` is chosen from needs already measured at `DRUG_PX` and `MID_PX` respectively, so one shared ratio keeps every cell inside its own column. It is **floored, not rounded** — the same rule `rowPx` follows, because every width guarantee here is an inequality a fraction of a pixel can break.
    - `DRUG_PX` / `MID_PX` are **exported and the tests assert against the constants**, not against literals — the sizes moved three times in one day and each move used to mean rewriting a dozen expectations by hand.
    - **⚠️ `MID_PX` (11) is the smallest type on the sheet and a dispenser reads the DOSE off it.** Since 2026-09-21 it is also exactly what every dose prints at — there is no per-row shrink to push it lower. Treat it as a floor to defend: bring a sheet down with `MAX_SCALE`, which moves everything together, rather than by trimming this.
    - Measured on the reported sheets across the three passes: cap 1.600 → 1.250 → **1.150**; ℞ medicine name 22.4 → 16.9 → **13.5px**; ℞ dose/food/duration 22.4 → 16.9 → **11.4px**; block title 17.6 → 15.7 → **13.5px**; clinical line 22.4 → 14.5 → **12.5px**.
  - **⛕ The paper does not scale, so no WIDTH may be written through `--k`** (reported 2026-08-30, and the reason the rule above changed). The Rx `<colgroup>` widths *were* `calc(var(--k) * Npx)`, on the reasoning that text and column can never outgrow each other if they grow together. They can outgrow the page: at `--k` = 1.19 the table measured **573px inside its 490px grid track**, the `.body` grid handed it the overflow, and the clinical column collapsed **209px → 87px** — the whole diagnosis printed one word per line down the left edge, some words split mid-word ("multifoc / al HCC"). Three rules hold it shut, all pinned in `prescriptionDoc.test.ts`:
    - **Column widths are a SHARE of the table** (`<col style="width:N%">`, from the same measured px), so the table is always exactly its track at every `--k`. Horizontal `td` padding is therefore a plain `4px` — it must not grow either, or it would eat the content box the widths were measured against. `CELL_PAD_PX` is 2 × that; keep them in step.
    - **The grid tracks are `minmax(0, …fr) 0.5px minmax(0, …fr)`.** A bare `fr` floors at its content's min width, so anything too wide on the ℞ side steals the clinical column's share instead of wrapping inside its own. With `minmax(0, …)` the two columns hold their proportions whatever they carry. **The two shares are no longer constants** — see the Body Section bullet below; an untouched slider still resolves to the historic `0.7 / 1.7`, written normalised as `0.291667 / 0.708333`.
  - **⚕️ The Body Section's separator now reaches the paper (`bodyShares`, physician's report 2026-09-12: "eikhane barale komale seta apply hoy na, ami print kore dekhsi").** `bodySplit`, `bodyLeftTopMargin`, `bodyRightTopMargin` and `bodyBottomLine` were saved to `PrescriptionLayout` from the day the settings wizard was built and read by **nothing** — the sheet's columns were hard-coded — so moving the slider changed the settings preview and never the printed sheet. `PrescriptionDoc.body` now carries them and `PrescriptionView` passes them. Five rules, all pinned in `prescriptionDoc.test.ts`:
    - **A blank / absent / unparseable / zero / negative split prints byte-identical output to before.** Pinned as an exact string equality against six such inputs — a doctor who never opens that step must not find a new layout on the sheet they hand to a patient.
    - **`bodyShares(page, body)` is the ONE answer** and everything measures against it: the `.body` grid, `rxTableInnerPx`, the clinical column's word bound and the ℞ side's prose bound. A second, independently-derived share is precisely how a table ends up sized for a track it does not have (the 2026-08-30 overflow).
    - **The split is measured from the left edge of the PRINTABLE box, in the page's unit** — the same origin `BodySection` uses, so the centimetre printed under the slider is the centimetre that prints on paper.
    - **⚠️ The clamp is derived from the paper, NOT a fixed percentage.** A flat `0.70` cap was tried and is wrong: measured on the reported 18.5cm page it left the ℞ side a 169px track while `rxTableInnerPx`'s 160px floor made the table 192px — wider than the column holding it. The ceiling is now `1 − RX_MIN_TRACK_PX/contentPx` (the width at which that floor stops binding) and the floor `CLINICAL_MIN_TRACK_PX/contentPx`; paper too narrow for both keeps the historic split rather than obeying the slider into an overflow. A test sweeps the slider from −20% to 130% across five real page sizes and asserts the table always fits its track.
    - **Top margins print in the page's unit and are NOT written through `SCALE_PX`.** They are distances the doctor measured on paper, like the page margins; growing them with the type would move the body every time the fill factor changed.
    - The settings screen's own preview was lying when the slider was untouched — it drew the separator at the middle of the page while the sheet has always printed `0.7 / 1.7`. `BodySection` now imports `DEFAULT_LEFT_SHARE` from the print builder, so the preview and the paper cannot drift.
  - **⚕️ The Header Section PRINTS, inside the printable area (physician's decision, 2026-10-07: "header a ja likhbo oita printable area a print hobe").** Until then `headerSplit`, `headerAlign`, `headerHtml`, `headerLeftHtml` and `headerRightHtml` were saved and read by nobody, and `.head` was deliberately empty on the theory that the band above it was a pre-printed letterhead. The physician's call: that band is a **margin** — Page Setup now labels the two bands **Top margin** / **Bottom margin** (stored names unchanged, `headerHeight` / `footerHeight`; pinned in `PrescriptionSettingsView.test.tsx`) — and the header they design prints under it, above the rule and the patient details, on every page. `PrescriptionDoc.header` carries it; `PrescriptionView` passes it. Rules, pinned in `prescriptionDoc.test.ts`:
    - **No visible header ⇒ byte-identical output to before** (`<div class="head"></div>`): blank, `<div><br></div>`, `&nbsp;`, or text only in the half the split switch is not showing. A doctor who never wrote one sees no change on the sheet they hand over.
    - **It is sanitised in the CALLER, never in the builder.** `buildPrescriptionHtml` runs without a DOM (the whole-document snapshots pin it in node), so it prints what it is given; `PrescriptionView` runs `sanitizeHtml(…, { images: true })` first — the one place `<img>` survives, and only from an `http(s)` URL or `/uploads/…`, with `width`/`height`/`alt` and nothing else (a clinic logo). The personal note keeps the default and never prints a picture.
    - **The header's type is NOT written through `--k`.** Its sizes are the doctor's own, set in the settings editor, and print as designed whatever the fill factor does to the prescription under it; the base is the editor surface's 13px / 1.6 so paper matches screen. It is part of `.pagecontent`, so the fitting script measures it and a tall header simply leaves less room for the sheet to grow.
    - A split header is a `minmax(0, 1fr) minmax(0, 1fr)` grid, for the reason `.body` and `.pt` carry it. An unknown `align` prints left.
    - **The Footer Section prints too (same day, "footer o print hbe"):** `PrescriptionDoc.footerHtml`, sanitised the same way, as `.foot-body` in the repeating `<tfoot>` UNDER the signature row — the signature keeps its fixed place and the doctor's own strip (chamber, hours, contact) is the last thing on every page. Blank ⇒ nothing emitted (byte-identical). Same 13px / 1.6 base, never through `--k`, measured by the fitting script as part of the foot.
  - **⚕️ The signature is FIXED at the foot of the page (physician's decision, 2026-10-07: "name sob somoi nicha fixed thakbe").** `.sign` moved from the end of the ℞ column into the repeating `<tfoot>`, in a `.foot` flex row — brand bar left, signature right, both on the bottom edge. On a short prescription it used to sit halfway down the sheet. Two things make it the bottom of the PAPER and not just of the content: on screen the sheet was already a flex column with the table stretched; **in print `.pagegrid` now gets `height: calc(pageH − top − bottom − 4px)`** — the printable height the `@page` margins leave, less a hair so a rounding error can never push out a blank second page. A table's height is a minimum, so a prescription that genuinely needs two pages still fragments as before, with the foot (and the signature) repeated under each part. The 56px above the line is room to sign in and is part of the foot's measured height, so the fitting script reserves it. Checked in Chromium (Playwright `page.pdf`, 2026-10-07): a two-medicine sheet on the physician's own A4 with 2in top/bottom margins prints ONE page with the signature's line 719px down a 738px printable area; a split header on the 18.5×27cm page likewise; the OPD privacy copy prints two pages; a 22-medicine sheet fragments to three with no blank trailing page.
    - **`overflow-wrap` / `word-break` are INHERITED properties.** The ℞-cell rule (`overflow-wrap: anywhere`) reached the entire sheet through `td.pagebody` and broke a diagnosis mid-word — and `anywhere` also drops an element's min-content width to one character, which is what let the column be squeezed to nothing in the first place. `td.pagebody` resets both; only the ℞ cells break words now.
  - **The fill factor is bounded by every column, not just the ℞ table.** `data-kmax` = `min(layoutRxColumns().maxScale, wordHeadroom(…))`. `wordHeadroom` measures the widest single WORD of each block of prose against the fixed column it prints in — the clinical column (`0.7/2.4` of the page less `.left` and `ul` padding), the ℞ side's prose (notes, advice, follow-up, signature) and the two halves of the patient header. Wrapping between words is normal typesetting; splitting a word is not something a prescription should print, and on a diagnosis it is what a reader notices first. It never goes below 1 — a word too long for its column at the floor size still breaks, because shrinking the sheet is not on the table. This is why `cleanItem` / `drugNameOnly` return **plain text** and the caller escapes: the bound has to measure exactly what is printed, and `&amp;` is not the width of `&`.
  - **EVERY medicine name prints at ONE size, and an over-full row WRAPS** (physician's decision, **2026-09-21**, reversing the per-row shrink of 2026-08-28 and restoring the 2026-08-26 wrap rule). The reported sheet had eight medicines at four different sizes — `Capsule (Enteric Coated). Maxpro 40mg` set at 11px directly above `Tablet Amaryl 1mg` at 13px — and the physician's judgement is that a reader scanning a prescription takes a size difference for a MEANING difference: the smaller name reads as the lesser instruction. A wrapped name is one medicine on two lines, which the numbered column already makes unambiguous. So `rowPx` is now `DRUG_PX` for every row and `rowWrap` is simply "did not fit"; `ROW_MIN_PX` is gone. The whole ℞ table therefore carries exactly **two** sizes — `DRUG_PX` (13) for names, `MID_PX` (11) for dose/food/duration — and `prescriptionDoc.test.ts` pins that a third size never appears. `rowPx` is still indexed over the NON-NOTE rows only, so a free-typed note line must not advance the counter when the table is rendered. The on-screen ℞ pad was never affected: `MedicinePad` sets every drug line at a flat 13.5px and has no per-row sizing.
  - **⚠️ A page configured larger than the paper is the other half of “the print is too small”, and no code can fix it.** The reported sheet came from settings of **7.5 × 15 in** printed on A4: the browser scales a 15in-tall page down to 11.69in, so everything printed at ~78% and the content sat in the top half. On that geometry `maxScale` is **1.000** — the ℞ table is already width-bound on a 7.5in-wide page — so the fill above cannot help either. When a printout comes back small, read Prescription settings first: the page must be the paper.
  - **The shortfall is taken off the DRUG column, never the dose — but a column that will wrap anyway is capped at an equal share first** (`fitColumns`, 2026-08-26). The rule was plain max-min fair on the natural widths until a printed sheet came back with seven of its eight medicine names broken. Max-min fair reads a column's longest value as a requirement, and ONE free-typed dose (`2-4TSF at night if constipation`, 197px) made the dose column look as needy as the drug column: the two split the remainder evenly at **117px each**, the dose still wrapped at 117px, and every drug name (134-266px) was starved for nothing. So the allocation is now by need, not by rank — each non-drug column keeps its whole value on one line if that fits inside an **equal share** of the row (this is what still protects `1+0+1`, `Before meal` and `Continue` absolutely), a column asking for more is capped there but **never below its own longest word** (`td` carries `word-break: break-word`, so a narrower column would print `consti / pation`), and every remaining pixel goes to the drug names. Measured in Chrome on the reported 8-medicine sheet: the drug column went 117px → 173px and one-line medicines went **1 of 8 → 6 of 8**, with only `Capsule (Enteric Coated). Sergel 40 mg` (38 chars) and `Oral Solution. Avolac 3.35 gm/5 ml` (34 chars) taking a second line — down from three lines each. Pinned by "starves the drug column, never the dose, when the row is over-full" and "keeps ordinary medicine names on one line beside one long free-typed dose".
  - **Only the brand NAME is bold** (physician's decision, 2026-08-23): in `Tablet. Napa 500 mg` the eye should land on `Napa`, not on the dosage form or the strength. `.rx-drug` is weight 400 and `splitDrugLabel` (`lib/rxShorthand.ts`, the inverse of `fmtMedicine`) wraps the name in a `<b>`. It returns **index ranges of the label**, so the three escaped pieces reassemble byte-for-byte into what the doctor entered — the split decides emphasis, never text, and `rxShorthand.test.ts` asserts that round-trip on every case. The form rule is the structural one from `server/src/rx-habits/normalise.ts#splitForm` (up to the first `.`, no digit in the head, ≤4 words, qualifier included); the strength is the trailing run starting at the first digit-leading token or a trailing `N/A`, and never the first token after the form, so `Tablet. 5-FU 500 mg` keeps its name. A label whose name cannot be read stays wholly bold — no emphasis at all would be worse. **`layoutRxColumns` still measures the label as if all of it were bold**: an over-estimate of a couple of percent that can only hand the column more room than it needs, deliberately kept over a slightly larger print.
  - **Whether the sheet can print `nowrap` is read off the width each column GOT, not the share it asked for.** Widths are whole px and their total can never exceed the row; a `nowrap` cell sitting a fraction wider than its own column is sub-pixel, invisible in a browser, and exactly the kind of thing that prints as a collision — pinned by "never lets a cell overflow its own column, at any sheet width" in `prescriptionDoc.test.ts`. There is no legibility floor any more (`FLOOR_PX` is gone): nothing is ever truncated or pushed past the printable width, and nothing is ever printed under 14px.
  - `rxTableInnerPx` derives the row from the doctor's own page-size settings (in/cm), so a custom page or wider margins stays safe. Verified in a real browser, not just in theory; `prescriptionDoc.test.ts` pins those numbers (`A4_INNER` is the **data** columns — **458px** since 2026-08-26, was 428px — with `RX_NO_PX` making up the rest). **`RX_NO_PX` (32) is sized for a TWO-digit serial**, because a 10-medicine prescription is ordinary and `10.` measures 19.5px at 14px DM Sans; at the old 22px the number dropped onto a second line beside the medicine it numbers. **Known trade-off — SUPERSEDED 2026-09-12, kept for the reasoning:** at a fixed 14px a crowded sheet used to buy its size with wrapped drug names — a label past ~34 characters alongside food values took a second line, and the note here said no sane page split fixed that (fitting a 38-character label on one line needs the clinical column down to ~150px). A page split did fix it: moving the dose **under the medicine name** freed its whole column for the names, and the reported 8-medicine sheet now prints every label on one line at 14px (see the dose bullet above). Two levers bought the width back on 2026-08-26, both product decisions the physician made rather than tweaks: the `.body` grid went `0.8fr / 0.5px / 1.6fr` → **`0.7fr / 0.5px / 1.7fr`** (clinical column 239px → 209px) and `CELL_PAD_PX` went 12 → **8** (`td { padding: 7px 4px }`). Measured then: **dropping the type size is NOT a third lever** — at 13px and even 12px the same two labels still wrap, because the non-drug columns are capped at a share of the row that does not shrink with the font. Keep 14px. The document carries a `<base href>` because it is written into an `about:blank` window (and an off-screen iframe for the gallery snapshot), where a relative image `src` has no reliable base — that is why the footer logo loads at all. Each `.sheet` is a single-cell `<table class="pagegrid">` whose `<tfoot>` holds the MHS / By EXHORT brand bar: a `tfoot` repeats on every printed page **and** has its height reserved in the flow, so it can never overprint a medicine row. Do not "simplify" it to `position: fixed` — that sits lower but is free to overlay content on a full page. The scoped `.pagegrid > tbody|tfoot > tr > td` resets exist so the global `table`/`td` rules (which belong to the Rx table) do not leak into the wrapper; keep the child combinators. The OPD "privacy copy" masks identity and drops clinical content — keep new sections out of it unless the patient needs them. Drug history prints **names only**, deduped.
  - **The patient header's right half — Date / Mobile / Address — starts PAST the middle of the sheet** (physician's ask, 2026-09-12). `.pt` was two equal halves (`1fr 1fr`); it is now `minmax(0, 0.56fr) minmax(0, 0.44fr)`, so the date column begins at ~57.5% of the printable width instead of ~51.7%. Three things hold it, all pinned in `prescriptionDoc.test.ts`:
    - **The offset is a SHARE, never a px indent.** That is the whole of "keep it aligned for every paper size": measured across A4, Letter, Legal, A5, a 5.8in page and the reported 7.5×15in, the date starts at **57.5–58.2%** on every one (it moved 42px on A4 and 27px on A5 — proportionally, which is the point). A fixed px nudge would be a hair on A4 and a third of the column on a narrow sheet. To move it further, raise `PT_LEFT_FR` and lower `PT_RIGHT_FR` by the same amount; they are one pair of constants beside `PT_GAP_PX`, which now also writes the CSS `gap` so the stylesheet and the width bound cannot drift apart.
    - **`minmax(0, …)` for the same reason `.body` carries it.** A bare `fr` track floors at its content's min width, so one long name or address would shove the date column to wherever it happened to fit — a different offset on every patient. With `minmax(0, …)` the halves hold their share whatever they carry and long values wrap inside their own column.
    - **The two halves are measured SEPARATELY in `wordHeadroom`.** They are no longer equal, and the narrower right half carries the **Address** — the longest value on that side. The old single `headAvail` (`content / 2 - PT_GAP_PX / 2`) would now over-state the room the address has and let the fill factor grow the type until an address word broke. **Known trade-off the physician should see in use:** a long address has ~12% less width than before and will wrap to a second line sooner. It wraps — it is never truncated — and the fill bound stops it being split mid-word.

## A long ℞ line wraps cleanly, and a medicine is never cut across two pages (2026-11-15)

_New on 2026-11-15, not moved from a `CLAUDE.md`._ Physician's report: "after printing, the lines come out misaligned and messy; if a line is too long for the Rx pad it should wrap cleanly onto the next line; whatever size is selected in the settings, the template layout must stay consistent." "Size" was read as **Page Size** in Prescription settings (total width / height and margins), the only size setting that reaches the paper.

- **What was measured first.** A nine-line sheet (long names, a free-typed dose, a taper, a note, an insulin pen line) built by the real `buildPrescriptionHtml` in Chromium, then printed to PDF (`page.pdf({ preferCSSPageSize: true })`) and read back page by page in Chromium's own PDF viewer. On A5, 6×9 in and 15×21 cm the sheet ran onto a second page and **medicine 8 was cut in two**: its name and the start of its description stood at the foot of page 1, and "prefilled pen" and its DOSE (`20 units subcutaneous at bedtime`) began page 2 with no name above them. A `>>>` taper could be parted from its medicine the same way. On A4 with the same data nothing was cut, which is why it looked like a problem of page size. Also measured: the serial (14px), the name (13px) and the food / duration cells (11px) hung from the TOP of the row, so each sat on its own baseline, up to **2px apart on every line**; and a wrapped name split a number from its unit ("Napa Extra 500 / mg+65 mg", "Esoral 20 / mg").
- **⚕️ A ℞ row is never cut across two pages.** `.right table tr { break-inside: avoid }`: a row that does not fit what is left of a page moves, whole, to the next one. A dose line that starts a page without its medicine name above it is a misread, not a tidy break. `.rx-keep-next` (`break-after: avoid`) goes on a row that a `>>>` taper continues, so the taper stays on the page of its medicine (the same rule the pad keeps in `rxItemsFromRows`); a note line is not a taper and does not get it. `.block-title` and the ℞ symbol keep with the line under them, and a `li` / the follow-up line are not split. Pinned in `prescriptionDoc.test.ts` ("a medicine is never cut across two pages"); the breaks themselves can only be seen in a browser.
- **One baseline per row.** `.rx-no, .rx-drug, .rx-mid, .rx-note { vertical-align: baseline }`. Measured 0.0px apart on every page size after it (was up to 2.0px).
- **⚕️ A number is kept with its unit by a wrap where the pair fits its cell — `glueUnits`, `glueWhereItFits`.** A non-breaking space replaces the space between a digit (Latin or Bangla) and a unit from a LISTED set (`mg`, `ml`, `IU`, `units`, `days`, `month`, `দিন`, `চামচ`, …) in the ℞ cells: name, dose, food, duration. Only the listed units: gluing every word after a digit would build long unbreakable runs (`1+0+1 before`). **Only where the glued pair fits the cell** (`glueWhereItFits`, against the drug cell's content width): a glued pair cannot break at its space, so in a cell narrower than it the browser breaks it between DIGITS — on A6 "500 mg+65 mg" printed "500 mg+6" over "5 mg", a 65 mg strength read as 6 and 5 (found in independent review, 2026-11-15, in the first version, which glued unconditionally). Where it does not fit, the cell prints exactly as typed and breaks at its spaces, as it did before this change. The same test is made for the food and duration cells (their columns are floored at their own longest glued word, but `fitColumns`' final rounding correction can still take a pixel off the widest). Three more cases are left unglued on purpose: **nothing is glued when the ℞ side of the page is narrower than the table's 160px floor** (`RX_INNER_FLOOR_PX`: the columns are then modelled on a table wider than the real one, so a pair that "fits" can still break — second review, 2026-11-15; about a 3.9 in page with 0.4 in margins, or an A6 with wide margins); **a tapering row's dose is never glued** (it sits beside the ↳, whose width `CONT_INDENT_PX` only estimates); and the decision is made with the app's measure (DM Sans) while the print frame has no `@font-face` and prints in Arial — the same assumption every width on the sheet rests on, with the same 2% `FIT_SAFETY`; a wrapped cell has no runtime guard (`letWrap` covers only cells held on one line). Pinned over page widths 2.5–9 in against the model (`prescriptionDoc.test.ts`), which cannot see the last of these. The change is the space only: nothing is added, lost or reordered (pinned; idempotent) and the stored text is untouched — but the printed HTML does carry U+00A0, so text copied from the print preview or extracted from the PDF has U+00A0 in it, and a run of spaces or tabs is printed as one. The **column measurement uses the glued word** (`widestWordIn` calls `glueUnits` first and splits on ordinary whitespace only, never JS `\s`, which matches U+00A0) — measured as "months" alone, a squeezed duration column was set narrower than "12 months". The constant is `String.fromCharCode(0xa0)`, never a literal U+00A0 in source: invisible, and it gets "tidied" into a plain space.
- **⚕️ The page foot stays ONE row.** The foot (brand bar + signature) is a repeating `<tfoot>`, which Chromium repeats under every page only if it is short enough. A foot that wrapped onto a second line (`flex-wrap`, tried to stop the brand bar being squeezed to "B / y" on a narrow page) was taller than that: on a four-page A6 sheet pages 1–3 printed **with no signature at all**. So `.foot` has no `flex-wrap`; the brand bar is `flex: 1 0 auto` (never shrinks below its content) and the signature is `flex: 0 1 auto; min-width: 0` with its line `min-width: min(200px, 100%)`, so it is the signature's NAME that wraps on a narrow page (the foot is then one line of text taller; that still repeated on all four pages of the A6 check — it is a foot whose whole signature block drops BELOW the brand bar that did not).
- **⚕️ The fitting script catches a cell the browser could not hold on one line** (`letWrap`, `spills` in `FIT_SCRIPT`). A row measured as fitting prints `white-space: nowrap`; if the print frame resolves a font a little wider than the one the widths were measured with (the frame has no `@font-face`; the app measured with the web DM Sans), the text ran into the next column — "Before meal" 4–7px into the duration — while the table, still inside its own box, reported nothing (reproduced by widening the glyphs of a built sheet by 0.9px). Now: a cell of SEVERAL words that does not fit is let go (`white-space: normal`) and wraps at its spaces — that cell only; a SINGLE word is never let go, because it has no space to wrap at and would be split mid-word ("Continu / e", seen once when the whole row was let go); for a spill that cannot wrap the fill-factor search (`fits`) backs `--k` off instead. What is measured is the cell's TEXT (a `Range`) against its content box, not `scrollWidth`, which ignores text that spills into the cell's own empty padding. A cell that fits is left exactly as built. Logic pinned in `prescriptionDoc.fit.test.ts` (jsdom, geometry stubbed — it lays nothing out); the browser side was checked by the forced-wider-font run above.
- **Side effect, by design:** the gallery snapshot key (`rxSnapshotKey`) is a hash of the sheet's HTML, and this change altered the HTML of every sheet (the stylesheet, the fitting script, and the non-breaking spaces in ℞ cells). The first "Save & print" of an existing visit after it is deployed therefore files one more copy of the sheet in "All prescriptions(Image)" — the rule ("any change to the sheet counts") working as written; the same happens after any change to this file.
- **How it was checked, and what was NOT.** Chromium via Playwright (`page.pdf`, then the PDF opened in a `channel: 'chromium'` page at `file:///x.pdf#toolbar=0&view=Fit&page=N` and screenshotted) on A4, A4 with wide margins, A5, A6, 6×9 in, Letter, Legal, 7.5×15 in, 18.5×27 cm and 15×21 cm, with Latin and Bangla text; the sheet is built in a page that has DM Sans loaded (as the app does) and printed from a separate document with no `@font-face` (as the frame does). Every new assertion was broken once in a copy and went red (19 print rules, 7 guard decisions, 8 for the fit rule of the glue). **Not run:** the browser suite (`e2e/`, Docker was not running), a real printer or print dialog, Firefox / Safari, and the physician's own printer driver. The foot-repeat limit above is Chromium's; another browser may differ.
- **Known limits, left as they are (also in `audit/printing.md`).** (1) A second page carries no patient name — the header and patient block print once; a loose page 2 is unidentified. A product decision (repeat the block in the table head?), not made here. (2) On a very narrow page (under about 5 in printable) the clinical column is narrower than a long heading ("CHIEF COMPLAINT / S"): `wordHeadroom` never goes below 1, so a word that cannot fit still breaks. (3) The patient block's wrapped value returns to the left under its label, not hung under the value. (4) "Consistent" here means the same RULES at every page size — the same arrangement, wrapping, baselines and foot — not the same pixels: the physician's type floors (`MID_PX`) and the measured columns stay, so a smaller page wraps more.
