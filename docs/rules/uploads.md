## At a glance

- Upload URLs minted on localhost are never stored (the dev DB is production); `upload.service.ts` refuses them.
- `backfill-image-thumbs.js` only adds `imageThumbs` keys, runs on the machine holding the files, refuses a localhost `PUBLIC_URL`, installs sharp into `scripts/.tools/` (+N more).
- `/uploads` is served `immutable, max-age=365d`, correct only because every upload gets a fresh UUID name; do not add an overwrite-in-place upload path without removing this first.
- `uploadImage` refuses (503, before `writeFileSync`) a localhost `PUBLIC_URL` unless `ALLOW_LOCALHOST_UPLOAD_URLS=true` exactly; never inferred (+1 more: repair script).
- `upload.service.ts#sniff` is the one format gate, by BYTES; the stored extension comes from content, never filename; SVG and PDF stay refused; client copy: edit one, edit both (+N more).
- CORS must be registered BEFORE `useStaticAssets` in `main.ts`, or `/uploads` files go out with no `Access-Control-Allow-Origin`.
- Uploads are files under `uploads/`, never base64 in the DB; `server/.gitignore` must anchor `/uploads/` with the leading slash, or `src/uploads/` goes untracked.
- multer is lifted to 2.4 by an `overrides` entry and `POST /uploads/image` takes ONE file and no text field (`limits.fields: 0`); drop the override only with a Nest upgrade (+N more).
- The upload size limit is 8 MB on purpose (HEIC/GIF originals are sent uncompressed); the hardening that matters is the magic-byte check.
- Image formats: ONE table, `lib/imageFormats.ts`, read by the BYTES; accepted JPEG, PNG, GIF, BMP, WEBP, AVIF, HEIC/HEIF, TIFF
- Image detection is by content (`detectImageKind`, first 32 bytes), not by name or MIME; filename and `file.type` are only a fallback when the read fails
- HEIC and TIFF are CONVERTED to JPEG before upload (`lib/decodeImage.ts`), the converters behind a dynamic `import()`
- A failed image conversion THROWS and never falls back to the original (an unviewable file in a patient's record); the error names the file and tells the doctor what to do
- `IMAGE_ACCEPT` is the `accept` attribute everywhere — `image/*` alone is NOT enough (Windows greys out `.heic` / `.tif`)
- SVG is refused and must stay refused (it carries script) — a security boundary; `imageUrlIsRenderable` excludes it
- The server mirrors the image-format table (`upload.service.ts#sniff`) and the two test files share signature literals — edit one, edit both
- Known limit — Known limit: a multi-page TIFF converts its FIRST page only (`tiffPageCount` lets a caller warn); do not silently drop pages 2..n of a report
- Image viewer at fit (`LIGHTBOX_CSS`): the whole page is on screen and nothing is drawn over it; to look without storing a file, use a `data:` URL in the throwaway test database (+1 more)
- One gallery, one viewer: zoom RESETS on every image change; failed tile gets one silent retry, state keyed by URL; thumbnails in a side map, never folded into the image arrays (+3 more)
- `ImageGallery`: a file dropped on a tile uploads ONCE (`stopPropagation`); batch uploads use `Promise.allSettled`, not `Promise.all`

# The rules, in full

## Patterns We Do Not Use

_From the root `CLAUDE.md`._

- We do not store upload URLs minted on localhost. The dev DB is production; `upload.service.ts` refuses them.

## Gotchas

_From `server/CLAUDE.md`._

- **Backfilling old thumbnails: `node scripts/backfill-image-thumbs.js [--dry-run] [--limit N]`** (2026-09-07). Generates the 400px copies for gallery images filed before `imageThumbs` existed, with sharp, at the same size and quality the browser uses (400px long side, JPEG q80 — keep it in step with `client/src/lib/imageThumbs.ts`). Four things about it are deliberate: it **only ever adds keys** to the display-only map and never touches `prescriptionImages` / `reportImages`; it **must run on the machine that holds the files** (the DB is shared, `uploads/` is not — a laptop run skips the 178 production images and finds only its own), and it **refuses to write when `PUBLIC_URL` is localhost** because that run would put unreachable thumbnail URLs into the doctors' real records; it installs sharp into **`scripts/.tools/`** rather than `server/node_modules`, since a plain `npm install sharp` here reported *"added 10 packages, removed 4, changed 64"* — the live API's dependency tree moving to add a resizer — and touching `package-lock.json` is what blocked a deploy on 2026-07-20; and it merges under a `FOR UPDATE` lock so a doctor adding an image mid-run is not silently overwritten. It does **not** cover the ward's analogue order sheets: that column is written through per-page routes with their own soft-delete and audit trail, and a script doing read-modify-write on it could clobber a round in progress.
- **`/uploads` is served `immutable, max-age=365d` (2026-09-07), and that is correctness, not speed.** express.static's default is `Cache-Control: public, max-age=0`, which caches the bytes but makes the browser **revalidate every one of them on every use**. A patient records page carries dozens of images (48 on a real record), `api.muqsithealthsystem.com` negotiates **no HTTP/2** (verified: no ALPN), so those revalidations queue six at a time behind the app's own API calls and the SSE mirror stream — every tile sat blank until its round trip returned, and one request dropped on a clinic connection left it blank until the whole page was reloaded. That was the reported "images are broken until I reload". `immutable` is a fact here, not a hope: every upload is written under a fresh `randomUUID()` name and nothing in the app rewrites one, so a changed image is always a new URL and a stale cache entry cannot show a doctor the wrong page. **Do not add an overwrite-in-place upload path without removing this first.** The client's other half is the failed-tile retry in `ImageGallery` (`client/CLAUDE.md`).
- **⚕️ An upload URL is ABSOLUTE and carries the environment that minted it — so a localhost one is REFUSED (2026-09-20).** `upload.service.ts` stamps `${PUBLIC_URL}/uploads/<uuid>` into the patient's record at upload time. On a laptop that is `http://localhost:4000`, and **the database is the live one** (dev tunnels to it), so every image uploaded while working locally landed in a doctor's real record as an address no other machine can open: the live site showed "Did not load" and the console read `net::ERR_CONNECTION_REFUSED`. It hid for months because it looks perfect on the machine that created it, and it reached further than the two galleries — the scan found **274 files across `ActivityLog.imageUrl` (266 rows), `Patient.prescriptionImages`, `reportImages`, `imageThumbs` and `pictureUrl`**. `uploadImage` now throws `503` **before `writeFileSync`** (a refused upload must not leave an orphan on disk) whenever the origin resolves to localhost/127.0.0.1/::1/0.0.0.0, unless `ALLOW_LOCALHOST_UPLOAD_URLS=true`. That flag is opt-in and **never inferred**: the tunnel makes the production database look like `localhost:5432`, so the `DATABASE_URL` host cannot tell a local database from the live one. Anything but the exact string `true` fails closed. Pinned in `upload.service.spec.ts`.
  - **Repair, never hand-edit: `node scripts/repair-localhost-image-urls.js [--scan|--stage <dir>|--apply --target <origin>]`.** It finds the URLs by asking `information_schema` which text/JSON column actually holds one, rather than listing models by hand — that is how the 266 activity-feed rows were found at all. Three rules are safety, not style: it **HEAD-checks every filename at the target first and rewrites only a live 200** (a broken link a doctor can report beats a rewritten one that 404s silently); it changes **only the host prefix** of a matched URL, never the filename, array order or JSON shape; and each column is one **atomic UPDATE**, so a doctor saving the same row mid-run cannot lose their write to a read-modify-write. Idempotent — a repaired URL no longer matches. **Order matters: the files must be copied to the serving machine BEFORE `--apply`**, or verification refuses everything and nothing is written (`--stage` collects them for `scp`).
- **⚕️ ONE format table, and it reads the BYTES (2026-09-20).** `upload.service.ts#sniff` is the single gate deciding what may be stored: **JPEG, PNG, GIF, BMP, WEBP, AVIF, HEIC/HEIF, TIFF**. Three things changed and each fixed a real rejection or a real unviewable file:
  - **TIFF was refused outright.** Most document scanners produce it, so a doctor picking their own scan was told "File is not a valid JPEG, PNG or WEBP image". Now accepted.
  - **The stored EXTENSION now comes from the content, never the filename.** It used to prefer the uploaded name and fall back to the MIME subtype, so HEIC bytes were saved as `.jpg` whenever the browser sent `application/octet-stream` (routine on Windows) — served as `image/jpeg` and undrawable by anything. The extension decides the `Content-Type` express.static serves, so it has to describe the bytes.
  - **The multer MIME filter is gone**, deliberately. It refused anything whose `Content-Type` did not start with `image/`, which threw away real HEIC and TIFF uploads. The header is caller-supplied and was never evidence; an empty filter plus the magic-byte check is strictly stronger than a trusted-header filter plus the same check. Five HEIF brands a real iPhone emits (`hevx`, `heim`, `heis`, `hevm`, `hevs`) were also missing and read to the doctor as a corrupt photo.
  - **SVG stays refused, permanently.** It is a script-bearing document and this app renders stored images inline — that is a security boundary, not a format gap. PDF is refused too (it is not an image; the galleries render `<img>`).
  - The rejection message now names every accepted format. It used to say "JPEG, PNG or WEBP" while the code also took GIF, BMP, AVIF and HEIC, sending doctors to convert files that would have been accepted.
  - The client mirrors this table in `client/src/lib/imageFormats.ts` and converts HEIC/TIFF to JPEG **before** upload, so one arriving here is a browser that could not. The two copies are pinned by tests sharing the same signature literals (`upload.service.spec.ts` ⇄ `imageFormats.test.ts`) — **edit one, edit both.**
- **CORS is registered BEFORE `useStaticAssets` in `main.ts` (2026-09-24), and the order is load-bearing.** express.static answers a file itself and never calls `next()`, so with CORS registered after it every real `/uploads` file went out with no `Access-Control-Allow-Origin` (only 404s had one). The galleries' Download PDF reads the image bytes with `fetch`, which the browser refuses cross-origin without it. Only the `CORS_ORIGIN` list is allowed; `<img>` loading is unaffected.
- Uploaded files are on-disk under `uploads/` (served at `/uploads/<file>`) — hosted URLs, never base64 into the DB. `server/.gitignore` anchors this as `/uploads/`: an unanchored `uploads/` **also matched `src/uploads/`**, the upload module, so a new file added there was silently untracked and never deployed. Keep the leading slash.
- **⚠️ multer is lifted to 2.4 under Nest 10 by an `overrides` entry in `package.json` (2026-10-16), and the public upload route takes ONE file and no text field.** `@nestjs/platform-express` 10 pins multer 2.0.2, which carries eight denial-of-service advisories fixed in 2.3.0 (GHSA-wc9g-mqfw-jrwm, GHSA-535w-7cp7-47q4, GHSA-72gw-mp4g-v24j, …) — on `POST /uploads/image`, which anyone on the internet can reach. Three things came with it, each held in `test/uploads.int-spec.ts`, the first spec to send a real multipart request through the route:
  - **Nest 10 maps multer's errors by their MESSAGE** (`multer.utils.js#transformException`), and multer 2.4 reworded "Unexpected field" and raises codes Nest 10 does not know (`INVALID_FIELD_NAME`, `LIMIT_FIELD_NESTING`, …): unmapped, a file under the wrong field name was a 500 logged as a server fault. `uploads/multer-error.filter.ts` answers whatever Nest leaves by multer's stable CODE — 413 for a file over the limit, 400 otherwise.
  - **`limits.fields: 0`.** The one caller (`client/src/lib/api.ts#uploadImage`) sends a single part, the file. The advisories ride in text fields' NAMES; with no text field accepted, such a name is refused before it is parsed. A new caller that needs a field must widen this on purpose.
  - **Drop the override when Nest is upgraded** to a platform-express that ships a fixed multer. `uploads/multer-version.spec.ts` fails if the override is lost and multer goes back below 2.4.
- The upload size limit is **8 MB on purpose**. `compressImage()` on the client returns the ORIGINAL file whenever `createImageBitmap` throws (HEIC on most desktop browsers), for GIFs, and whenever the re-encode isn't smaller — and `upload.service.ts#checkMagic` accepts `heic`/`heif`/`avif` deliberately. iPhone report photos are routinely 3-8 MB; a tighter ceiling rejects real uploads. The hardening that matters is the magic-byte check, not the last few MB.

## UI conventions

_From `client/CLAUDE.md`._

- **⚕️ Image formats: ONE table, `lib/imageFormats.ts`, and it reads the BYTES (2026-09-20).** Accepted: **JPEG, PNG, GIF, BMP, WEBP, AVIF, HEIC/HEIF, TIFF**. Before this there were **five disagreeing allowlists** — `compressImage`, the IPD panel's `ACCEPTED_TYPES`, the server's multer MIME filter, the server's magic-byte check, and `PatientChat.isImageUrl` — so a format could pass one gate and fail another and *which screen broke depended on which list it hit*: the ward's order-sheet panel refused GIF and BMP that the server stored, and the chat rendered SVG (never storable) but not AVIF (stored every day). Rules:
  - **Detection is by content, not by name or MIME.** `detectImageKind` sniffs the first 32 bytes; the filename and `file.type` are only a fallback for when the read fails. A file's declared MIME is the least reliable signal here — iPhone photos routinely arrive as `application/octet-stream`, and HEIC bytes under a `.jpg` name are ordinary.
  - **HEIC and TIFF are CONVERTED to JPEG before upload** (`lib/decodeImage.ts`, `heic2any` + `utif`, both behind a dynamic `import()` so an ordinary JPEG upload downloads neither — verified in a production build: heic2any's 1.3 MB is its own chunk and First Load JS is unchanged). No mainstream desktop browser can draw either, so storing them as they arrived filed a document nobody could open.
  - **A failed conversion THROWS; it never falls back to the original.** That asymmetry is the safety rule: for a format the browser can read, handing the original back is fine (it still renders); for one it cannot, the fallback is an unviewable file in a patient's record. `compressImage`'s old blanket `catch { return file }` is exactly how that happened. The error names the file and tells the doctor what to do.
  - **`IMAGE_ACCEPT` is the `accept` attribute everywhere — `image/*` alone is NOT enough.** Windows has no MIME registration for `.heic` or `.tif` on a stock install, so a picker filtered on `image/*` greys the doctor's own scan out and they cannot select it at all.
  - **SVG is refused and must stay refused** — it carries script and stored images render inline. That is a security boundary, not a gap. `imageUrlIsRenderable` deliberately excludes it.
  - The server mirrors the same table (`server/src/uploads/upload.service.ts#sniff`), and the two test files share the same signature literals (`imageFormats.test.ts` ⇄ `upload.service.spec.ts`) — **edit one, edit both.**
  - **Known limit:** a multi-page TIFF converts its FIRST page only (`tiffPageCount` exists so a caller can warn by name). Multi-page scans need a deliberate design — do not silently drop pages 2..n of a report.
- **⚕️ In the image viewer, at fit, the whole page is on the screen and nothing is drawn over it (2026-10-09).** `LIGHTBOX_CSS` in `ImageLightbox.tsx` holds the rule. The picture's limits are the veil's own padded box, with 64px kept below for the zoom bar and 48px each side for the arrows — before this a portrait page at 1280×720 stood from −3px to 723px with its last line under the bar. **On a phone** a page is nearly as wide as the screen, so the two arrows used to sit ON the sheet (a white disc over each margin of a handwritten page) and the zoom bar ran off both edges with its − button: there the arrows come down beside the bar, the picture takes the width, and the bar keeps the page counter and loses the hint about keys and a wheel. A drag moves the page by exactly the pointer's travel (see the page-zoom rule above). On the narrowest phones (≤340px) the arrows are a size smaller and the bar closes up, or the three met. **To look at the viewer without storing a file:** the sandbox API DOES store uploads — into `server/uploads/` on this machine, where a hand-run "Save & print" also files its snapshot (delete what it wrote; only the Playwright guard answers 503) — so put a `data:image/svg+xml;base64,…` URL into a made-up patient's `reportImages` in the throwaway test database, look, and set it back to `'{}'`.
- **Images: one gallery, one viewer.** `components/common/ImageGallery.tsx` (upload, OS-file drag & drop, Edit-mode multi-remove, optional drag-reorder, optional per-item label, `thumbUrl` falling back to `url`, `loading="lazy"`) and `components/common/ImageLightbox.tsx` (←/→/Esc, `n / total`, opt-in `wrap`, and a **zoom**: − / % / ＋ buttons, `+ − 0` keys, wheel, double-click, drag to pan, up to 6×). Extracted 2026-08-26 from `PatientRecordsView`, where the gallery was a local component with two call sites and the viewer existed twice over. Three callers now: the patient's prescription and report galleries, the investigation findings field, and the ward's analogue order sheet. `ImageGallery.test.tsx` and `ImageLightbox.test.tsx` are the only jsdom tests in the repo and opt in with a `// @vitest-environment jsdom` docblock rather than switching the whole suite (there is no `jest-dom`, so assert on plain DOM properties — `btn.disabled`, `el.getAttribute(…)` — not `toBeDisabled()`). **The viewer's zoom RESETS on every image change (2026-08-30)**, and that is the clinical rule, not a nicety: carrying page 1's magnified corner onto page 2 would show the doctor a crop of a document they have never seen whole. It starts at fit, so nothing changes until they ask for it. **Tile size and crop are opt-in per caller** — `size="lg"` (portrait 270×370, landscape 370×270) and `fit="contain"`; the default stays the small cropped tile every existing gallery has. **A tile that failed to load says so, and offers a way back (2026-09-07).** The `<img>` had no `onError` at all, so a dropped request left a permanently blank square — indistinguishable, on a records screen, from a patient who has no such sheet, and unrecoverable except by reloading the whole page. Now one **silent** automatic retry (a dropped request usually comes back on the second ask), then the tile shows ⚠ "Did not load · ↻ Try again" and stops — hammering the server behind the doctor's back is not a fix, and a second failure is worth their attention. Two details are load-bearing: the retry carries a `?mhsRetry=N` parameter **and** a changed React `key`, because without the parameter the browser answers with the cached failure and without the key React keeps the failed element; and the state is keyed by the **image URL, never by `item.id`**, since `id` used to be the array index for the two patient galleries (it is the URL since 2026-09-29, and the selection is cleared whenever the set of URLs changes, so "Remove selected" can never name a different image after an upload or a patient switch) — keying by position would move one image's failure onto whichever image later took that slot. The stored record never sees the parameter (`onOpen` hands the viewer the clean URL). The server's half of this is the `immutable` cache on `/uploads` (`server/CLAUDE.md`), which is what stops 48 revalidation round trips on every visit. **New images in both patient galleries now carry a 400px copy (2026-09-07).** A 150×110 tile was pulling the full 1185×1600 original — 48 of them on a real record. The small copy lives in **`Patient.imageThumbs`, a SIDE MAP keyed by the full URL** (`lib/imageThumbs.ts`, `manual-patient-image-thumbs.sql`), never folded into `prescriptionImages` / `reportImages`: those arrays ARE the record — their order is the doctor's own order, and print, snapshot and mirror all read them as plain URL strings — so turning them into objects would rewrite every existing gallery for a display optimisation. **Nothing was migrated and nothing needs to be:** a URL with no entry falls back to the full image, which is exactly how every image stored before this reads. It is a `Json` column, so `safeThumbMap` is total and `imageThumbs.test.ts` throws garbage at it. Three rules: the map travels in the **same PATCH as the array it belongs to** (`saveRxImages(next, addedThumbs)` / `saveReportImages` / `saveRxSnapshot(url, key, thumbUrl)`) so the two can never describe different sets; the thumbnail is **best-effort and uploaded after** the full image, because the full-resolution image is the record and a thumbnail that fails must never cost it; and **orphaned keys are ignored, never purged** — deciding from a display map which images no longer exist is not worth a tidier column. `THUMB_MAX_DIM` is defined once in `lib/imageThumbs.ts` and re-exported by `lib/ipdAnalogue.ts`. Images filed **before** this keep pulling the full original — a backfill would need server-side resizing (a new dependency) and was deliberately not taken.

Two rules `ImageGallery.test.tsx` pins: a file dropped ON a tile uploads ONCE (the drop bubbles to the container, which carries the same handler — without `stopPropagation` every dragged page was filed twice), and batch uploads use `Promise.allSettled` (the old `Promise.all` discarded five successful uploads because the sixth timed out, and said only "Upload failed").
