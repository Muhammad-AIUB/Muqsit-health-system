## At a glance

- The line under the Save buttons holds its KIND with its words (`SaveNotice`); a failed or refused save is a `tell()` box (`whyNotSaved`); a throw after the prescription was created is never called "not saved".
- "Is this medicine on the pad already?" is asked ONE way: `sameMedicine` / `MedicineMap` (`medicineKey.ts`) and `instructionKey`; it converts no unit, never sets aside a strength, never takes two forms for one.
- No way onto the ℞ pad that no screen uses is kept: dead code that writes clinical content is removed, not left for a later change to wire back in.
- A `>>>` line never falls onto the medicine above: a medicine with `>>>` lines keeps its name, EVERY edit that changes position keeps the rule (`rxItemsFromRows`), and the pad's rows are held with the visit (`rxPadHeld`).
- What was sent twice is never filed as two, and "not saved" is never said of what may be on the record: the server answers a repeat with the one on record (`repeat.ts`); Save & print's request is built ONCE (`sendAgain.ts`).
- Two copies of the same state are never kept in step with one effect each way: the ℞ pad's rows and `rxItems` go through ONE effect (`usePadSync.ts`); where the pad moved, the pad's edit wins.
- Monthly cost box: priced from the medicine chart by `sameMedicine` (two strengths are two prices); a price is never guessed and what is not priced is said, never summed silently (+4 more)
- `RxItem.generic` is set only when the line was chosen from the medicines dropdown and is cleared as soon as the drug text is edited by hand, so a safety rule never fires on the wrong drug.
- ⚕️ The ℞ pad is ALWAYS English; BAN/EN changes only the PRINTOUT (dose/food/duration in Bangla via `lib/rxLanguage.ts#rxForPrint`, physician's table verbatim; a decimal point never the dari); a NAME never converted; EN prints as entered; server copy of the table still reads Bangla cells: edit both
- ℞ pad rows and `rxItems` are kept in step by ONE effect (`lib/usePadSync.ts`), the pad's edit winning; a test of effect-synced state must land two edits in one render — `act()` alone never does.
- Save & print takes ONE save at a time: `handleSave` holds a synchronous `savingRef`; `savePrescription` is not re-entrant and does not serialise — any new caller owes the same guard.
- ℞ pad `MedicinePad`: only the brand NAME is bold, via an `aria-hidden` overlay on lines not typed in; overlay content must stay ONE flex item with `white-space: pre`; notes never bolded (+1 more)
- OPD ℞ line reorder (`reorderable`): what moves is a BLOCK (medicine with its `>>>` lines); drag is live pointer events, never native drag-and-drop; only the order changes, no field (+3 more)
- OPD ℞ pad and print: notes and medicines are ONE numbered list, but a note stays a NOTE (no dose, mirror, alerts or habits); in print a note advances `rxNo` but never `rxRowNo`
- OPD ℞ pad shows ten medicines then scrolls (`maxHeight`); the min height must stay below the max at every viewport height, or the scroll silently dies
- ℞ medicine dropdown is `position: fixed` via `anchorDropdown`; convert the measured rect with `zoomScale` / `toLayoutPx`; never put `transform`/`filter`/`will-change` on an ancestor of the pad
- ℞ pad medicine column has a 190px floor (`MedicinePad.tsx`); do not remove the floor to "save a line" — a pad too narrow wraps the doses to the next line
- Save buttons: a failed save is a `tell()` box, never the green line; a throw after the prescription was created is never "not saved"; a lost answer is re-sent AS IT IS (+4 more)
- `create()` answers a request identical to the latest Rx for the patient within 30 min with that one; never narrow comparison, window or lock; a new DTO field needs a line in `repeat.ts` (+1 more).
- The habit write is awaited, in try/catch, AFTER `prescription.create` returns — it must never fail or roll back a prescription; `prescriptions.service.spec.ts` is the regression spec for `create()`.

Filed with the entry they belong to, in another file:

- A `>>>` taper never leaves its medicine: written only under a named medicine directly above; a tapered medicine keeps its name; unwritable lines are held, red, and Save refuses (+4 more) → [`drug-history.md`](drug-history.md)
- Save & print: modal opens at once in "Saving…"; save runs before anything that can throw; a failed save CLOSES the modal — never a printable sheet for a visit not on record (+1 more) → [`printing.md`](printing.md)

# The rules, in full

## Patterns We Do Not Use

_From the root `CLAUDE.md`._

- We do not draw every message of one line in one colour, or say on a line that goes that a save failed. The line under the Save buttons was `C.ok` green for all it ever said — "Save failed: …", "Draft NOT saved. Is the API running?" and the refusal of a pad it cannot write among them — and it went after three seconds, under the print sheet after Save & print (release review, 18/10/2026). It holds its KIND with its words (`SaveNotice`); a save that failed, or was refused for anything but an empty form, is a `tell()` box in the doctor's words (`whyNotSaved`, `client/CLAUDE.md`); and a throw after the prescription was created is never called "not saved", and does not stop the visit being marked complete — either way the doctor would file it twice.

- We do not ask "is this medicine on the pad already?" in two ways. Drug history's "Move to Rx" compared the label letter for letter; the "Add Bulk Medicine" box, written later, compared the medicine as the app does elsewhere. The same entry was a line written twice from one screen and skipped from the other: `tab napa 500mg`, typed at an earlier visit, went on the pad beside `Tablet. Napa 500 mg` at the same dose (in production until the release that carried this). Both ask `sameMedicine` / `MedicineMap` (`client/src/lib/medicineKey.ts`) — how a label was typed, set aside: spaces, capitals, `Tab` for `Tablet.`, a decimal typed `.5`, and since the physician's decision of the same day a label typed with no dosage form as any form of that name and strength; it converts no unit, never sets aside a strength, and never takes two forms for one — and both compare the dose, food and duration by `instructionKey` (capitals and spaces only). For both, a NOTE that reads as the medicine is a line of it with nothing in those three and no tapering lines (an entry whose doses are in its tapering lines was skipped against such a note, and the regimen never reached the pad — review, before release), and a tapering line is not a first line. (How each reads the pad is still its own code, written to that one rule.) And a key that sets typing aside is tried on what typing does to a NUMBER: the first one read the point of `.5 mg` as the full stop that ends a dosage form, and took 0.5 mg and 5 mg for one medicine (review, before release). A rule given to a second screen is given as the same function, not as the same idea written again (2026-10-14).
- We do not keep a way onto the ℞ pad that no screen uses. The legacy drug picker and the static "templates" could not be opened from any screen, and they still held code that wrote a medicine with `1+0+1 · After meal · 5 days` beside it, and whole regimens kept in the app (amoxicillin 1+1+1 for 7 days), onto the pad. The templates had no caller at all; the picker's open flag still rode the device mirror, which no build had set since 2026-06-18. Dead code that writes clinical content is removed, not left for a later change to wire back in (2026-10-14).

- We do not let a line that lost its medicine fall onto the medicine above. A `>>>` line belongs to the line directly above it, by position alone — so when that line's NAME was cleared, the pad's reading dropped the nameless line and kept its tapers, and from there everything read them as the previous medicine's: Save & print filled that medicine's name in, the sheet printed the dose under it, Drug history recorded it (physician, 18/10/2026: "dangerous bug"; older than the release that found it). A rule that hangs on position is checked where the position is still known (`rxItemsFromRows`) — and the state is stopped where it is MADE: a medicine with `>>>` lines keeps its name. The first fix only refused at Save, and its review found the same danger by another door (× tidied away the blank line and moved the next `>>>` line under the medicine above), typed vitals moved into a log before a refusal, and one patient's flagged lines left on the next one's pad. Refusing at the end is the second line of defence, not the first. And a rule that hangs on position holds only if EVERY edit that changes position keeps it: the third review found two more doors for a `>>>` line saved before the fix with no medicine above it (× tidying away a blank note above it, ▲ putting a medicine above it at the top), and the kept name put back by row index onto another medicine's `>>>` line after the rows moved under the caret. Such a line is now drawn as a line of its own (`rowsFromRxItems`), and the name goes back only onto the very rows it came from. And such a line is not lost either: since 19/10/2026 the pad's rows are held with the visit while one is on it (`rxPadHeld`, `client/src/lib/rxPadHold.ts`) — the draft, `incompleteRx`, the device mirror — drawn back only where they still fit the prescription's items; where one no longer fits, the pad says what went (`client/CLAUDE.md`, which also says where it cannot). Keeping it in `rxItems` instead was weighed and not done: every reader of `rxItems` would then need a check of its own, and the printed sheet reads a nameless line as a `>>>` line.

- We do not file what was sent twice as two, and we do not say "not saved" of what may be on the record. A save whose answer was lost on the way back read to the doctor as "not saved", and the next press stored the visit again; the server is the only one that can tell, and it answers the same prescription sent again within 30 minutes with the one on record (`server/src/prescriptions/repeat.ts`), and an OPD add pressed again with the visit already waiting and not yet printed. What "the same" is, is every field the request can carry: a test reads the DTOs and fails on a field the comparison leaves out, since that field's value would be lost. And "not saved" said of a stored prescription left the visit "Incomplete" with a prescription on the record, and a word changed before the next press filed it twice (20/10/2026): Save & print's request is built ONCE and sent again AS IT IS, quietly, while its answer is lost (`client/src/lib/sendAgain.ts`); where no answer comes, the box says it MAY not have been saved, and that pressed again unchanged within half an hour it will not be filed twice. Only a request the server answers once however often it is sent is ever sent again by itself.

- We do not keep two copies of the same state in step with one effect each way. The OPD ℞ pad's rows and the prescription's `rxItems` each had their own effect: pad → `rxItems`, and `rxItems` → pad for changes made elsewhere. When two key presses land in ONE render, the first press's copy reaches `rxItems` in the same render as the second press's rows. The `rxItems` → pad effect took that older copy for a change made elsewhere and put it back. The pad → `rxItems` effect then wrote the newer rows again, and the two kept overwriting each other until React stopped the screen. Typing `b`, `m` in a food cell in BAN did it every time in the browser pass (2026-10-15, before release; the unit tests had passed, because `act()` never lands two presses in one render). Now it is one effect (`client/src/lib/usePadSync.ts`): in a render where the pad moved, the pad's edit is the newest and wins. Its test holds the copy back so that it lands in the same render as the next edit.

## ⚕️ Clinical-accuracy rules specific to the client

_From `client/CLAUDE.md`._

- **Medicine search hits the server** (`/medicines/search`, raw `medicines` table). **⚕️ The "Total monthly approximate cost" box in the patient header is priced from that table — "the medicine chart" — since 2026-10-14** (physician's decision: "take from medicine chart — but remember like Sergel 20 and Sergel 40 mg is not same"; `components/prescription/MonthlyCost.tsx`, `hooks/useMonthlyCost.ts`, `lib/monthlyCost.ts`, `POST /medicines/by-brand`). It read an 18-item list kept in the app (`src/data/drugs.ts`, removed), by exact name, which no medicine picked from the chart was on: for a real prescription it showed `৳0.0`. Rules, each held in `monthlyCost.test.ts`: the chart's row is a line's medicine by `sameMedicine`, form and strength included, so two strengths are two prices, and a medicine is priced only where every row it matches gives ONE unit price (a label typed without its form matches every form of that name and strength) and no pack of its brand stored with no form or strength — as the import stores a brand's second pack — gives another; only a `Unit Price: ৳ N` of a tablet, capsule or suppository is a price, read whole (`unitPrice` — each of the 15,540 rows of the workbooks the chart was imported from that begins `Unit Price` is read by it; the production table was not read) — a bottle, vial or tube is priced by the pack, and what one dose of it costs is not guessed; the dose must be counts joined by `+` (`1+0+1`, `1/2+0+1/2`), the duration days, weeks or months (English or Bangla) or Continue, and the food cell blank or saying only WHEN beside a meal (`After meal`, `2 hr before meal` — what `parseFood` writes): `once a week` or `alternate day` there may say how often, and `1+0+0` once a week is four tablets a month, not thirty (review, before release); a month is 30 days — a shorter course for its days, a longer one and Continue for 30, tapering lines in order after their medicine. **What is not priced is said, never summed silently:** the box reads `৳8,350.0 · 1 not priced`, and pressing the count names each medicine with its reason (`tell()`); with nothing priced it shows `৳—`; a chart that could not be reached shows no total, only `Prices not loaded` (asked with `networkMode: "always"`, two quiet retries, an answer that is not the chart thrown). A note is no medicine's line and is never priced or counted. The chart is asked once per pad for the first word of each brand (`brandWordsOf`), 400 ms after typing stops, and kept ten minutes. **The legacy drug picker and the static "templates" were removed on 2026-10-14:** no screen could open either, and both wrote what no doctor wrote — the picker any medicine of the 18-item list with `1+0+1 · After meal · 5 days` beside it (`addDrug`), the templates whole regimens kept in the app (`templateRx`, `loadTemplate`: `Cap. Amoxicillin 500mg` 1+1+1 for 7 days among them). The one way the picker could still have opened was a snapshot mirrored from another device carrying `showDrugPicker: true` (no build since 2026-06-18 sends one; the templates had no caller at all); an older build may still send that key and `drugSearch`, and nothing reads them. Pinned in `MuqsitContext.test.tsx`.

- **`RxItem.generic`** is set only when the line was chosen from the medicines dropdown; `drug` holds the brand label (`"Tablet. Entaliv 0.5mg"`). It is **cleared as soon as the doctor edits the drug text by hand** (`MedicinePad.tsx`) — a stale generic pointing at a different medicine would let a safety rule fire on the wrong drug. Additive: prescriptions and drafts saved before it simply lack the field.

## Editor lifecycle (easy to break — know it)

_From `client/CLAUDE.md`._

- **Save & print takes ONE save at a time (2026-08-23).** It had no in-flight guard, so a double-press ran the whole flow twice and recorded one consultation as **two `Prescription` rows** — measured in the running app: two clicks 120ms apart produced two rows 321ms apart. `handleSave` now holds a synchronous `savingRef` and returns immediately on a second click (no second window, no second row), with `runSave` carrying the old body; the `saving` state beside it only disables the two Save buttons and shows "Saving…", because doctors press twice when nothing appears to have happened. "Save to complete later" is disabled for the same window so a draft cannot interleave with the visit being completed. (Historic note: `runSave` was split out so everything up to its first `await` ran inside the click, which was what kept the old `window.open` out of the pop-up blocker. The sheet is in-app since 2026-08-26 and no longer needs the gesture; the split stays because the guard reads better with it.) `savePrescription` itself is still not re-entrant and does not serialise — the guard is the caller's, and any new caller owes the same.

## UI conventions

_From `client/CLAUDE.md`._

- **The ℞ pad sets the brand NAME in bold, and nothing else** (`MedicinePad`, medicine column, 2026-08-23) — the same emphasis the printed sheet carries, via the same `splitDrugLabel`. An `<input>` can only hold ONE font weight, so the line the doctor is **not** typing in is covered by a read-only `aria-hidden` copy that can, with the input's own text turned transparent underneath. On focus the overlay goes and the real input shows through unchanged: bold glyphs are wider than regular, and an input places its caret using its own single weight, so leaving the overlay up while typing would drift the caret away from the letters. Two traps if you touch it: the overlay's content must stay ONE flex item (a bare text node beside the `<b>` becomes its own flex item and its outer spaces collapse — `Tablet.Napa500 mg`), and `white-space: pre` is what keeps the spacing identical to the input's. The input itself is untouched — still mounted, still holding `drugRefs[idx]`, so focus, Enter-navigation, the autocomplete dropdown and device mirroring all behave as before. Verified in the browser: programmatic `focus()` drops the overlay, editing re-splits the label on blur. Free-typed note lines are not medicines and are never split or bolded. **Known cosmetic limit:** a click lands the caret by the input's regular-weight metrics while the eye aims at the wider bold name, so clicking into a name can be under half a character off.
- **℞ lines can be moved (physician's request, 2026-09-23), OPD pad only** (`MedicinePad`'s opt-in `reorderable`, passed by `RightColumn`). Two ways: **drag the line by its serial number** (it turns into a ⠿ grip on hover), or **▲ / ▼ beside the ✕ while ✎ Edit is on**. `lib/rxRowMove.ts` owns the rules and `rxRowMove.test.ts` + `MedicinePad.reorder.test.tsx` pin them: **what moves is a BLOCK** — a medicine with its `>>>` tapering lines — because a taper row has no drug name and moved alone it would hand its dose to whichever medicine it landed under; a note is a block of one;
  - **The drag is LIVE, pointer events, one step per neighbour middle crossed — never native drag-and-drop.** The first version (same day) used HTML5 DnD and chose the landing spot at release from React state set during `dragover`; a quick release read the previous render's value and fell back to "before", so dragging UP went one step too far and DOWN one step short (measured in the browser: 2 steps and 0 steps for a one-row move). Now nothing is decided at release: `dragStep` swaps the block with one neighbour each time the pointer passes that neighbour's middle, the same rule both ways. **Row heights are measured once at pickup and carried through the swaps**, and positions are computed from them — reading positions off the DOM meant waiting for a render between steps, and a fast three-row sweep (which a browser reports as ~2 pointer events) moved two places. The move/up/cancel handlers are attached on every row of an opted-in pad, not just grips: rows are keyed by position, so after a swap the element holding pointer capture can be a taper row. `touch-action: none` on the grip makes it work on a tablet too.
  - Rules, continued: the trailing "start typing" row never moves and nothing lands below it; and no field of any row is edited, only the order. The printed serial numbers and the alert-to-line indices simply follow the new order (both are derived from `rows` every render). The IPD sheet, the Drug-history pad and the template editor do not opt in.

- **⚕️ Notes and medicines are ONE numbered list on the OPD ℞ pad and its printed sheet (physician's decision, 2026-09-24).** A free-typed line that is not in the medicine database (`bed rest`, `insulin as before`, `advice : Hospitalization`) takes the next serial exactly like a medicine: `1. bed rest · 2. insulin as before · 3. Tablet. Napa …`. It is still a NOTE — one spanning italic cell on paper, no dose/food/duration, not mirrored into Drug history, not matched by the prescribing alerts, not counted by the habit learner. A taper (`>>>`) row and the empty typing line are never numbered. On screen it is `MedicinePad`'s opt-in `numberNotes`, passed by `RightColumn` only; the IPD sheet and the template editor keep medicine-only numbers. In print (`prescriptionDoc.ts`) a note advances `rxNo` but **never `rxRowNo`**, because the row-size arrays are indexed over medicine rows only. Pinned in `prescriptionDoc.test.ts` and `MedicinePad.reorder.test.tsx`; the print was checked rendered.

- **The OPD ℞ pad shows ten medicines, then scrolls** (`MedicinePad`'s `maxHeight`, physician's decision 2026-08-28). `RightColumn` passes `minHeight` `min(400px, 50vh)` (mobile `min(280px, 45vh)`) and `maxHeight` `min(448px, 62vh)`: ten medicine lines plus the trailing "start typing" line are 444px, so the pad stops growing at the eleventh medicine and scrolls instead. Measured in a real browser at 1280×720 — 10 medicines, `scrollHeight === clientHeight`; 11 medicines, it scrolls. Both bounds carry a `vh` cap so a laptop or a phone never gets a pad taller than its screen, and **the min must stay below the max at every viewport height** — `min-height` beats `max-height` in CSS, so a min that could exceed the max would silently kill the scroll. The IPD sheet, the Drug-history pad and the template editor pass no `maxHeight` and are unchanged.
  - **The medicine dropdown is `position: fixed`, anchored by `lib/dropdownAnchor.ts`.** An `overflow` ancestor clips an absolutely positioned child, so the moment the pad scrolled, the old `position: absolute; top: 100%` list would have been cut off at the pad's edge — on the one interaction that matters most. `anchorDropdown` places it from the row's measured rect: hanging below by default, **flipped above** when there is less than 160px underneath, height trimmed to the room available (never under 120px), and pulled back inside the right edge so a 92vw list stays on screen on a phone. `MedicinePad` re-measures on `scroll` (capture, so the pad's own scroll box counts) and `resize`, immediately and again on the next frame — reading the rect mid-scroll leaves the list trailing its row. **The rect is converted before it is used (2026-10-09):** `measure()` runs it and the viewport through `toLayoutPx(…, zoomScale(el))`, because a measured rect is in screen px and a fixed coordinate is in the page's own (the page-zoom rule under UI conventions). Unconverted, the list hung 12% too low and too far right, and its `92vw` cap was wider than a phone — the cap is `acMaxW` now, worked out in the same px. Verified in the browser: 2.5px under its row at 1280 wide and 2.3px at 375, left edges flush, hanging 55px past the pad's bottom and still hit-testable, flipping above when scrolled near the foot of the screen, and fully on screen at 375×812. Do not put `transform`/`filter`/`will-change` on an ancestor of the pad — any of them would make the viewport-anchored coordinates wrong and bring the clipping back.

_These stood under the bullet "Inline styles only" (now in `docs/rules/theme-and-colour.md`):_

  - **⚕️ The ℞ pad's medicine column has a 190px floor** (`MedicinePad.tsx`). Without it the name column grows from nothing while dose/food/duration start at 240px, and on a pad around 470px wide the name showed as "Tablet. Nap". A pad too narrow for both wraps the doses to the next line, as a phone always did; do not remove the floor to "save a line".

  - **⚕️ What the Save buttons say (18/10/2026).** The line under Save & print and "Save to complete later" (`savedMsg`) holds its KIND with its words (`SaveNotice` in `lib/saveNotice.ts`; drawn by `SaveNoticeLine`), never a bare string whose colour is guessed: `ok` is green (`C.ok` — "Prescription saved!", "Draft saved — you can complete it later.") and `warn` is amber (an empty form: "Add a medicine or some clinical detail before saving."). Until that day every message was drawn in the saved green — "Save failed: …", "Draft NOT saved …" and the `UNWRITABLE_PAD` refusal among them — and two ended "Is the API running?". **A save that failed, or was refused for anything but an empty form, is never that line: it is a `tell()` box** — "The prescription was not saved." / "The visit was not saved for later.", then `notSavedBody`: the reason and "Everything you wrote is still here." The line went after three to five seconds, and after Save & print it was under the print sheet. The reason (`whyNotSaved`): no answer, or a successful answer that was not JSON (a Wi-Fi sign-in page served in its place) → "Check your internet connection and try again." (such a page sent with an error status is an `ApiError`, and reads as the server's failure below); a 401 (apiFetch could not renew the session; refused, the app goes to the sign-in page and the editor with it) → "Your sign-in could not be renewed just now. If the sign-in page opens, sign in again and open this patient." — with NO "still here", which over the sign-in page would not be true; a 403 → the server's own sentence (worded for a person: the save grant, `WorkstationGuard`), but not apiFetch's stand-in "Request failed (403)" for a proxy's page; a 400 / 413 → "The server did not accept it as it is written." (a validator's words otherwise, and trying again would not help); anything else → "The server could not save it just now. Please try again in a moment." — never "Internal server error", "Unauthorized" or "Request failed (502)". The error itself goes to the console. **A prescription that IS saved while part of the record was not brought up to date with it** gets its own box (`historyNotUpdated`), naming only what failed — "The investigation history kept in the patient's record was not updated. The prescription itself is saved, with everything written on it." ## ⚠️ Rule 2c — `DoctorRxHabit` is DERIVED, and its write path is load-bearing

_From `server/CLAUDE.md`._

- **⚕️ The same prescription sent again is the one on record (19/10/2026).** A save whose answer was lost on the way back reads to the doctor as "not saved", and they press again: the visit was filed twice. **Since 20/10/2026 the doctor app leans on this rule twice:** it sends Save & print's very request again by itself while its answer is lost (`client/src/lib/sendAgain.ts`), and where no answer comes it tells the doctor that pressed again unchanged within half an hour it will not be filed twice (`MAY_BE_SAVED`, `client/src/lib/saveNotice.ts`, whose test reads `REPEAT_WINDOW_MS` here). A change that narrows the comparison, the window or the lock turns those re-sends into second prescriptions. `create()` now takes an advisory lock per doctor and patient, and answers a request identical to this doctor's LATEST prescription for the patient, from the last 30 minutes (`REPEAT_WINDOW_MS`), with that one — 201, the same shape, no second row, and nothing learned a second time. "Identical" is every field the DTO can carry and every line (`repeat.ts#sameContent`); `repeat.spec.ts` reads the DTOs' metadata and fails when a field is added without a line in `repeat.ts`, since a field left out of the comparison would make two prescriptions that differ only there one — the second one's value lost. Compared with the latest only: a third save like the first, after a different second, is new. The repeat is answered with `repeat: true` added, so the client writes the visit's audit lines once. Pinned in `test/repeat-save.int-spec.ts` (another patient, another doctor, a changed dose, a >>> line marked otherwise, 31 minutes later — each a new row; the lock by HOLDING it from the test and seeing the save wait — two copies sent at once passed with the lock taken out, review) and `repeat.spec.ts` (each line property changed in turn — a property left out of a hand-written comparison passed every test, review; the comparison is now driven by `ITEM_FIELDS`). The OPD queue does the same for an add: a patient still waiting in today's queue whose prescription is not yet printed keeps their visit (`opd.service.ts`; printed — `rxStatus: complete`, which Save & print sets without pressing Done — or Done, they are queued again: the first version handed a morning visit back in the afternoon, review), and both OPD writes take one advisory lock per doctor. A reused visit keeps its own `type` (the client sends none).
- **The write is awaited, in a try/catch, AFTER `prescription.create` returns.**
  All three parts matter and each was chosen against a specific failure:
  *outside the prescription write*, because a habit failure inside it would roll
  back a prescription the doctor believes was saved and has already printed;
  *awaited*, because every deploy restarts pm2 and a detached promise in flight
  at that moment is simply lost; *caught*, because a convenience must never fail
  the single most important write path in the product.
  `prescriptions.service.spec.ts` is a REGRESSION spec for exactly this — if you
  touch `create()`, it is the test that says whether you broke the record.
