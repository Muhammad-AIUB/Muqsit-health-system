## At a glance

- A queue's day is never found through `createdAt`: `OpdVisit.queueDate` says whose day it is; a day that has passed is refused by the SERVICE, not hidden by the screen.
- A serial's time is never shown from a schedule box that is still being typed in: times come from the SAVED schedule (`useOpdSchedule`), and a save clears only what it sent (`OpdScheduleBar`).
- OPD queue adds a patient by mobile number only (every row has a Patient record); IPD admit waits for a chosen patient; rows show serials, not tokens; one add at a time via a ref (+3 more)
- OPD queue is booked by day (past days locked); serial times only from the SAVED schedule, never the boxes; status/colour derived in `lib/opdPresence.ts`; SMS with no answer never retried (+8 more)
- OPD marked rows (`rowTone`) are drawn `C[tone][100]` with a 4px `C[tone][400]` left bar; text on toned rows darkened so every pair keeps AA in both modes (`theme/contrast.test.ts`).
- How it works — Each of a doctor's chambers has its OWN OPD list, tokens, day schedule and OPD print settings; design in `docs/decisions/2026-11-01-multi-chamber-design.md`.
- Chamber choice is `lib/chamber.ts` (`setChamber` sets `X-Chamber`, per user per practice, not mirrored); `selectWorkstation` must set the new practice's chamber in the same step as `X-Workstation`.
- How it works — "My Chamber" (`ChamberPicker.tsx`) is a plain `<select>` after the Prescription tab, in the phone and OPD headers; disabled "Chambers did not load" on failure; renders nothing when signed out.
- `ChamberSync` cancels and removes cached `["opd"]` queries on a chamber change so one chamber's list never shows under another's name; a removed chamber falls back to main with a `tell()` box.
- How it works — Chambers are pinned in `ChamberPicker.test.tsx`, `ChambersSettingsView.test.tsx`, `chamberLayout.test.ts`, `PrescriptionSettingsView.test.tsx` and `e2e/tests/chambers.spec.ts`.
- `OpdVisit.queueDate` / `position` name a visit's day and place, `OpdDaySetting` a day's schedule; apply `manual-opd-queue-date.sql` BEFORE the release is deployed.
- The OPD day is `queueDate`, never `createdAt`; old rows without it are read by `dayWhere` as their Dhaka creation day and listed after placed rows.
- A past day is locked in the SERVICE: add/move/re-time refused before any write; Done today only; `setRxStatusByPatient` marks TODAY's visit only.
- Queue order is pure (`queue-order.ts`): swap with the nearest WAITING patient, seen ones keep place; every write takes the doctor's advisory lock and `ROW_LOCK_TX`.
- The first visit added to a day saves its inherited schedule (`freezeSchedule`) so times told to patients do not move; otherwise latest earlier day's, else `DEFAULT_OPD_SCHEDULE`.
- `manual-opd-queue-date.sql` REPLACES the token-unique index with `(doctorId, queueDate, token)`; not applied to the shared database (applying it migrates production).
- OPD presence: `presentAt` is the SERVER's clock, today only; `padStage` never leaks draft text; fields listed only in `pad-stage.ts`; apply `manual-opd-presence.sql` BEFORE release (+N more).
- `ChambersService.resolve` is the ONE place deciding the chamber: foreign/removed/made-up id is 404, never a fall-back; NULL is the default; never point at profile `Chamber` rows (+N more).

# The rules, in full

## Patterns We Do Not Use

_From the root `CLAUDE.md`._

- We do not find a queue's day through `createdAt`. The OPD queue is booked by day (28/10/2026): a patient can be added today for a later day, so `createdAt` says when a row was written and `OpdVisit.queueDate` says whose day it is. "Today" read as `createdAt >= start of day` would have shown tomorrow's patients in today's queue and let Save & print mark a later booking as printed; the same index (`manual-opd-token-unique.sql`) would have refused a later day's `T-01`. A day that has passed is refused by the SERVICE, not hidden by the screen (`server/CLAUDE.md`, `opd`).
- We do not show a serial's time from a schedule box that is still being typed in. The times are told to patients: they come from the SAVED schedule (`useOpdSchedule`), a box keeps what was typed until the server has it, and a save clears only what it sent (`OpdScheduleBar`).

## ⚠️ Patient sex: one word, one vocabulary, never a guess

_From `client/CLAUDE.md`._

**The OPD queue adds a patient by mobile number and nothing else (physician's sheet, 15/10/2026, item 5).** "+ Add to queue" opens `PatientMobileLookup` alone: a patient saved on the number is offered as on the prescription header, and choosing one puts them on the queue at once, tied to their record (`OpdView#addToQueue`); "Add New" (no patient on the number) and "Add person related to …" open the lookup's own boxes, which create the patient, who then joins the queue the same way. The name / age / sex / visit-type boxes and their Add button were crossed out on the sheet and are gone, so **every new queue row now has a Patient record** and is sent with no `type` — the server's default, `New`. Age is sent only when `displayAge` gives a whole number of years, sex only when `normaliseSex` recognises it; a failed add says so in words (never the raw error) and keeps the number in the box, and choosing the patient again retries. **IPD admits the same way since 18/10/2026 (sheet item 5):** the Mobile lookup is the first box of the admit form, the name is SHOWN from the chosen patient (never typed), and Admit waits for a chosen patient — every admission this client makes carries `patientId` (the server still takes one without, from an older build); changing the number lets the patient go, Hospital ID with them (it is the chosen patient's), and a record with no name says why Admit waits (`IpdView.admitByNumber.test.tsx`). The server refuses a `patientId` the practice cannot reach (`server/CLAUDE.md`). **Each queue row starts with its serial, 1, 2, 3 … in the order shown** (physician's request, 18/10/2026) — not the token: T-01 is still stored and not renumbered, but the doctor app shows it nowhere since 29/10/2026 (`OpdView.serial.test.tsx`). **One add at a time** (independent review, 2026-10-17): a pick goes straight to the queue and the server gives a new token each time, so a second pick while the first was on its way put one patient on the queue twice; a ref (not `isPending`, which two picks in one render both read as false) drops it. A retry after an add that LANDED but whose answer was lost no longer adds a second token (19/10/2026): the server answers with the patient's visit still waiting in today's queue whose prescription is not yet printed. A patient seen already today — Done pressed, or their prescription printed (Save & print marks the visit complete and leaves it waiting) — is queued again with a new token (review, 19/10/2026: the first version gave a patient printed in the morning their morning row back in the afternoon). A reused visit keeps its own type. Pinned in `OpdView.addByNumber.test.tsx`.

**The OPD queue is booked by DAY (physician's sheet, 28/10/2026).** The date beside the title is a button that opens `components/opd/OpdDayPicker.tsx` (a `useDialog` popup; arrows MOVE along the days, only a click, Enter or Space CHOOSES — as in the Investigation calendar; every day can be looked at and the past ones are marked locked). `OpdView` holds the day on show (`dhakaToday()` / `dayRelation()`, `lib/opdDay.ts` — a day is a `yyyy-mm-dd` name, never a `Date`, never `toLocale…`); `today` is read at every render, so a screen left open past midnight locks yesterday by itself. **Today** is worked as before (Prescribe, Done). **A later day**: patients are added (the add names the day on show: `date`) and put in order with ▲ ▼ (`useMoveOpdVisit`; a patient moves past the next one still WAITING, and a patient already seen keeps their place and has no arrows); no Prescribe, no Done. **A day that has passed**: shown as it was — no add, no arrows, no actions, the schedule boxes disabled; the server refuses it as well. A form left open on one day is closed when the day changes. **The schedule bar** (`OpdScheduleBar.tsx`, `lib/opdSchedule.ts`): Start time, Break from / to, Minutes per patient. The serial's time is `slotTimes(count, schedule)` — worked out, never stored — and it is read from the **saved** schedule (`useOpdSchedule`), NEVER from the boxes, which keep what is typed until the server has it (a patient is told these times); a save clears only what it SENT; the bar is remounted per day (`key`) so a half-typed schedule can never be saved onto the day the doctor has just moved to; `scheduleProblem` (mirrored in `server/src/opd/schedule.ts`; ONE table of cases in both specs — edit one, edit both) says what is wrong in words before anything is sent, and a 400 from the server is shown as its own sentence (it is written for a doctor), anything else as "Could not save the schedule. Try again.". A day that has passed with no schedule of its own was never told a time, and shows none. **Presence, urgency and status (physician's sheet, 29/10/2026).** Each row has three boxes — Present, Critically ill, Pt needs urgent attention (the third is written in full, as the physician wrote it) — then a Status and a coloured row. Status, colour and the cards' counts are all DERIVED in `lib/opdPresence.ts` (`visitStatus`, `rowTone`, `presentClock`, `queueCounts`) from what the server sent, never stored on the client: the status is the LATEST thing that is true (Completed > Prescription pending > History taken > Waiting > empty), the colour the strongest mark (Urgent > Critically ill > Present). The boxes are enabled on today only (the server refuses another day). A tick is optimistic and rolled back if the server refuses (`useSetOpdPresence`); the settle always re-reads the server, so the list is what the server says. The Present time shown right after a tick is the browser's clock until the server's own replaces it. The photo is `components/opd/PatientAvatar.tsx`: the stored picture, else the app's existing placeholder (`photoPlaceholder` + `Icon`, as in the prescription header) — no second set of drawings. The token chip and the Incomplete / Complete chips are gone from the row; the four cards (Total Serial, Present, Completed, Waiting) carry `data-card` hooks. **Today's queue is read again every ~10 s** (`useOpdQueue`, `OPD_POLL_MS`; not in a background tab; no other day polls), so a mark made by reception on another device shows on a doctor's screen that is already open; a tick just made is protected because `useSetOpdPresence` cancels the day's in-flight read before writing and reads again when its own request settles. **A row of a day other than today shows no status stage** (the server sends `padStage: null` for it: the parked visit is today's). **"Completed" counts a visit that is Done OR printed**, and **"Waiting" is present and not completed** — both changed on 29/10/2026. Pinned in `OpdView.presence.test.tsx`, `opdPresence.test.ts`, `PatientAvatar.test.tsx`. **Print Queue (30/10/2026):** the sheet is built by `client/src/lib/opdQueueDoc.ts` (`buildQueueDoc`; pure, imports no theme, and is on the `rawColours` SKIP list like `prescriptionDoc.ts`), shown in `PrintSheetModal` with `label="OPD queue"`; the doctor named is `activeWorkstation.name` (no line when none), the times come from the SAVED schedule (`useOpdSchedule`), and the button waits for both the queue and the schedule to load (`OpdView.print.test.tsx`). The title (জনাব / জনাবা, Mr. / Ms., none when the sex is not recorded) and the wholly Bangla time are the server's (`server/CLAUDE.md`). ## ⚠️ `opd` — the queue is booked by DAY (28/10/2026)

_From `server/CLAUDE.md`._

`OpdVisit.queueDate` (Dhaka `yyyy-mm-dd`) and `position` (1, 2, 3 …) name a visit's day and place; `OpdDaySetting` holds a day's chamber schedule (`manual-opd-queue-date.sql` — **apply it BEFORE the release is deployed**: every OPD request reads these columns). Rules that are safety, not style:

- **The day is `queueDate`, never `createdAt`.** A patient can be booked today for a later day, so `createdAt` is no longer the day. A row an older build wrote has neither column (and so does one written between the SQL and the deploy): `OpdService.dayWhere` reads it as the Dhaka day it was created, and lists it after the rows that have a place; the next add or move numbers them in the order shown first (`queue-order.ts#renumber`).
- **A day that has passed is locked in the SERVICE** (`PAST_DAY`, `TODAY_ONLY`): add, move and re-time are refused (400, in words for a doctor) before anything is read for writing or written, whatever a client sends. Done is for today only. `setRxStatusByPatient` (Save & print) marks TODAY's visit only — a patient booked for a later day is never the one marked printed. `opd.service.spec.ts` checks each refusal happens before a write; `test/opd-queue.int-spec.ts` runs the rest against the database.
- **Order is a pure function** (`queue-order.ts`): a patient swaps places with the nearest patient still WAITING; someone already seen keeps their place and is not moved. Every write takes the doctor's advisory lock and `ROW_LOCK_TX` (the lock is waited for; Prisma's 5 s default would fail the writes at the back of a queue).
- **The first visit added to a day saves its schedule** (`freezeSchedule`) when the day inherited one, so changing an earlier day later does not move times already told to patients. A day with no schedule of its own takes the latest earlier day's, else the pre-set values (`schedule.ts#DEFAULT_OPD_SCHEDULE`, a copy of the client's).
- **`manual-opd-queue-date.sql` REPLACES the token-unique index.** `manual-opd-token-unique.sql` made a token unique per doctor and per day of `createdAt`; a later day's `T-01`, written today, would collide with today's `T-01`. The new script drops `OpdVisit_doctor_day_token_key` and builds the same guarantee on `(doctorId, queueDate, token)` (skipped with a NOTICE if a duplicate already exists). Checked on a scratch database with an old-shape table: the Dhaka-midnight boundary, a second run changes nothing, a later day's `T-01` is accepted and a true duplicate refused. **It has not been applied to the shared database** (applying it migrates production).
- **Presence, urgency and status (physician's sheet, 29/10/2026).** `OpdVisit.presentAt`, `criticallyIll`, `urgent` (`PATCH /opd/:id/presence`, `manual-opd-presence.sql`). Rules that are safety, not style:
  - **`presentAt` is the SERVER's clock**, never a time a client sends: it is set once and kept if Present is pressed again, and cleared when taken off. A browser's clock can be wrong, and the time is what reception tells the doctor.
  - **Today's queue only** (400 "Only today's queue can be marked present."), refused in the service before any write. Another doctor's visit is a 404; the doctor is `@WorkstationDoctorId()` as everywhere.
  - **`list` and `move` rows carry `pictureUrl` and `padStage`** (`decorate()` in `opd.service.ts`). The draft that `padStage` is read from NEVER leaves the server: the row says `'history' | 'pending' | null`, nothing of the text.
  - **The patient lookup is scoped like `accessibleWhere`** (owner OR supervisor). A visit whose patient the practice cannot reach shows no picture and no stage. The owner's `incompleteRx` is read only for the owner's OWN patients; a supervising practice reads its own `SupervisedDraft` only, so one practice's work in progress never reads as another's.
  - **A missing `SupervisedDraft` table (`P2021`) costs only the stage** of a supervised patient and is logged naming `manual-supervised-draft.sql`; any other error is thrown, not swallowed. A draft whose `ptDate` is not today (or has none) says nothing, so a visit parked yesterday never reads "History taken". **A row of a day other than today carries `padStage: null`** (a visit booked for tomorrow, or left unseen on yesterday's queue, must not read today's draft). The missing-table message is logged once per process, not on every list call.
  - **`HISTORY_FIELDS` / `PENDING_FIELDS` in `src/opd/pad-stage.ts` are the ONE place that names which editor fields count** (physician: "Chief complaints or any data entry"). Change the lists there, nowhere else; the client has no copy.
  - **`manual-opd-presence.sql` has NOT been applied to the shared database and must be applied BEFORE the release is deployed:** it adds three columns, and every queue read selects them.
- **⚕️ Chambers (physician's sheet 28/10/2026, item 8; 01/11/2026).** A practice sits in several chambers (Labaid, Ibn Sina), each with its OWN queue, tokens, schedule and OPD print settings. `OpdChamber` / `OpdChamberLayout` (`src/chambers/`, `manual-opd-chambers.sql` — **apply it after `manual-opd-queue-date.sql` and BEFORE the release**: every queue read selects `chamberId`). Rules that are safety, not style:
  - **`ChambersService.resolve(doctorId, X-Chamber)` is the ONE place that decides the chamber** — the header is a claim. No header or the default chamber's id → NULL; another live chamber of THIS practice → its id; another practice's, a removed one or a made-up id → 404 (never a quiet fall-back: a patient in the wrong chamber's list is told the wrong place). The OPD controller resolves it and passes `chamberId` into the service (`list`, `create`, `getSchedule`, `saveSchedule`, `setRxStatusByPatient`); calls on one visit by id (status, presence, move) act where the visit is (move within its own chamber).
  - **NULL is the DEFAULT chamber**, always: every row from before chambers, and every new row of the default (never stored with its id), so the default's list is one predicate and nothing was backfilled. The default is made on the first `GET /chambers` (under an advisory lock; one per doctor, partial unique index), named "Main chamber", address copied once from the profile's first chamber; it cannot be removed.
  - **NOT the profile's `Chamber` table**: `users.service.ts` deletes and recreates those rows on every profile save, so nothing may point at them.
  - **Uniqueness moved to expression indexes Prisma cannot express**: `(doctorId, COALESCE(chamberId,''), queueDate, token)` and `(doctorId, COALESCE(chamberId,''), day)` replace `OpdVisit_doctorId_queueDate_token_key` and `OpdDaySetting_doctorId_day_key` — the new one is built first and the old dropped only once it exists; a duplicate is a NOTICE, the old index then stays (a second chamber's `T-01` on that day would fail until it is de-duplicated). `schema.prisma` has `@@index([doctorId, day])` on `OpdDaySetting` now, so the schedule is found with `findFirst` and written under the queue's lock (no `upsert` on `doctorId_day`). Verified on a scratch database with old-shape tables (idempotent second run, both guarantees, the duplicate NOTICE); `test/opd-chambers.int-spec.ts` applies the SQL to the test database itself.
  - **Chamber print settings are OPD only** (`GET|PUT|DELETE /chambers/:id/layout`): no row → the doctor's own `PrescriptionLayout` prints; the first PUT starts from the practice doctor's settings. Chambers and their settings are written by the OWNER only (`ws.role`); an assistant reads them and chooses one.
  - **A schedule is inherited only from the SAME chamber's earlier days**; a new chamber starts from the pre-set values.
